日期：2026-08-18
狀態：**未開始（0%）**，因為目前沒有 Raspberry Pi 5，也沒有第二台主機。

本文件的用途有兩個：

1. 讓報告能把這個缺口寫成**有明確驗收條件的未完成項目**，而不是含糊帶過。
   「我們定義了驗收標準但硬體未到」遠比「這部分沒做」好辯護。
2. 硬體一到就能照著執行，不必再重新設計。

## ⚠️ 2026-09-02 更正：Pi 5 是 TurtleBot 的機載電腦，不是獨立閘道

Jesse 指出 Pi 5 要**在 TurtleBot 上跑自動巡邏系統**。本文原本寫「目標主機
（跑 ROS 2 stack ＋ nftables）」，語意上不算錯，但沒有反映它同時是機器人的
機載電腦。三件事因此改變：

### 一、負載變成三份而不是一份

  `turtlebot3_bringup`（馬達 ＋ LiDAR 驅動）＋ 巡邏／導航
  ＋ 安全 stack（monitor／guard／IDS／HMAC 驗章）
  ＋ pcap 擷取

**不需要 Gazebo**——那是模擬器，真機不跑。先前寫的「不要在 Pi 上跑 Gazebo」
方向正確但框錯了：要避免的是模擬器，不是機器人 stack。

### 二、供電路徑是最可能咬人的地方

TurtleBot3 的標準設計由 **OpenCR 板供電給 Pi**，而那個設計是為 Pi 3B+／4
做的。Pi 5 的電流需求更高，**供電不足時它不會關機，而是限制 USB 總電流**
——而 **LiDAR 是 USB 供電的**。

失效模式：LiDAR 間歇掉線 → `/scan` 斷續 → **看起來像感測器攻擊或防禦誤判**。
這與本專案已經記錄九次的形態同類：硬體限制偽裝成安全事件。

⚠️ 我對 OpenCR 5V 軌的確切額定值沒有把握，**這是要量的不是斷言的**：
接上之後先用 `vcgencmd get_throttled`（非 0 即代表曾經限流）與
`dmesg | grep -i usb` 量一輪，再決定要不要給 Pi 獨立供電。

### 三、因此從「建議」變成「幾乎必要」的

| 項目 | 理由 |
|---|---|
| 8GB RAM | 三份負載並存 |
| 主動散熱 | 持續負載，不是間歇 |
| NVMe 或 A2 級卡 | pcap 寫入與導航搶 I/O；**掉封包會偽裝成「攻擊沒送到」** |
| 27W USB-C PD（若獨立供電） | Pi 4 的 15W 電源會降頻 |

### 四、一個仍需決定的設計問題

本文其他地方寫 Pi 5 是「**房間級**部署平台」。但防火牆若跑在 TurtleBot 上，
它保護的是**機器人自己**，不是房間裡其他裝置——nftables 封鎖的意義也不同：

| 部署位置 | 封鎖保護誰 |
|---|---|
| 機器人上（host-based） | 機器人自己 |
| 獨立閘道（room-level） | 整個網段 |

兩種都成立，但**論文要主張哪一種必須先定**，因為它決定驗收條件怎麼寫。
本文以下各節仍以原本的房間級假設撰寫，尚未依這個更正調整。

## 二、需要的硬體

| 項目 | 用途 | 備註 |
|---|---|---|
| Raspberry Pi 5 | 目標主機（跑 ROS 2 stack ＋ nftables） | 專題設定的房間級部署平台 |
| 第二台主機 | 攻擊者 | 任何能跑 ROS 2 的 Linux 機器即可，不必是 Pi |
| 實體網路隔離 | 兩台獨立網段，**不可有預設路由、不可通外網** | 見第三節 |

> 攻擊者不必是第二台 Pi。重點是**兩個不同的實體 machine_id／boot_id／hardware_id**——
> 驗證器會比對三者的雜湊，相同就直接拒絕。用 VM 或容器偽裝**過不了**。

## 三、網路拓撲的硬性要求

`isolated_topology.verify_isolated_topology_report` 會拒絕不符者，這些不是建議：

| 欄位 | 必須是 | 為什麼 |
|---|---|---|
| `same_physical_host` | `false` | 同機不算跨主機 |
| `default_route_present` | `false` | 有預設路由代表可能外洩到校園網 |
| `internet_reachable` | `false` | 同上 |
| `attacker_owned` / `target_owned` | `true` | 只能打自己的機器 |
| 兩台的 `network_cidr` | **相同** | 必須在同一隔離網段才是有意義的攻防 |
| 兩台的 `ipv4_address` | **不同** | 顯而易見 |
| `machine_id` / `boot_id` / `hardware_id` 雜湊 | **三者都不同** | 這是「真的是兩台機器」的證明 |

**建議接法**：一條網路線直連兩台，或一台不接上游的獨立交換器。
不要接到宿舍／校園網路。

> ⚠️ 這一步是整個專題唯一會產生**真實網路攻擊流量**的階段。
> 依 `專題執行基準_2026-07-29.md` §5，共用網段禁止掃描與攻擊流量。
> 必須實體隔離之後才能開始，而且要另外取得 Jesse 的明確授權。

## 四、五個 BLOCK 各自需要什麼

### 4.1 `isolated_cross_host_topology`

在**每一台**上各跑一次收集，兩份證據放同一目錄：

```bash
python3 -m firewall_lab.isolated_topology collect \
  --role target --interface eth0 \
  --output target_host.json --owned-ack <ACK>
```

然後產生彙總宣告。驗證器會重新雜湊兩份主機證據，
彙總裡的 `attacker_ip`／`target_ip`／`capture_interface` 必須與證據**逐欄相符**。

### 4.2 `local_defense_outcomes`（九項本機 outcome）

**這一項不需要第二台主機**，可以先做。流程已寫在
`firewall_lab/LOCAL_OUTCOME_LIVE_RUNBOOK.md`：

- 全部九項共用**同一個 collector session_id** 與同一份停止後的 telemetry JSONL
- observer 走專屬 `/local_outcome_probe` enclave，只有訂閱權，無控制發布權
- 每個 stage 上限 60 秒，observer 單次上限 300 秒
- 缺階段、來源錯誤、collector 中斷、hash 改變、或只寫 `passed: true` 都會 fail closed

> 依 Codex 在 C2C-004 第 5 點的意見：其中要求「無憑證 participant 產生
> permission deny」的那一項，在 security sink 配置好之前恆為不可達。
> 現在 sink 已配置（`fastdds_security_log.xml`），這一項應該可以真正驗證了，
> 但**尚未實測**。

### 4.3 `response_backend_recovery`（kernel nftables 驗收）

**自述式報告已經不被接受**，必須是特權 kernel 狀態的證明。要證的是：

1. 規則**真的進了 kernel**（`nft list ruleset` 能看到，不是程式說它加了）
2. **timeout 會自動到期**（等待後規則自行消失，不是靠程式刪）
3. **撤銷可行**（票證到期或撤銷後規則消失）
4. **重啟後復原正確**（重開機後不留下孤兒封鎖規則）

第 2 與第 4 項最容易被跳過，但正是「暫時封鎖」與「永久封鎖」的差別。
本專題主張的是可撤銷的暫時封鎖，這兩項不過就不能這樣宣稱。

> 這一步需要 **root**。依專案規則必須另外取得授權。

### 4.4 `live_multimodal`

contract 目前 `blocked`，blocker 是「安全模式必須被證明無法從網路特徵還原」。
實測 separability 是 **0.9451**（門檻 0.70）——**這一項在目前設計下不會通過**。

這不是缺工作，是既有的研究結論：DDS Security 改變流量形狀，因此改為分模式訓練。
建議把 contract 的這一條改寫成「已量測並據以改採分模式訓練」，
而不是留著一個永遠不會綠的 gate。**此決定尚未做，需與 Codex 對齊。**

### 4.5 `deployment_model`

需要 `deployment_eligible=true` 的已簽章模型。目前兩個模型都是 `false`，
因為 balanced accuracy 0.5587／0.2660 遠低於門檻 0.80。

依 §5.2.4 的結論，這要靠**替缺證據的類別設計專屬遙測**才可能改善，
不是調模型。所以這一項實質上排在最後。

## 五、建議順序

| 順序 | 項目 | 需要 | 可否現在做 |
|---|---|---|---|
| 1 | 九項本機 outcome | live 授權，**不需硬體** | ✅ 可以 |
| 2 | 驗證 security sink 與 N1 QoS 修正 | live 授權，不需硬體 | ✅ 可以 |
| 3 | 專屬遙測設計 ＋ 一次完整重跑 | live 授權，不需硬體 | ✅ 可以 |
| 4 | 隔離拓撲宣告 | **兩台主機** | ❌ 等硬體 |
| 5 | kernel nftables 驗收 | **Pi 5 ＋ root** | ❌ 等硬體 |
| 6 | 部署模型 | 取決於第 3 項的結果 | 排最後 |

**第 1–3 項不需要任何硬體。** 若硬體遲遲不到，這三項做完仍能把
「回應／執行」從 20% 推到約 50%，並讓識別率有機會改善。
