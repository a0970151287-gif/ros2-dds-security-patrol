# 第二層守衛：可撤銷的 GUID 阻斷（原型）

**結果：封鎖 → 解除 → 恢復的完整循環成立，兩個方向都在 25 毫秒內。**

這是三層回應鏈裡唯一**可撤銷**的一層，也是唯一能承載 IDS 判定的一層——
因為 IDS 會錯，而錯了必須能收回。

證據：`文件/第二層守衛證據_2026-08-26/`

---

## 一、為什麼需要這一層

| 層 | 動作 | 可逆 | 誰能觸發 |
|---|---|---|---|
| 1 | DDS `ignore_participant` | ❌ **不可逆** | 只有密碼學證據（認證失敗） |
| **2** | **依 GUID 丟棄訊息** | ✅ **可撤銷** | **IDS 行為判定** |
| 3 | nftables | ✅ | 網路層持續濫用 |

設計原則：**動作的不可逆程度必須配得上證據的確定程度。**

IDS 的判定是統計的、會錯——處女 holdout 的 open-set recall 只有 **0.0273**，
而在 family-LOO 最差 fold 的已知誤否決高達 0.2556。把不可逆的權力交給這種
判定是不合理的。所以 IDS 只能觸發第二層。

而 Fast DDS 的 header 明文寫著：

```
Locally ignore a remote domain participant.
@note This action is not reversible.
```

`ignore_topic`／`ignore_publication`／`ignore_subscription` 三個更是
`RETCODE_UNSUPPORTED`。**DDS 標準沒有提供可撤銷的阻斷原語**，所以第二層
必須自己做。

## 二、實作

`firewall_lab/security_observer/guard_filter.cpp`

### 2.1 為什麼是 C++

2026-08-26 實測：`publisher_gid` 在 **rclpy 完全沒有露出**——`message_info`
只有 `publication_sequence_number`、`received_timestamp`、
`reception_sequence_number`、`source_timestamp` 四個鍵。只有 rclcpp 拿得到，
而且 `rmw_fastrtps` 確實有填（`populated=yes`）。

沒有發送者身份就無法依身份丟棄，所以這一層**只能用 C++ 寫**。
現有的 `monitor_node.py`、`velocity_guard_node.py` 都是 Python。

### 2.2 為什麼黑名單用檔案

- **不用 ROS topic**：控制訊息不該走在攻擊者所在的那條匯流排上
- 可稽核、可撤銷、重啟後仍在
- 與本專案既有的 fault seam 慣例一致

檔案不存在 = 空黑名單。這是刻意的：讓「還沒有任何封鎖」與「黑名單被刪掉」
表現一致，都是全部放行。

### 2.3 允許與丟棄都要記

決策日誌兩種都寫。只記丟棄的話，**無法分辨「沒有丟棄」與「守衛根本沒在跑」**
——這正是本專案被咬過好幾次的那類陷阱。

## 三、實測：完整循環

發送者 1 Hz，守衛每 200 毫秒檢查一次黑名單 mtime。

```
  -6.59s  allow          ← 封鎖前，7 筆
  -0.60s  allow
  +0.02s  ** 黑名單重載：1 筆 **
  +0.40s  drop           ← 開始丟棄，8 筆
  +7.40s  drop
  +8.02s  ** 黑名單重載：0 筆 **
  +8.40s  allow          ← 恢復放行，8 筆
 +15.40s  allow
```

| 量測 | 值 |
|---|---:|
| **啟用延遲**（寫入黑名單 → 生效） | **0.0225 秒** |
| **撤銷延遲**（刪除黑名單 → 生效） | **0.0109 秒** |
| 訊息層首次丟棄 | 0.4027 秒 |
| 訊息層恢復放行 | 0.3911 秒 |
| 封鎖期間漏放行 | **0 筆** |
| 撤銷後恢復 | 8 筆 |

訊息層的 0.4 秒**不是守衛的延遲**，是 1 Hz 發送週期造成的——守衛在
22 毫秒內就已經生效，只是要等下一則訊息才看得到效果。真實系統的
`/cmd_vel` 是 10 Hz 以上，那個間隔會小一個數量級。

**撤銷比啟用還快**（10.9 毫秒對 22.5 毫秒），因為刪檔的 `stat` 失敗路徑
比讀檔快。兩者都遠低於 200 毫秒的輪詢上限。

### 對照既有的速度守衛

| 機制 | 延遲 | 可撤銷 |
|---|---:|---|
| 速度守衛歸零（既有） | 0.0187–0.2100 秒（六次量測） | ✅ |
| **GUID 阻斷（本層）** | **0.0109–0.0225 秒** | ✅ |

同一個數量級，而且本層是**依身份**而不是依整體狀態——可以只擋一個發送者，
不影響其他人。

## 四、還不能宣稱什麼

1. **這是原型，不在資料路徑上。** 它只做判定與量測，**不轉送訊息**。
   要真的擋住必須改變拓撲（發送者 → 守衛 → 消費者），那是下一步。
   所以目前它證明的是「判定機制與撤銷機制成立」，不是「訊息真的被擋下」。
2. **沒有接上 IDS。** 黑名單目前由測試腳本寫入。要讓 IDS 驅動，
   需要把模型判定接到黑名單寫入端，而那必須經過授權器
   （`executable_classes` 仍為空清單）。
3. **同機、未啟用 SROS2、domain 77。** 這一輪只驗機制，沒有安全模式。
   與 SROS2 同時啟用時的行為未測。
4. **黑名單檔案本身沒有完整性保護。** 誰能寫那個檔案就能封鎖任何人。
   正式版需要簽章或權限限制（本專案的 fault seam 用 0600／0700，
   可以沿用）。
