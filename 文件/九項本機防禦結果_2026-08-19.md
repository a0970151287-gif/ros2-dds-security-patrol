## 二、已取得的五項

五項全部由真實 ROS 事件重算，**每一項都在單一場 session 內完整成立**。因 observer
有 300 秒硬上限，五項分屬兩場 session（`…ada2223a` 四項、`…86f283de` 含 oversized）。

### 1. `normal_traffic_preserved`

```
required_topics_live      : true      （scan / odom / imu 皆有訊息）
authenticated_heartbeat_live : true
final_cmd_vel_observed    : true      （唯一合法 publisher = velocity_guard_node）
unauthorized_publishers   : 0
```

⚠️ 這一項有變異性：另一場出現 `authenticated_heartbeat_live: false`。
寫報告時不應描述成必然成立。

### 2. `unauthorized_participant_denied`

```
unauthorized_delivery_count : 0
protected_state_unchanged   : true
authorized_participant_healthy : true
sros_deny_evaluable         : false   ← 誠實標記
```

`sros_deny_evaluable: false` 明確記錄「廠商拒絕記錄在本技術棧取不到」
（見 `DDS_Security_audit_log_不可用_2026-08-18.md`），判定改綁在**送達數為 0**
這個可量測的性質上。**沒有把「沒看到」算成通過。**

### 3. `hmac_forgery_dropped`（內部威脅模型）

```
bad_hmac_reject_count : 11
forged_accept_count   : 0
state_unchanged       : true
next_valid_accepted   : true
```

攻擊者持**合法 SROS2 憑證**（模擬 IDS 節點被攻陷），但沒有 HMAC 共享金鑰。
SROS2 放行了他，HMAC 仍然擋下全部 11 則偽造訊息，而下一則真訊息照常通過。

**這是分層防禦第一次被直接量到，而不是推論。**

偽造刻意用攻擊者自己生的 32 位元組金鑰去簽**格式完全正確**的信封，只有 HMAC
對不上。否則會被判 `malformed_envelope`——那證明的是解析器擋住畸形輸入，不是
簽章檢查擋住偽造，是兩道不同的防線。

### 4. `oversized_input_dropped`（內部威脅模型）

```
oversized_reject_count : 7
oversized_accept_count : 0
process_alive          : true
state_unchanged        : true
next_valid_accepted    : true
```

**修正過程本身是個警訊。** 第一版送 8,192 點的 scan（上限 4,096）**一次都沒觸發**；
改成 4,097 點才正常。8,192 點約 32KB，大樣本在預設 Fast DDS buffer 下於傳輸層
就被丟掉。

> **「訊息根本沒到」與「防禦擋下了」在遙測上完全一樣。**
> 攻擊要取「剛好超過門檻」，不是「遠遠超過」。

### 5. `velocity_guard_zeroed`

停車延遲六次獨立量測：**0.0187 / 0.0293 / 0.0525 / 0.1155 / 0.1235 / 0.2100 秒**，
全部在 250 毫秒內。鎖定期間線速度與角速度絕對值上限皆為 **0.0**。

## 三、未取得的四項：逐項原因

### 6. `replay_dropped` — 重放抵達了，但撞的是另一道防線

實測（兩場）：

| session | 重放次數 | `timestamp_violation` | `nonce_reuse_or_capacity` |
|---|---:|---:|---:|
| `…c418d496` | 12 | 12 | **0** |
| `…1b05b6bd` | 12 | 126 | **0** |

四種排法全部試過，全部輸掉同一場競速：

1. 側錄放在整場開頭、90 秒後重放 → 必然過期。
2. 側錄成功才啟動重放行程 → rclpy 匯入＋DDS discovery 就吃掉數秒。
3. 重放行程先起、先 discovery，用獨立 go 檔控制發送時機。
4. 側錄端只收信封 `ts` 在 2 秒內的樣本（防 TRANSIENT_LOCAL 陳舊快取）。

**結論（可寫進報告）：這套系統的 anti-replay 不是靠 ReplayCache 生效的。**

時間戳窗（alerts 10 秒、心跳 3 秒）加上最小權限 ACL 讓重放**來不及發生**：
要夠快，側錄與重放必須在同一個行程內完成；但沒有任何 enclave 同時擁有某個安全
頻道的發布與訂閱權（monitor 只發心跳、IDS 與 guard 只收；alerts 亦然）。
**ACL 強迫攻擊者跨行程，而跨行程的成本超過了新鮮度窗。**
ReplayCache 是第二道，不是第一道。

附帶觀察：alerts 是 TRANSIENT_LOCAL，後加入的訂閱者會先拿到 durability 快取裡的
**陳舊** alert。攻擊者就算側錄到真品簽章訊息，拿到的也是過期品。

### 7. `parameter_unchanged` — 三重阻塞

| 層 | 阻塞 |
|---|---|
| SROS2 ACL | policy 明文：**沒有任何節點**獲得 `services request` 參數權限，連內鬼也送不了 `set_parameters` |
| rcl | `whitelist` 宣告時帶 `read_only=True`，rcl 在 `on_set_parameters` callback **之前**就拒絕 |
| 遙測 | `parameter_veto` 掛在那個 callback 裡 → 對 whitelist **永遠不會發**；`SECURITY_LOCKED_PARAMS` 只有 `use_sim_time` |

**這暴露了檢查本身的語意矛盾**：`baseline` 與 `protected` 監看 `whitelist` 的
digest，`trigger` 卻要求一個 whitelist 永遠產生不了的 veto。另一個可接受的證據
`sros2_deny kind=permission` 在本技術棧 source_unavailable。

三個 stage 中 `baseline`、`protected`、`recovery` 都可取得，只有 `trigger` 不可能。

### 8. `velocity_guard_recovered` — 兩個 stage 曾經互相排斥

原本用 SIGSTOP 整個 monitor 行程，兩個 stage 因此**透過凍結時間直接對立**：
`trigger` 要等 D5（10 秒）之後的 `monitor_fault` 轉換，凍久一點才穩；但凍結超過
約 40 秒，DDS liveliness lease 就把 participant 判死，心跳再也不回來。
五次嘗試：trigger 成功 2 次、recovery 成功 2 次、**同場同時成功 0 次**。

已實作**受控心跳抑制接縫**（只跳過 `_publish_heartbeat` 的 publish 那一行，
行程與 participant 照常運作），對立因此消失。它確實運作過一次完整證據：

```
239.41  guard_state locked/monitor_fault   ← fault_latched
257.22  authenticated_action guard_clear    ← 故障後約 23 秒，對應 hold 24 秒
257.25  guard_state released
```

但其後兩輪 arm 檔寫入後 monitor 未消費，根因未定位，因此**不宣稱通過**。

### 9. `graph_failure_fail_safe` — 結構性不可得

實測時間軸（同一場，單位秒）：

```
92.18  detector_state  d4 = incident         ← trigger 窗需要
92.22  guard_state     locked/generic_alert  ← protected 窗需要（差 0.04 秒）
94.84  graph_state     fault                 ← trigger 窗需要
```

`trigger` 必須同時涵蓋 d4 與 `graph_state=fault`，所以 guard lock **必然**被關在
trigger 裡；而 `guard_state` 只在轉換時發一次，`protected` 於是永遠是空的。
兩者相隔 0.04 秒，而一個窗邊界光是確認 marker 落地就要 0.7 秒。

嘗試過「兩次故障」（第一次取 trigger、等 guard 釋放後再故障一次）——**不可行**：
seam 是「每個行程最多消費一張 arm」，第二張 arm 寫進去了但沒有任何行程消費它。
那是刻意的安全保證，不該為了讓一項檢查過而拿掉。

**要讓這一項成立，必須讓 guard 的已驗章鎖定晚於故障偵測——那是改防禦行為去
遷就量測。不建議。** 正確的修法是改檢查本身：讓 `protected` 接受「窗內處於鎖定
狀態且輸出為零」，而不是要求窗內出現一次鎖定「轉換」。

## 四、四項阻塞裡有三項是防禦有效的證據

| 項目 | 阻塞原因 | 這代表什麼 |
|---|---|---|
| `replay_dropped` | ACL 強迫跨行程，超過新鮮度窗 | 最小權限讓重放來不及發生 |
| `parameter_unchanged` | 無人有 `services request` 權限 | 連內鬼都改不了安全參數 |
| `graph_failure_fail_safe` | guard 在 40 毫秒內就鎖定 | 反應快到量測窗切不開 |

只有 `velocity_guard_recovered` 是真正的工程缺口（接縫觸發不穩定）。

**這個檢查表在本系統上永遠不會全綠**，因為它的幾項前提與實際防禦行為不相容。
建議與檢查表的設計者討論語意調整，而不是修改防禦去配合檢查。

## 五、量測工具自己造成的三個缺陷（都已修）

這三個都會**偽裝成「防禦沒反應」**，值得單獨記錄：

| 缺陷 | 症狀 |
|---|---|
| 等待器每輪重讀整份 JSONL | 22 秒的等待做出 **137 秒**的窗，撞上 60 秒安全上限 |
| 窗起點行號取在 marker 前／後 | 取前 → 匹配到窗外舊事件；取後 → 漏掉 marker 那 0.7 秒內的轉換 |
| marker 輔助函式全檔掃描 | 開窗與關窗本身就撐爆窗（80.3 秒 → 7.5 秒） |

另有兩個同類的執行面缺陷：受控 seam 的目錄必須在 stack **之前**建立（否則每個
行程都以 `enabled=false` 啟動），以及攻擊者自己也是 ROS 節點，它加入／退出 graph
會改變 state digest，`protected` 窗必須等它離開後再開。

> 共同教訓：**觀測工具自己的缺陷，會偽裝成被觀測系統的問題。**
> 這也是本專案第三、四次踩到「沒送達」與「被擋下」在遙測上無法區分的坑。
