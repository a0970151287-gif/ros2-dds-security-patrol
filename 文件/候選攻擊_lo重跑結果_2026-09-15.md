- 日期：2026-09-15
- **經 Jesse 對本次操作明確授權執行 live**：同機、loopback、Permissive、domain 30。
  未使用 `sudo`、未修改防火牆、未連接第二台主機。收尾後逐項確認**零殘留行程**。
- 批次：`~/candidate_smoke_lo_20260915T074804Z`（8 場：5 支候選 ＋ 3 場基線）
- 相關：`候選攻擊的網路層重判_擷取無效_2026-09-15.md`（為什麼要重跑）

## 0. 一句話

擷取介面修好之後（`eth1` → `lo`，單播佔比 0% → 80–94%），gate 從「三支不可分」
變成 3／5 通過；但**同一批資料裡出現了一個我沒有設計的陰性對照**，它證明
那些「專屬訊號」有一大部分是「一個不在白名單的節點加入 graph」產生的，
不是攻擊產生的。

## 1. 前置：先確認環境能跑，再跑

Jesse 把筆電帶離家裡，網路變了，而 WSL 的 mirrored 初始化失敗、退回
`networkingMode None`——**沒有 eth0／eth1，只剩 `lo` 與 `docker0`**，而且
`lo` 上掛著 `10.255.255.254/32 scope global`，那正是 C2C-043 量到會讓
Fast DDS 同機 discovery 靜默失效的東西。

所以先跑一個 12 秒的 loopback 連通性測試（一個 talker、一個 echo、一份擷取，
**沒有攻擊流量**），兩道都要過才准開始：

| 檢查 | 結果 |
|---|---|
| DDS 同機 discovery | **收到 91 則**（門檻 ≥5）✅ |
| `dumpcap -i lo` 看得到單播 RTPS | **1,084 個封包、100% 單播** ✅ |

`ROS_LOCALHOST_ONLY=1` 讓 Fast DDS 避開了 `10.255.255.254`，所以那個位址在
這個設定下不咬人。**沒有這一步的話，失敗會長得像「攻擊沒效果」。**

另外 Gazebo 花了 **39 秒**才起來——中途查看時 `gz sim` 是 0，而那正是
C2C-044 記錄過「Gazebo readiness failed」的表面症狀。這次是慢，不是壞。

## 3. Gate 結果：3／5 通過

| 候選 | 攻擊執行 | 專屬訊號 | verdict |
|---|---|---:|---|
| `baseline_poisoning` | ✅ rc=0 | 3 | ✅ 通過 |
| `node_name_evasion` | ✅ rc=0 | **0** | ❌ 拒絕 |
| `verify_flood` | ❌ **rc=2** | — | ⛔ **本場作廢** |
| `odom_spoof` | ✅ rc=0 | 4 | ✅ 通過 |
| `spdp_flood` | ✅ rc=0 | 6 | ✅ 通過 |

`verify_flood` 的 rc=2 是**我自己在 commit `cd8ee1b` 加的配對訂閱者守衛**擋下的：

```
⛔ /security/heartbeat 上沒有任何 QoS 相容的訂閱者配對（等了 8 秒）。
   這次攻擊不會送達，不執行。若對方是 RELIABLE，請用 `reliable` 當第三個參數。
```

gate 因此判 `void_attack_did_not_run`，**而不是**「沒有專屬證據」。
這兩件事在資料上長得一樣，意義完全不同——這正是加那道守衛的目的。

## 4. 那道守衛順便造出了一個我沒設計的陰性對照

`verify_flood` 的攻擊**一個位元組都沒送**，但那一場的遙測是：

| class | rc | `hmac_result.channel=alerts` | `guard_lock` | `log_reject` |
|---|---:|---:|---:|---:|
| normal ×3 | — | **0** | **0** | 0 |
| `baseline_poisoning` | 0 | **4** | **1** | 0 |
| **`verify_flood`** | **2（沒執行）** | **4** | **1** | 0 |
| `node_name_evasion` | 0 | 0 | 0 | 0 |
| `odom_spoof` | 0 | 16 | 4 | 1 |
| `spdp_flood` | 0 | 111 | 28 | 3 |

**攻擊沒執行的那一場，訊號與 `baseline_poisoning` 逐位相同。**

成因很直接：N20 在檢查訂閱者**之前**就已經 `rclpy.init()` 並建立節點
`attacker_verify_flood`。monitor 看到一個不在白名單的節點 → 發一則 alert →
守衛鎖定。整個「專屬訊號」就是這個。

> **gate 的判準（「基線恆為零」）被「有一個不在白名單的參與者加進來」滿足了。
> 任何會連線的攻擊都會產生它。那不是類別證據。**

這給了一個**經驗地板**：`4 次 alert ／ 1 次 guard_lock ／ 0 次 log_reject`。
用它重讀上面那張表：

| 候選 | 相對地板 | 重讀 |
|---|---|---|
| `baseline_poisoning` | **正好在地板上**（4／1／0） | 通過**不代表**攻擊留下痕跡 |
| `odom_spoof` | 4×（16／4／1） | 地板之上，訊號是真的但弱 |
| `spdp_flood` | **28×**（111／28／3） | 明顯在地板之上 |
| `node_name_evasion` | **在地板之下**（0／0／0） | 見第 6 節 |

---

## 5. 候選彼此分得開嗎——gate 沒問的那個問題

活狀態表那句「三支**彼此**不可分」問的不是 gate 問的問題。直接算：

```
四個有訊號的候選，**全部共有**的訊號 3 個（都是 hmac_result.channel=alerts 的變體）
baseline_poisoning  只有它有的訊號  0 個
odom_spoof          只有它有的訊號  0 個
verify_flood        只有它有的訊號  0 個
spdp_flood          只有它有的訊號  2 個  ['log_reject', 'log_reject.count>0']

兩兩 Jaccard：baseline_poisoning ↔ verify_flood = 1.00（完全相同）
              最低 0.50（spdp_flood 對其餘）
```

（`odom_spoof` 也有 1 次 `log_reject`，但 gate 的 `min_count` 是 3，沒有達標。）

⇒ **`spdp_flood` 可分，`baseline_poisoning` 不可分。** 原本那句話**對一半**。

---

## 6. `node_name_evasion` 的 0 是結果，不是缺口

它是唯一連「加入的 alert」都沒有的候選——**連地板都沒踩到**。
它的機制就是取一個能繞過白名單比對的節點名，所以 monitor 根本沒有把它
當成未知節點。

**那不是「偵測不到這個攻擊」，是「這個規避手法成功了」**，而且是本批唯一
一個對防禦有直接意涵的結果。它的 ❌ 是正確答案。

---

## 7. `verify_flood` 的根因已定位並修好

`firewall_lab/runners.py` 傳的第三個參數是 `"be"`（BEST_EFFORT），而防守端
`intelligent_defense_node.py` 的 `/security/heartbeat` 用 `qos_hb`，是 **RELIABLE**。

DDS 的相容規則是單向的：**BEST_EFFORT writer 配不上 RELIABLE reader。**
所以那一支從 2026-09-02 到現在從來沒有送出過任何東西。

已改成 `"reliable"`，並新增 `tests/test_attack_deliverability.py`（5 個測試）：

1. **前提查核**——直接讀防守端程式確認 `qos_hb` 真的是 RELIABLE，不是憑記憶。
2. `verify_flood` 的 argv 不得含 `be`。
3. **全 catalog 掃描**（出貨 ＋ 候選），不只這一支。
4. **變異測試**——把 argv 還原成 2026-09-02 的樣子，判準必須咬人。

⚠️ **`verify_flood` 仍然是「未評估」**。修好了配置，但還沒有一場真的跑過它。

## 9. 不可宣稱

- **每類 1 場、基線 3 場。** 地板（4／1／0）是從**單一**場次估的。
- gate 的 `min_count=3` 讓 `odom_spoof` 的 1 次 `log_reject` 沒達標；
  改門檻會改變「誰有專屬訊號」，而我沒有動它。
- 只有 Permissive。Enforce 下這些候選的行為沒有量。
- **這一批不是訓練資料**，沒有進任何特徵表，出貨 catalog 一個位元未改。
- `spdp_flood` 在封包層為什麼只多 16 個多播（C2C-061 §5 留的問題）
  **本輪沒有回答**——這次的擷取在 `lo`，與那個問題問的 `eth1` 不是同一件事。

## 10. 給下一次的提醒

1. **gate 的判準需要一條「加入地板」。** 目前它比對的是基線（正常流量，
   沒有任何額外參與者），所以「有人加進來」必然滿足它。正確的對照組應該是
   **一個什麼都不做、只加入 graph 的參與者**。這一輪是靠 `verify_flood`
   意外提供的。建議把它變成 catalog 裡的一個正式 scenario。
2. **fail-closed 守衛的副產物比守衛本身更有價值。** 那道守衛原本只是要避免
   一場白跑，結果它產生的「攻擊沒執行但環境相同」的場次，正好是判準需要的
   陰性對照。
3. 這是第九次「量測工具的性質決定了結論」——前八次列在
   `候選攻擊的網路層重判_擷取無效_2026-09-15.md`。
