# 跨主機鏈：防守端就緒，而 NAT 封死了 WSL（2026-10-07）

三台機器第一次同時可用。這一輪把**防守端完整佈建在 Pi 上**並建立對照組，
然後用一個決定性的對照量掉一個原本只是推論的限制：
**NAT 後面的 WSL 不能當這條鏈的任何一端。**

鏈本身**仍然沒有跑過** —— 卡在攻擊端，見最後一節。

---

## 一、拓樸：管理網與實驗網必須分開

```
桌機 192.168.0.141 ─┐                         DESKTOP-R94VLR5（Windows）
筆電 192.168.0.142 ─┼── 路由器 192.168.0.1    campaign 在這台
Pi   192.168.0.145 ─┘   （wlan0，實驗網路）
  └─(網路線)─ Pi eth0 192.168.137.2            ← 管理通道，直連筆電
```

一開始我建議把 Pi 的線從筆電改插路由器。**那個建議是錯的方向**：
正確的結構是**兩條網路各司其職**——

| | 用途 | 為什麼必須分開 |
|---|---|---|
| 直連線（`eth0`） | ssh 控制 | nft 封鎖實驗若把控制通道自己封掉就救不回來。C2C-070 記過 `sudo` 的 `env_reset` 會剝掉 `SSH_CONNECTION`，讓防鎖死閘變成 no-op——有獨立的 out-of-band 通道之後，那個風險才真正消失 |
| Wi-Fi（`wlan0`） | 實驗流量 | 歸因要有意義，攻擊端與防守端必須同一個 L2 廣播域 |

**同 L2 已經驗證**：Pi 的鄰居表直接記著
`192.168.0.141 lladdr e8:65:38:20:23:2f` ⇒ 它看得到桌機的**真實 MAC**，
沒有 AP isolation。所以 C2C-051 加的第四條判定（來源 MAC 對 ARP 解析 MAC，
擋位址偽造）在這個拓樸下**真的有判別力**，不是裝飾。

⚠️ 那張網卡的 MAC 與 C2C-052 記下的攻擊機網卡**逐位相同**（IP 從 .30 換到
.141，網卡沒換），所以這是同一台機器。

### 順帶修掉的：時鐘差 6 天

Pi 的 `RTC time` 是 `1970-01-01` —— **Pi 5 沒有電池供電的 RTC**。
它開機時 UTC 是 `2026-10-01T06:15:49Z`，而筆電是 `2026-10-07T15:22:44Z`，
**差 6 天 9 小時**。`timesyncd` 是 active 的，只是連不到伺服器（當時沒有
對外網路）。

Wi-Fi 一上線 NTP 自己校回來：Pi `15:30:36Z` 對筆電 `15:30:29Z`，**差 7 秒**。
這一步不是可選的——C2C-048 那次跨主機失敗就是兩端差了 7 分 44 秒，
而窗只開 2–3 分鐘。

## 二、Pi 的佈建：缺的比預期多

09-24 那次只把 nft 驗收那一支送上去，所以這條鏈的程式幾乎都不在：

```
n crosscheck_identity_attribution.py     n check_link_layer_binding.py
n decode_rtps_identity.py                n run_attribution_driven_block.py
n run_crosshost_identity.sh              n observer_events_to_observations.py
```

而且 **`security_observer` 根本不在 Pi 上** —— 那支 C++ 是整條鏈的起點
（記 `UNAUTHORIZED` 的就是它）。已在 Pi 上用 cmake 編好（Fast DDS 2.13+、
`rmw_fastrtps_cpp` 8.4.4），連同 `gid_probe`、`guard_filter` 放在
`~/sros2/bin/`（不是 `/tmp`，免得重開就沒了）。

全部依賴都是**標準庫**（argparse／hashlib／ipaddress／json／subprocess／
pathlib），所以 Pi 的 `python3` 就夠；建一個空的 venv 只為滿足
`run_crosshost_identity.sh` 的路徑約定。

### 兩道 fail-closed 在 Pi 上實測通過

```
dumpcap  cap_net_admin,cap_net_raw=eip        ← 非 root 擷取可用
libfastrtps.so.2.14 -> /opt/ros/jazzy/lib
libfastcdr.so.2     -> /opt/ros/jazzy/lib     ← 同目錄
```

第二道擋的正是 C2C-041 查明的那個失效：FastCDR 與 FastRTPS 不同源時，
觀測者會**跑滿整個視窗、log 乾乾淨淨、事件檔是空的**，而封包擷取證明攻擊者
確實同時在線。那是這個專案最危險的一類錯誤，所以它必須 fail-closed
而不是事後才發現。

### ⚠️ permissions 綁的是 domain 41，不是 30

```
permissions.xml:  <domains><id>41</id></domains>
```

而 campaign 正在用 **domain 30**（從執行中的 `monitor_node` 的
`/proc/<pid>/environ` 直接讀出來的，不是從設定檔推的）。

第一輪對照我跑在 domain 30，觀測者起得來（governance 允許建 participant），
但 permissions 不涵蓋那個 domain。C2C-075 記過這個陷阱：
**「規則存在但域不對」與「規則不存在」在 Fast DDS 的錯誤訊息上完全一樣**，
而那次差一點讓我去 policy 裡加一條真的放寬。

⇒ 跨主機一律用 **domain 41**，一次解掉兩件事：與 Pi 的 permissions 一致，
且**不再靠 NAT 的運氣**與 campaign 隔離。

## 三、兩輪陰性對照：儀器會動，而且不誤報

沒有對照組的話，「觀測者靜默失效」與「防禦成功」在資料上長得一樣
（C2C-040 記過這件事）。所以在跑真的那一輪之前先建立 baseline。

第二輪刻意設 `ATTACKER_IP=192.168.0.141`，讓它與真正那一輪的**唯一差別
就是「攻擊者沒跑」**。

| 量測 | domain 30 | domain 41 |
|---|---|---|
| 解析的 RTPS 封包 | 20 → 6 筆觀測 | 同形狀 |
| 乙太網框 | 45 | 同形狀 |
| 觀測者判定 AUTHORIZED／UNAUTHORIZED | **0 / 0** | **0 / 0** |
| 兩半都看到的 GUID | 0 | 0 |
| **通過三條判定的位址** | **0** | **0** |

Pi 自己（`192.168.0.145`）被正確拒絕，理由是
「觀測者沒有對此 GUID 的拒絕記錄（**不可用查無記錄推論**）」——
那正是 C2C-041 加的第三條判定在做它該做的事。

domain 41 那一輪的判定更精確，因為設了 `ATTACKER_IP`：

```
⛔ 本輪證據無效：擷取檔中沒有來自 192.168.0.141 的 RTPS 封包。
   這不可解讀成防禦成功，但原因也還沒確定。三種可能：
     1. 攻擊根本沒有執行  2. 攻擊端 participant 起不來  3. 網路路徑不通
   先向攻擊端索取 rc 與 Publishing 行數再判斷
```

這段話是 C2C-048 修正過的（當時它編了一個「網路路徑不通」的理由，
而真因是攻擊沒執行）。**它在這裡做對了**：判定為無效、但不假裝知道原因。

另一個佐證：擷取裡的 RTPS **只有 192.168.0.145**（Pi 自己）
⇒ 確認 campaign 的 domain-30 流量真的沒有到 Pi。

## 四、決定性的量測：NAT 後面的 WSL 不能當任何一端

原本我把「筆電可以當備用攻擊端」寫進計畫，理由是歸因會指向筆電的 Wi-Fi
位址而機制不變。**那是推論，而且是錯的。**

同一個封包、兩個 listener：

| listener | 結果 |
|---|---|
| **Windows**（綁 `0.0.0.0:29999`） | **`RECEIVED from 192.168.0.145`** |
| **WSL**（綁 `0.0.0.0:29999`，50 秒） | **`RESULT=TIMEOUT`**，0 個封包 |

⇒ 封包**到得了筆電**，但 **NAT 不把它轉發進 WSL**。
而且這排除了防火牆（Windows 收到了），所以成因是明確的。

為什麼這對鏈是致命的：

```
攻擊端 ──SPDP──> 防守端          出站，NAT 允許 ✓
防守端 ──unicast SPDP──> 攻擊端   入站，NAT 阻擋 ✗
防守端 ──handshake──> 攻擊端      入站，NAT 阻擋 ✗
```

SROS2 的認證握手需要**雙向**。只有出站的話，Pi 會收到 SPDP 但握手不完成，
而 `onParticipantAuthentication` 的 `UNAUTHORIZED` 是認證層的事件
（C2C-040 量過：攻擊者**只**產生 UNAUTHORIZED，沒有帶 subject 的
discovery 事件）⇒ **拿不到那筆證據**。

⚠️ 而失敗形態是「觀測者什麼都沒記到」——與防禦成功外觀相同。
這是本專案第二十三次遇到「失敗與成功在資料上長得一樣」的形態，
而這一次是**網路層**造成的。

⚠️ **這對桌機同樣成立**：桌機的 Ubuntu 24.04 如果也在預設的 NAT 模式，
它當不了攻擊端。C2C-048／049 那次成功的跨主機，筆電是 `mirrored` 模式
（那個 `192.168.0.129` 就是 mirrored 給 WSL 的位址）——**歷史上那次就是
靠 mirrored，而我先前沒有把這件事與拓樸連起來。**

⚠️ `netsh interface portproxy` 不是出路：它**只支援 TCP**，而 RTPS 是 UDP。

## 五、順帶驗證一個事前判準：`adaptive_observer` 欄位

C2C-098 加了 `manifest.result.adaptive_observer`，並明確寫「執行中的
campaign 吃不到這個欄位，要下一次重啟」。這一輪重啟了，所以判準可判定。

重啟後 59 場（`20261007T1441` 之後）：

| | |
|---|---:|
| 有這個欄位 | **58／59**（缺的是進行中的 `running`，manifest 還沒寫完） |
| `status = observed` | **48** |
| `status = not_applicable` | **10** |
| `blind = false` | **48** |
| **`blind = null`** | **10** |

三個刻意的設計決定**全部在 live 資料上成立**：

1. **三值不是布林** —— 10 場 `normal_patrol` 是 **`None`** 而不是 `False`。
   那正是 11 個測試釘住的那一點：判不出來不可以讀成「觀測者是好的」。
2. **不折疊成布林** —— 逐場記著 `blind_steps=0/3`、`0/8` 這樣的分子分母。
3. **不進訓練閘** —— 合格率 **58／59 = 98.3%**，`blind` 沒有影響任何判定。

⚠️ **`blind = true` 那一半還沒驗到**：持證內鬼只在 Enforce 下跑，
而這一輪是 permissive。48 場全部 `blind=false`，與 C2C-098 的全資料集稽核
一致（除那兩個內鬼類別外 0／1,411 盲打）。

順帶的健康指標：`attack rc` 全是 **0**（48 場），**沒有任何 `-9` 或 `-14`**
⇒ C2C-082 的 fork 收尾修正持續有效；98.3% 與 C2C-092 的 97.8%、
C2C-096 的 98.8% 一致。

## 六、不可宣稱

- **這條鏈仍然沒有跑過。** 階段 1（防守端）與階段 3（分析）都驗過了，
  **階段 2（攻擊端）一次都沒執行**，所以沒有任何新的歸因證據。
- 兩輪都是**陰性對照**。它們證明儀器會動且不誤報，**不證明它抓得到攻擊者**。
  真正的判準要等有攻擊流量的那一輪。
- `run_attribution_driven_block.py`（階段 4）**完全沒有碰過**，
  而 C2C-078 量過它拒絕本專案現有的**每一份**歸因證據（89 份 v1、
  2 份 v2 `verified=false`）。
- 第四節的結論範圍是「**預設 NAT 模式的 WSL2**」。它沒有測 mirrored，
  也沒有測桌機——桌機的模式**目前未知**。
- **進度百分比不動**：跨主機／硬體維持 85%、回應／執行維持 85%。
  這一輪佈建了防守端並排除了一條錯的路，但**沒有產出鏈的證據**。
- `LIVE_NFT_ACTIVATION_ALLOWED` 仍為 False、`executable_classes` 仍為空，
  Pi 上目前**沒有任何 nft 表**（`nft list tables` 空輸出）。
