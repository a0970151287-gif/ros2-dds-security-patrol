# 大型 campaign 的兩個排程缺陷（2026-09-20）

> 這兩個缺陷都**不在防禦裡**，也不在攻擊裡。一個讓 Permissive 的產能掉到
> Enforce 的四成，另一個讓訓練 gate 對某一類**收壞的、丟好的**。
>
> 全部在大型 campaign（`~/dataset_mega`）跑了 12.4 小時之後才浮出來——
> 兩個都只有在「同一個計畫連續排很多場」的規模下才會被看見。

## 一、計畫產生器沒有問過 `runner_requires_enforce()`

### 症狀

campaign 日誌反覆出現：

```
ValueError: runner 'insider_parameter_write' is a credentialed insider and is
only meaningful under Enforce; got security_mode='permissive'.
```

12.4 小時的成績單：**Permissive 完成 54 場，Enforce 完成 136 場。**

### 根因

`create_campaign_plan` 對每個情境呼叫 `_security_modes(count)` 對半分，
**從來沒有問過那個 runner 在 Permissive 下有沒有意義**。
`runners.runner_requires_enforce()` 這個判準 2026-09-01 就寫好了
（C2C-053），而且 `session_environment` 會據它 fail-closed 拒絕——
只是計畫產生器不知道它存在。

3,659 個 entry 裡有 **160 個**是持證內鬼被排成 Permissive。

### 為什麼代價是整批而不是一場

`execute_campaign` 對場次失敗是 **fail-closed** 的：

```python
            except Exception as exc:
                entry["status"] = "failed"
                …
                raise            # ← 整批中止
```

那個設計本身是對的（一場壞掉就停下來看，不要帶著問題繼續跑三十九場）。
但它讓「一個排程錯誤」的代價變成「一整批 40 場 ＋ 一次 stack 啟動」。
Permissive 每一批都在撞到第一個內鬼 entry 時死掉。

### 修法（三層，都有測試釘住）

| 層 | 做什麼 |
|---|---|
| `create_campaign_plan` | 內鬼情境一律 `["enforce"] * count` |
| `validate_campaign_plan` | 載入時就拒絕內鬼-permissive 的計畫 |
| `campaign repair` | 既有計畫就地修，**保住已完成的進度** |

第三層是必要的：重新產生計畫會丟掉 `status=complete` 與 `session_id`，
而那是已跑出來的 live 場次與 entry 之間**唯一**的對應。190 場不能為了
修一個排程錯誤而作廢。

`repair` 的三條界線：

* **只動不可執行的 entry。** 已完成的內鬼-permissive entry 在物理上不可能
  存在（`session_environment` 會先拒絕），遇到一個就 fail-closed、不要
  安靜地改掉它——那會把「守衛被繞過」的證據洗掉。
* **`failed` 一併回到 `pending`。** 它們的 error 就是那個 ValueError，
  不是真的攻擊失敗。
* **`requested_counts` 要跟著重算。** 摘要與 entry 是分開算的，
  `validate_campaign_plan` 會逐項比對。

### 實際套用

```
✅ 已改 160 個內鬼 entry → enforce；之後 pending：enforce 1860／permissive 1605
```

套用方式刻意**沒有 kill 任何東西**：跑到一半的那一批把計畫留在記憶體裡、
每場之後整份寫回，硬改會被蓋掉。改用一個 watcher 等到批次之間的空檔，
而 `repair` 自己會拿 `_CampaignLock`，所以就算算錯時機也不會跟 campaign
同時寫。實測第 11 次嘗試（約 4 分鐘後）拿到鎖。

## 二、訓練 gate 在自適應模式下把判定反過來了

### 症狀

```
RuntimeError: live session failed training gate:
  status=complete gate=not_eligible:attack_process
```

193 場裡 **14 場**被判不合格。

### 根因

`_attack_process_succeeded` 對 `unauthorized_participant` 有一條特例：
它的 runner 是 `ros2 run demo_nodes_cpp talker`，**故意長跑**，所以只有
「被工廠終止」才算數。

但開了 `--adaptive` 之後，被啟動的行程一律是 **N37 驅動器**，不是 catalog
宣告的那支 runner。N37 的契約正好相反：**自己在視窗結束前 `os._exit(0)`**。

於是那一類的 13 場：

| 實際情況 | 判定 | 場次 |
|---|---|---:|
| 乾淨收尾（rc=0、有 DECISION_TRACE） | **不合格** ❌ | 7 |
| 被工廠 SIGKILL（rc=−9、**決策軌跡整份遺失**） | **合格** ✅ | 5 |
| 被終止但退 0 | 合格 | 1 |

**收的是壞的，丟的是好的。** 規則是按 `scenario.runner` 這個名字寫的，
而在自適應模式下那個名字已經不代表實際執行的東西。

### 另外 7 場：rc=−9 是真的缺陷

`verify_flood` ×2、`spdp_flood` ×2、`cross_channel_relay`、`node_churn`、
`odom_spoof` 各一，全部 rc=−9。

**rc=−9 與「沒有 DECISION_TRACE」完全一一對應（12／12）。**
N37 的軌跡是在 `finally` 才印的，被 SIGKILL 就什麼都留不下來。

根因在 N37 收 burst 子行程的預算：

```python
                    rc = proc.wait(timeout=5)      # 最壞 5s
                    …  proc.kill(); proc.wait(timeout=5)   # 再 5s
```

最壞 10 秒，而 `ManagedProcess.stop()` 的寬限期只有 **3 秒**。
burst 結束得夠晚時，收子行程就把 4 秒的 `TEARDOWN_RESERVE_SEC` 吃光。

### 修法

* `_attack_process_succeeded` 新增 `adaptive` 參數：自適應模式下一律要求
  `rc == 0`，talker 那條特例不適用。
* N37 的 `CHILD_REAP_SEC = 1.0`（×2 = 2 秒，塞得進 3 秒寬限與 4 秒預留）；
  SIGKILL 之後仍收不掉就記 `rc="reap_timeout"` 並繼續收尾——再等下去換成
  **我們**被砍，連軌跡都留不下來。
* 測試直接從 `ManagedProcess.stop` 的簽章讀寬限期來比對，不是寫死 3.0。

### 淨效果

那一類從「7 好場被丟、5 壞場被收」變成「好場收、壞場丟」，而 rc=−9 本身
應該幾乎不再發生。

⚠️ **已經落地的 14 場不回溯。** 它們的 manifest 記著當時的判定，那是當時
的事實；重算會讓 manifest 與 `code_revision` 不一致。之後的場次用新規則。

## 三、順帶修掉一個名實不符的檢查

`synthetic_dataset._quality_report` 有一條
`balanced_security_sessions_per_scenario`——**名字說 per_scenario，實際數的
是 per_class**。在「一個類別只由一個情境產生」的時代兩者等價，現在不是了：
`hmac_forgery` 與 `confused_deputy` 各自同時有一個出貨 catalog 的持證內鬼
情境與一個合成的外部者情境（C2C-053 記過 N13 與內鬼同名不同物）。

修好第一個缺陷之後這道 gate 立刻掛掉，因為它對內鬼情境要求一個**不存在**
的東西（Permissive 那一半）。改成真的按情境數，並且對內鬼情境要求
`permissive == 0`——那比對半分**更嚴**。

「更嚴」是需要證明的，不是宣稱的：`test_synthetic_gate_still_bites_...`
謊報 `normal_patrol` 是持證內鬼，資料裡它有一半 permissive 場次，gate 必須
失敗。gate 若退化成什麼都不檢查，那個測試會安靜地通過。

## 這一輪的共同形態

三個缺陷都是**同一種**：一條規則寫的是某個時空條件下成立的東西，條件變了
而規則沒變，於是它開始量錯東西、而且**看起來完全正常**。

* 對半分：在「沒有持證內鬼」的時代是對的。
* talker 特例：在「沒有自適應驅動器」的時代是對的。
* per_class 計數：在「一類一情境」的時代是對的。

第二個最值得記：它不是漏掉什麼，是**把判定反過來**。若沒有去數
「rc 與 DECISION_TRACE 的對應」，只看合格率 93% 會覺得一切正常。
