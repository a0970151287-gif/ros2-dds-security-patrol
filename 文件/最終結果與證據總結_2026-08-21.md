## 二、300 場重跑：一個可否證的實驗

### 設計

正式資料集有三個 scenario 的攻擊專屬證據是空的，成因是兩個已修的 bug：

| scenario | 場次 | 失效原因 |
|---|---:|---|
| `heartbeat_replay` | 100 | 攻擊端是 BEST_EFFORT publisher 對 RELIABLE subscriber，DDS 直接不投遞 |
| `parameter_tamper` | 100 | `parameter_call` hook 掛在 rcl read-only 拒絕之下 |
| `parameter_flood` | 100 | `get_parameters` 當時沒有任何 hook |

重跑沿用原本的 `seed`、`scenario_id`、`security_mode`，**唯一的變因是那兩個修正**。
原始 `dataset_live` 完全未動——它是「bug 存在時長什麼樣」的唯一實證與對照基準。

### 預測寫在跑之前

| # | 預測 | 結果 |
|---|---|---|
| 1 | `parameter_call` > 0（Permissive） | ✅ 0 → **210,614** |
| 2 | `nonce_reuse_or_capacity` > 0（Permissive） | ✅ 0 → **312** |
| 3 | **（對照組）** `sros2_deny` 維持 0 | ✅ 0 → 0 |

第 3 項刻意設為對照：它沒有被修，所以不該動。它確實沒動，因此前兩項可以歸因於
修正，而不是環境漂移。

檢核器在**未重跑**的舊資料上先自我驗證過，當時報告前兩項「被推翻」——證明它會
咬人，不是只會蓋章。

### 逐類結果

| 類別 | 舊 test | 新 test | 有無重跑 | 有無專屬證據 |
|---|---:|---:|---|---|
| `replay` | 0.375 | **1.000** | ✅ | 修好後有 |
| `parameter_tamper` | 0.429 | **0.988** | ✅ | 修好後有 |
| `service_dos`（parameter_flood） | — | **0.975** | ✅ | 修好後有 |
| `sensor_spoof` | — | **1.000** | ❌ | 本來就有（`hmac_failure_rate`） |
| `message_dos` | — | **0.970** | ❌ | 本來就有（`oversized_message_ratio`） |
| `replay_dos` | — | 0.933 | ❌ | 本來就有（`alert_reflection_ratio`） |
| `command_injection` | — | **0.513** | ❌ | **沒有** |
| `identity_abuse` | 0.233 | **0.467** | ❌ | **沒有** |

**這張表是本研究的核心結論**：識別率由**證據排他性**決定，不是模型容量或標籤設計。
重跑的三類補上專屬證據後全部接近滿分；未重跑但本來就有專屬證據的仍然很高；
唯二仍然差的兩類，正是至今沒有專屬證據通道的。

### 為什麼不是批次效應

那 300 場是同一天連續跑的，環境同質，所以「提升來自批次指紋」必須被排除。
Permissive validation 消融：

| 特徵集 | balanced accuracy |
|---|---:|
| 只有 network | **0.3235** |
| 只有 telemetry | **0.8484** |
| fusion | 0.8602 |

若提升來自批次效應，**network 特徵應該也會變好**——流量形狀與時序是批次指紋最
可能出現的地方。它沒有。提升集中在 telemetry，正是被修好的那條通道。

## 三、Enforce：偵測得到，識別不出

Enforce 的 balanced accuracy 只有 0.4155，但 binary PR-AUC **0.9774**、
attack recall 0.9362。重跑實測 Enforce 的 `parameter_call` 與 nonce **全部維持 0**。

原因：SROS2 在 DDS handshake 就拒絕無憑證的攻擊者，訊息到不了應用層，
**應用層證據根本不存在**，只剩流量形狀可用。

> **這個不對稱是結果，不是缺陷。** 它量化了「防禦有效」與「事後可識別性」之間的
> 張力：防禦越早擋下攻擊，能用來分類攻擊種類的證據就越少。

## 四、分層防禦：直接量到，不是推論

九項本機防禦結果目前 **5／9** 有單場完整 live 證據
（`~/.local/share/sros2-firewall/local_outcomes/`）。

| 項目 | 關鍵數字 |
|---|---|
| `normal_traffic_preserved` | 未授權 publisher **0**；final `/cmd_vel` 唯一合法來源 |
| `unauthorized_participant_denied` | 未授權送達數 **0**；state digest 未變 |
| `hmac_forgery_dropped` | 偽造 **11 拒 / 0 收**；下一則真訊息仍被接受 |
| `oversized_input_dropped` | 超長輸入 **7 拒 / 0 收**；SensorHub 存活 |
| `velocity_guard_zeroed` | 已驗章鎖定 → 零速，延遲 **0.019–0.210 秒**（八次量測） |

`hmac_forgery_dropped` 是**分層防禦第一次被直接量到**：攻擊者持**合法 SROS2
憑證**（模擬節點被攻陷）但沒有 HMAC 金鑰，SROS2 放行了他，HMAC 仍然全數擋下。

偽造刻意用攻擊者自己生的金鑰去簽**格式完全正確**的信封。否則會被判
`malformed_envelope`——那證明的是解析器擋住畸形輸入，不是簽章檢查擋住偽造。

`unauthorized_participant_denied` 記錄 `sros_deny_evaluable: false`：廠商拒絕記錄
在本技術棧取不到，判定綁在「送達數為 0」這個可量測性質上。**沒有把「沒看到」
算成通過。**

## 五、兩個負面結果，都可寫進報告

### 5.1 anti-replay 不是靠 ReplayCache 生效

重放**確實抵達**驗證器，但兩場實測共 24 次重放全部落在 `timestamp_violation`，
`nonce_reuse_or_capacity` **0 次**。四種排法都輸掉同一場競速。

時間戳窗（alerts 10 秒、心跳 3 秒）加上最小權限 ACL 讓重放**來不及發生**：要夠快
必須側錄與重放在同一行程，但沒有任何 enclave 同時擁有某個安全頻道的發布與訂閱權。
**ACL 強迫攻擊者跨行程，而跨行程的成本超過新鮮度窗。**

附帶：alerts 是 TRANSIENT_LOCAL，後加入的訂閱者先拿到 durability 快取裡的**陳舊**
alert——攻擊者就算側錄到真品，拿到的也是過期品。

### 5.2 DDS Security 稽核日誌在本技術棧無法啟用

屬性設定經二進位驗證正確，未啟用 SROS2 時可成功初始化；一旦啟用 SROS2，
`rmw_fastrtps_shared_cpp` 自行組出 participant 的安全屬性清單，其中不含 logging
plugin。因此 `sros_auth_fail_rate` 與 `sros_permission_deny_rate` 標記為
**來源不可得**，不是「量測到零」。詳見 `DDS_Security_audit_log_不可用_2026-08-18.md`。

這也說明為何 `identity_abuse` 無法靠「補設定」改善——需要換觀測層（封包層 RTPS）。
