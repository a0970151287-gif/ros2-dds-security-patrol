## 為什麼要演練

`工具腳本/retrain_from_registration.py`（C2C-086）**從來沒有跑過一次真的重訓**
——它的 15 個測試驗的是契約與兩個順序，不是一次評估。

等 campaign 產出全新 holdout 的那一天，那會是這支程式的**第一次執行**。
那是最糟的時機去發現缺陷：新 holdout 是一次性的，而「程式壞掉」與
「模型不好」在失敗訊息上不一定分得出來。

所以用**已經花掉的**那批 test 先走一遍。

## ⚠️ 演練本身抓到的東西

**子命令名字我記錯了。** 第一次寫的是 `seal_holdout.py make`，實際是 `seal`
（另外是 `status`／`open`，不是 `unseal`）。那在真跑那天會是第一個絆腳處，

**這正是演練的價值**：它抓到的不是演算法問題，是**操作介面的記憶錯誤**，
而那種錯誤只有真的執行一次才會現形。

## 那個 0.7255 為什麼不是成績

```
test 場次         : 51（17 類）
balanced accuracy : 0.7255
macro F1          : 0.6999
算術上限          : 0.9412（恆零類別 1）
聚合寬度          : 624
```

三個理由，任一個就足以讓它不可引用：

1. **那批 test 已被設計流程看過**（09-03 開過一次，而從 09-15 到 09-27
   每一個識別設定都是從 CV 選出來的）。
2. **每類只有 3 場**（51 ÷ 17）。C2C-064 記過在那個解析度下
   「3 場全錯」就顯示成 0.000，而「永遠是零」與「三次擲硬幣全反面」分不出來。
3. 門檻是 0.80，而 0.7255 低於它——但**即使它高於 0.80 也不可引用**，
   理由是前兩點。

一致性確認：聚合寬度 **624** = 26 個活特徵 × 4（`d1_m3_x3` 展開）× 6 個統計量，
而選型 artifact 記的 `aggregate_width = 156` 是 `temporal=none` 的基底
（26 × 6）。**兩者相符** ⇒ 重訓用的確實是被選中的那個設定，不是工具預設。
