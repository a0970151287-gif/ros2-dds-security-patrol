# 跨主機攻擊機建置交接

> 給在 **5080 桌機**上執行的代理。你負責**攻擊端**；防守端在 Jesse 的筆電上，
> 由另一個代理負責。這份文件讓你不必讀完整段對話就知道要建什麼。

---

## 〇、最重要的一條界線

**攻擊機絕對不可以有防守方的 SROS2 keystore。**

不要複製 `sros2_keystore/`、不要複製任何 `key.pem`、不要複製 enclave。
攻擊機上有防守方的私鑰，整個威脅模型就沒有意義了——那不是「外部攻擊者」，
是「已經被完全攻陷的內部主機」。

N28 攻擊**自己生一個 CA、自己簽憑證**，不需要防守方的任何檔案。
（腳本原本會因為找不到防守方 keystore 而中止，2026-08-26 已改成跳過對照顯示、
攻擊照常執行。）

---

## 一、你要達成什麼

一句話：**讓這台機器上跑一個 DDS participant，它的憑證由錯誤的 CA 簽發，
並且它有一個與防守機不同的區網 IP。**

為什麼要不同的 IP：防守方要證明「這個 IP 上只有一個 participant，而且它不是
合法身分，所以封鎖它不會波及別人」。同機做不到——所有 participant 共用
`127.0.0.1`，這是物理限制不是設定問題。

---

## 二、需要安裝的東西

只有兩樣：

- **ROS 2 Jazzy**（要有 `demo_nodes_cpp`）
- **openssl**

不需要 Gazebo、不需要專案原始碼、不需要 Python 模型環境。

### 網路要求（比軟體重要）

這台機器必須有一個**與防守機同網段的 IP**，而且兩邊能互相 ping。

| 作法 | 侵入性 | 說明 |
|---|---|---|
| **Linux VM ＋ bridged 網路** | **最低，建議** | 不動桌機的 Windows，VM 直接拿一個區網 IP |
| WSL2 ＋ `networkingMode=mirrored` | 低 | 比 VM 輕，但 mirrored 模式有自己的眉角 |
| 雙開 Linux | 高 | 最乾淨但最麻煩 |

⚠️ **NAT 模式的 WSL2 不行。** 預設的 WSL2 躲在 NAT 後面（位址像
`172.30.x.x`），防守機連不到它，DDS 的多播也穿不過 NAT。

---

## 三、動手之前的五分鐘檢查

這一步不過，後面全部白做。

```bash
# 兩台各自查自己的 IPv4
ip addr        # Linux / WSL
ipconfig       # Windows
```

前三段要一樣（例如都是 `192.168.1.x`），然後互 ping：

```bash
ping <對方的 IP>
```

**ping 不通就不要往下走**，先解決網段問題——常見原因是一邊 WiFi 一邊有線被
路由隔開，或路由器開了 AP isolation。

---

## 四、取得 N28 腳本

只需要這一個檔案：

```
紅隊測試/PoC腳本/N28_wrong_ca_participant.sh
```

不要 clone 整個專案到攻擊機——那裡面有防守方的設定與文件。

## 五、執行

```bash
source /opt/ros/jazzy/setup.bash
export ROS_DOMAIN_ID=30            # 必須與防守方相同
bash N28_wrong_ca_participant.sh 40   # 40 秒
```

腳本會：

1. 生一個完全獨立的 CA（不碰防守方的任何東西）
2. 用它簽一張 `CN=/wrong_ca_intruder` 的身分憑證
3. 簽 governance 與 permissions
4. 以那組憑證加入 domain 30，跑一個 talker

產物留在 `~/.local/share/sros2-firewall/wrongca/` 供稽核。

### 怎麼知道有沒有真的跑

`rc=124` 是 **正常**（timeout 到期）。attack log 裡應該看得到
`Publishing: 'Hello World: N'`。

**如果 rc 是其他非零值，participant 根本沒起來，不可以視為攻擊已執行。**
這個專案已經被「攻擊回報成功但其實沒執行」咬過三次，所以一定要看 log 確認。

---

## 六、防守方那邊會發生什麼（你不需要做，但要知道）

防守機會跑一個 `security_observer`——一個用 Fast DDS API 直接建立的
participant，以合法身分加入同一個 domain。它會：

- 嘗試驗證你的憑證 → 失敗 → 記下 `UNAUTHORIZED` ＋ 你的 GUID
- 同時擷取封包，把你的 GUID 對應到你的**實際來源 IP**

2026-08-26 已在同機驗證過這個機制可行（攻擊組 2 筆 UNAUTHORIZED、
對照組 0 筆）。跨主機要補的是「IP 是分開的」這一半。

### 需要協調的時序

請與防守端協調：**先確認觀測者已啟動，再跑 N28。**

（先前記為「相反順序會漏記、成因未查明」的現象，2026-08-26 已查明與順序無關，
是防守端的 FastCDR 函式庫解析不一致，防守端已加 preflight 擋住。）

### ⚠️ 這個坑攻擊端也可能踩到

防守端曾經因為 `libfastrtps` 與 `libfastcdr` 來自不同目錄（一個在
`/opt/ros/jazzy/lib`、一個在 `/usr/local/lib`）而**discovery 靜默失效**：
participant 建得起來、log 乾乾淨淨、程式跑完整個視窗，但兩邊完全看不見對方。

所以在攻擊機上**跑之前先確認一次**：

```bash
source /opt/ros/jazzy/setup.bash
ldd $(which talker 2>/dev/null || echo /opt/ros/jazzy/lib/libfastrtps.so.2.14) | grep fastcdr
```

`libfastcdr` 必須解析到 `/opt/ros/jazzy/lib/`。若指向 `/usr/local/lib/`，
表示這台裝過另一套 Fast DDS，請先確認有 source ROS 的 setup.bash。

**這一點特別重要**，因為它的失敗形態是「攻擊看起來成功執行了、但防守端什麼
都沒收到」——會被誤讀成「防禦沒反應」或「攻擊被擋住」，兩者都是錯的結論。

---

## 七、要回報什麼

跑完之後把這些交回防守端：

| 項目 | 用途 |
|---|---|
| 攻擊機的**實際 IP** | 對照防守方擷取到的來源 IP |
| N28 的 rc 與 attack log | 證明攻擊真的執行了 |
| 攻擊開始／結束的 UTC 時間 | 對齊防守方的觀測視窗 |

**不要**回傳 `wrongca/private/ca.key.pem`——雖然那是攻擊者自己生的，
沒有價值，但保持「私鑰不離開產生它的機器」這個習慣。

---

## 八、你不該做的事

- 不要複製或索取防守方的 keystore、私鑰、enclave
- 不要在攻擊機上執行 `sudo` 相關的防火牆操作（nftables 是防守端的事）
- 不要修改防守端的任何檔案
- 不要把攻擊流量發到 domain 30 以外的地方
- **不要在未取得 Jesse 對該次操作的明確授權前執行攻擊**——
  這個專案的規則是每一次 live 操作都要單獨授權，不因前一次已授權而延續
