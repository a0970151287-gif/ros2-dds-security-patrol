# 跨主機身份歸因批次結果：79／80（2026-08-30）

> 2026-08-29 19:48Z – 2026-08-30 03:52Z，8 小時無人值守，80 輪。
> 這把 8/29 的**一場**成功變成**可重複、且有陰性對照**的一批證據。
>
> ⚠️ 仍然不授權自動封鎖：每一輪的 `authorizes_action` 都是 `false`。

## 一、結果

| 指標 | 值 |
|---|---:|
| 總輪數 | 80 |
| **attestation 成立** | **79** |
| 攻擊者 IP 判為可封鎖 | 79 |
| **誤把其他 IP 判為可封鎖** | **0** |
| 攻擊者每輪的 GUID 數 | 全部為 1 |
| UNAUTHORIZED 事件總數 | 237 |
| **不同的攻擊者 GUID** | **79** |

唯一失敗的是**第 1 輪**：防守端 19:48Z 啟動、第一個窗在 19:54:00Z，而攻擊端的
迴圈當時還沒被貼上去。那一輪被如實記成 `no_attacker_rtps_evidence_void`，
不是被當成防禦成功。第一輪成功是 `20:00:01Z`，之後 79 輪連續全中。

## 二、79 個**不同**的身份，不是同一個重複 79 次

N28 每次執行都產生全新的 participant，所以 79 輪對應 **79 個相異 GUID**。
每一輪都是「一個從未出現過的 wrong-CA 身份被拒絕，並被綁定到來源 IP」。

這比同一個 GUID 重複 79 次強得多——後者只證明某一次綁定穩定，前者證明
**機制對任意新身份都成立**。

## 三、陰性對照：80 輪零誤判

防守方自己的位址 `192.168.0.129` 在每一輪都：

- 只掛一個 GUID ✅
- 滿足 `unique_guid_to_ip_binding` ✅
- 滿足 `ip_not_shared_by_multiple_identities` ✅
- **但沒有觀測者的拒絕記錄** → 判定不可封鎖

**80 輪沒有任何一輪把它判成可封鎖。** 三條判定裡的第 3 條（必須有明確的
UNAUTHORIZED 記錄，不可用查無記錄推論，見 C2C-041）是唯一把兩個位址分開的
條件——沒有它，防守方自己每輪都會看起來可封鎖。

## 四、Soak：8 小時零退化

| | |
|---|---|
| 第一輪成功 | `20260829T200001Z` |
| 最後一輪 | `20260830T034759Z` |
| 跨距 | 約 7 小時 48 分 |
| 每輪 UNAUTHORIZED 事件數 | **min 3 / max 3**，分布 `{3: 79}` |

**零變異**。觀測者、封包擷取、交叉比對在第一輪與第 80 輪的行為完全一致。
沒有記憶體累積造成的退化、沒有 mirrored 中途掉線、沒有觀測者靜默失效。

## 五、絕對時間排程有效

第一版讓攻擊端週期比防守端略長，靠窗的餘裕吸收漂移——20 輪可行，80 輪會累積
約 600 秒而讓攻擊掉出窗外。改成兩邊都對齊 UTC 的 360 秒絕對邊界（防守端在邊界
開窗、攻擊端在邊界 +60 秒動手）之後：

- **80 輪沒有任何一輪漂移到窗外**
- **沒有任何一個窗落入兩次攻擊**（每輪 GUID 數恆為 1；若落入兩次，同一 IP 會掛
  兩個 GUID 而使綁定條件失敗）

## 六、退化偵測沒有被觸發

批次帶兩道自動停止：區網位址消失、或連續 6 輪沒有 attestation。**兩道都沒有
觸發**，批次自然跑完 80 輪。

這一點值得記：如果 mirrored 半夜掉線，繼續跑會產出幾十輪安靜的空資料，而那
看起來會很像「防禦一直在擋」。這個專案已經被「沒有證據」與「防禦有效」外觀
相同咬過八次，所以無人值守的批次必須會大聲失敗。

## 七、還不能宣稱什麼

1. **一種攻擊**（N28 wrong-CA）。79 輪是同一種攻擊的重複，不是攻擊面的覆蓋。
2. **同網段 Wi-Fi**，多播實測 0/25 不通，全程靠 unicast initial peer。
   換網路環境（有線、跨網段、企業 AP）要重驗。
3. **沒有整合進特徵**，family-LOO 未重做。Enforce 識別 0.4155 與處女 holdout
   0.0273 **完全沒有因此改善**。
4. `authorizes_action=false`、`executable_classes` 仍為空，沒有任何自動封鎖被啟用。
5. 既有 1,101 場**不會**因此變成有 attestation。
6. **沒有正向對照**：這批沒有「合法遠端 participant 應判為 AUTHORIZED 且不可
   封鎖」的場次。要有的話得在第二台機器放合法 enclave，那與現行威脅模型的
   界線（攻擊機不得持有防守方憑證）衝突，是一個需要 Jesse 決定的設計問題。
