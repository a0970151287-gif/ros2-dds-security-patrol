## 一、本輪已完成

### 1. 修正正常 LiDAR 被誤判為畸形資料

TurtleBot3 Gazebo 模型使用：

```text
samples=360
angle_min=0
angle_max=6.28
```

原驗證要求掃描端點精確到 `2π`，因此把正常 `0..6.28` 掃描誤判成
「未覆蓋前方 ±60°」，導致 `patrol_node` 丟棄所有正常幀。

修正後：

- 只把端點最多半個 beam 視為該 beam 的角度 cell。
- 容忍上限固定為 1°，不能用低解析度 metadata 隱藏大範圍盲區。
- 新增 Gazebo `0..6.28` 回歸測試。
- 新增 3° 真實前方盲區仍須拒絕的負向測試。

### 2. 實際 Gazebo readiness 驗證

為避免 WSL 掛載工作區重複掃描全部 ROS package，資料收集模式改為：

- Gazebo server 預設 headless。
- GUI 改為明確 `gui:=true` 才啟用。
- Permissive supervisor 與 Enforce 一樣，必須等 `/scan`、`/odom`、
  `/imu`、`/clock`、`/tf` 五條資料流都到達才宣告 ready。

本次以 `ROS_LOCALHOST_ONLY=1`、loopback scope 啟動，不執行任何攻擊：

```text
Gazebo readiness passed

Odom ready
front coverage warning count=0
scan stale count=0
```

驗證後已停止整組 ROS／Gazebo 程序，沒有殘留執行程序。

### 3. 補強資料 ground truth gate

正式 runner 現在新增兩個 fail-closed 條件：

1. campaign 內的 `catalog_sha256` 必須等於目前 `scenarios.json`，避免
   建立計畫後改了攻擊定義，卻沿用舊標籤。
2. 攻擊 runner 若提早崩潰或沒有可信的 process evidence，即使 PCAP
   非空、Zeek 成功，也不得標成 `training_eligible=true`。

training gate 現在同時要求：

- PCAP 非空。
- capture process 正常結束。
- Zeek return code、`conn.log` 均正常。
- allowlisted attack runner process evidence 合格。

### 4. 新增正式資料被動 preflight

新增：

```text
python3 -m firewall_lab.formal_preflight
```

它只做被動檢查，不啟動 Gazebo、不發 ROS 訊息、不擷取封包、不執行攻擊。
它會拒絕：

- `any` 或不存在的 capture interface。
- topology、localhost 設定與授權確認不一致。
- scenario catalog drift。
- campaign 有殘留 running／failed 狀態或 lock。
- 缺少 ROS2、Gazebo、dumpcap、Zeek、SROS2 artifacts 或 HMAC secret。
- dumpcap 沒有非 root 擷取權限。
- 磁碟不足。
- Git 工作樹不是單一凍結版本。

## 三、為何尚未直接跑第一批

目前有兩個 blocker：

1. `source_snapshot_clean`：執行程式尚未凍結成單一 Git revision。
2. `live_multimodal_contract`：正式 live 管線目前只有 14 維 network
   features；計畫中的 18 維 telemetry 尚未完成同一
   `session_id＋window` 的收集與對齊。

若現在直接開始，manifest 的 Git revision 只會指向舊 HEAD，無法完整代表
實際正在執行的未提交變更。這會讓日後無法重現：

- 哪一版 patrol scan 驗證產生資料。
- 哪一版 attack runner 與 training gate 產生標籤。
- 哪一版 SROS2／Zeek／資料特徵程式參與實驗。

因此正式 campaign 保持 **0/1,100**，沒有為了增加筆數而犧牲證據鏈。
