# 公開漏洞對照與攻擊面缺口（2026-08-31）

> 依 Jesse 指示，從公開的 ROS 2／DDS 安全研究找攻擊靈感，對照本專案已涵蓋的
> 8 類攻擊，找出缺口。
>
> ⚠️ **沒有使用 NCHC 的 malware 樣本。** 那些是 x86／Windows 惡意程式，與
> ROS 2／DDS 的攻擊面幾乎不重疊；而且我不從來源不明的地方取材當研究依據。
> 本文只用具名的公開研究。

## 二、公開弱點 vs 本專案涵蓋

### SROS2 設計弱點（CCS 2022）

| | 弱點 | 本專案 |
|---|---|---|
| V1 | **權限撤銷不足**——被感染節點在憑證撤銷後仍保有存取 | ⚠️ **有機制、從未被對抗測試** |
| V2 | namespace 隔離不足，跨 domain 資訊外洩 | ❌ 無 |
| V3 | **discovery 協定向被動攻擊者洩漏網路拓撲** | ❌ **完全無涵蓋** |
| V4 | 訊息注入與未授權訂閱 | ✅ `cmd_vel_injection`、`sensor_status_spoof` |

### DDS 中介層弱點

| 弱點 | 本專案 |
|---|---|
| 放大／反射（CWE-406，畸形 RTPS 讓受害者對第三方送流量） | ⚠️ `N13_health_reflection` 已寫，**未進資料集** |
| **locator 欄位缺乏驗證，可寫入任意 IP** | ✅ **不受影響**（見第三節） |
| 設定檔解析溢位（XML／JSON） | ❌ 無（需本機檔案存取，威脅模型外） |

## 三、我們的歸因為什麼不被 locator 偽造影響——但仍有一個殘留威脅

`decode_rtps_identity.py` 取的欄位是：

```python
FIELDS = ("frame.time_epoch", "ip.src", "rtps.guidPrefix")
```

**讀的是 IP 標頭的來源位址，不是 DDS 酬載裡宣告的 locator。** 所以「在 DDS 欄位
寫入任意 IP」騙不了它。

### 但 UDP 來源位址偽造可以

同一個 L2 網段上的攻擊者可以偽造 UDP 來源位址：

1. 攻擊者以**受害者的 IP** 為來源，送出帶自己 GUID 的 RTPS
2. 握手必然失敗（回應送到受害者那裡去了）→ 觀測者記下 `UNAUTHORIZED`
3. 封包層把那個 GUID 綁到**受害者的 IP**
4. 三條判定全部成立 → **系統宣告受害者的 IP 可封鎖**

這會讓防禦去封鎖一個無辜的主機——**自動封鎖最糟的失效方向**，而且昨天那
79／80 的陰性對照**測不到它**（對照組是防守方自己，不是被偽造的第三方）。

### 現成的鑑別方式

8/30 的跨主機資料裡有一個現象可以用：真正的攻擊者產生了 **156 個分片封包、
MTU 大小的訊框**，那是憑證交換。**偽造來源的單向攻擊者做不到**——它收不到
回應，握手停在第一步，不會有憑證流量。

所以判定可以再加一條：**該 IP 必須有雙向流量與憑證交換的證據**。目前
`crosscheck_identity_attribution.py` **沒有檢查這件事**。

## 四、三個最有價值的缺口

依「對本專案已宣稱的東西威脅多大」排序：

### 缺口一：來源位址偽造（威脅昨天的 79／80）

上一節。這是唯一一個會讓我們**已經寫下的結論**失效的弱點，優先度最高。
可實作的加固：判定加入「雙向流量／憑證交換」條件。

### 缺口二：被動偵察（V3），資料集完全沒有

八個攻擊**全部會送流量**。一個純被動的攻擊者——只監聽 SPDP／SEDP、繪製拓撲、
不送任何東西——會產生 **0 個異常封包**。

而現有 14 個網路特徵全部是速率／比例／連線數:

```
conn_count, conn_rate, uniq_dst_ports, uniq_dst_hosts, spdp_ratio, meta_ratio,
userdata_ratio, mcast_ratio, dst_port_entropy, interarrival_cv, burstiness,
dominant_port_ratio, dominant_host_ratio, tuple_repeat_ratio
```

**沒有一個看得見一個不說話的攻擊者。** 這正是「小量間接型攻擊」的極端情況，
而它在資料集裡的覆蓋是零。

被動攻擊者唯一會留下的痕跡是 **participant 的存在本身**——也就是身份層，
正是今天補起來的那條通道。**這個缺口會讓那條通道的價值第一次被量到。**

### 缺口三：權限撤銷繞過（V1），機制存在但沒被攻擊過

本專案的 `DdsGuardBackend` 有可撤銷封鎖，7／7 live pass，**但那是應用層黑名單，
不是 SROS2 憑證撤銷**。CCS 論文指出的正是「憑證撤銷後仍保有存取」。

沒有測過的問題：**已經完成握手的 participant，在被加入黑名單之後，是否仍能
繼續發布？** 守衛是在訂閱端過濾，所以理論上會擋；但那與「撤銷」不是同一件事，
而且從未以攻擊者的角度驗證過。

## 五、不建議追的

| 弱點 | 為什麼不追 |
|---|---|
| 設定檔解析溢位 | 需要本機檔案寫入權限，那時攻擊者已經贏了 |
| namespace 隔離（V2） | 本專案是單一 domain，沒有跨 domain 情境 |
| XML 解析器 CVE | 是上游函式庫問題，不是這個防火牆能防的層次 |

## 六、與 Jesse 提出的關鍵詞對照

| 關鍵詞 | 對應 |
|---|---|
| 小量間接型攻擊 | **缺口二**（被動偵察是其極端形式） |
| SmartDDoS | 放大／反射（`N13` 已寫未用） |
| 流量大小 | **現有特徵完全沒有位元組量**，見下 |
| 流量控管：限制單一 IP | 回應階梯缺少「限流」這一階 |
| zero trust | 已是本專案的核心，但論文沒有這樣命名 |
| 程式特徵碼 | 已有規則式基線可對照 |
