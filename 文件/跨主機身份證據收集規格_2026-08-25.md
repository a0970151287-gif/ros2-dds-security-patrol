## 〇、更正：這個問題 2026-08-18 已經查過，答案是「不行」

本文初版把「跑 N28 看防守端會不會產生 authentication 記錄」列為階段 0。
**那個實驗已經做過了，而且結論比我寫的更根本**——見
`文件/DDS_Security_audit_log_不可用_2026-08-18.md`。

根因不是 N28 觸發不了握手，是**logging plugin 根本不會被安裝**：

```
librmw_fastrtps_shared_cpp.so 裡的 security property 只有
  dds.sec.auth.*    dds.sec.access.*    dds.sec.crypto.*
dds.sec.log.plugin 不在其中。
```

RMW 層啟用安全時會自行從 keystore 組出 participant 的屬性清單，XML profile
的 `propertiesPolicy` 不被保留，也沒有附加額外 property 的途徑。對照組很乾淨：

| 條件 | 稽核檔 |
|---|---|
| 有 profile、**未啟用** SROS2 | ✅ 建立（plugin 會初始化） |
| 有 profile ＋ SROS2 Enforce | ❌ 消失 |
| 同上 ＋ `RMW_FASTRTPS_USE_QOS_FROM_XML=1` | ❌ 消失 |

**所以再跑 N28 是白跑。** 經由 ROS 建立的 participant 永遠拿不到稽核日誌。

### 但那份文件否決的第四個選項值得重新檢視

它列了四條替代途徑，第四條寫「不經 ROS，直接用 Fast DDS API 建 participant →
會失去整個 ROS 生態，不合理」。

**那個否決針對的是「取代」整個系統，是對的。** 但還有一個變體沒有被考慮：
**不取代任何東西，只在旁邊多加一個觀測者。**

ROS 堆疊原封不動照跑；旁邊多跑一個用 Fast DDS API 直接建立的 participant。
因為它不經過 rmw，**它自己的屬性不會被覆蓋**，可以同時設安全外掛與 logging
外掛。它以合法身分加入同一個 domain，而 DDS 的握手是雙向的——當 N28 那種
「憑證由錯誤 CA 簽發」的 participant 宣告自己時，觀測者會嘗試驗證、失敗，
並產生 authentication 記錄。

這條路：

- 不需要改 rmw_fastrtps（那確實超出專題範圍）
- 不需要放棄 ROS 生態
- 不需要 root
- 只讀：不發布、不訂閱任何使用者 topic

**已實作並編譯通過**：`firewall_lab/security_observer/`
（Fast DDS 2.14.5，直接連 `/opt/ros/jazzy` 的函式庫，版本與受測系統一致）。
缺憑證時 fail-closed（非零退出），已驗證。

**它還沒有被實際執行過，所以還不能宣稱任何事。** 真正要回答的問題變成：

> 一個自行設定 logging plugin 的 Fast DDS participant，
> 是否會記錄它與錯誤 CA participant 之間的握手失敗？

這仍然是最高風險項，仍然同機就能回答，但實驗的**受測對象換了**——
不是 N28 能不能觸發，而是觀測者能不能記到。

## 一、為什麼一定要跨主機

同機 loopback 下，`dataset_live` 1,101 場的來源位址只有兩個：
`127.0.0.1` 與 `10.255.255.254`（WSL 鏡像位址）。

契約的第一與第二條驗收條件是：

```
unique_guid_to_ip_binding          每個 GUID 對應唯一 IP
ip_not_shared_by_multiple_identities   一個 IP 不得被多個身份共用
```

同機上**每一個 participant 都共用同一個 IP**，第二條在物理上不可能成立。
這不是軟體問題，寫再多程式、收再多場次都無法解決。

## 二、契約要什麼，各從哪裡來

來源：`firewall_lab/identity_attribution_contract.v1.json`（P2，Codex）。

### 2.1 三種必要 artifact

| artifact | 內容 | 來源 | 現況 |
|---|---|---|---|
| `rtps_identity.jsonl` | RTPS 觀測記錄 | 封包解碼器（**待寫**） | 0／1,101 |
| `identity_attestation.json` | 可信收集器簽章 | 收集器（**待寫**） | 0／1,101 |
| `dds_security_audit.jsonl` | DDS 安全層握手結果 | Fast DDS security log | 0／1,101，**且從未成功產出** |

### 2.2 三種證據等級——這是整個設計的重點

`identity_attribution.py` 的 `evidence_kind` 分三種，欄位互斥：

| kind | 帶什麼 | 誰能產生 | 可否偽造 |
|---|---|---|---|
| `spdp_locator` | `guid_prefix` ＋ `source_ip` | 封包擷取 | **可以** |
| `sedp_endpoint` | ＋ `entity_id`、`topic` | 封包擷取 | **可以** |
| `authenticated_identity` | ＋ `identity_subject_sha256` | **只有 DDS 安全層** | 否 |

契約的 claim boundary 寫得很清楚：

> SPDP or SEDP packet fields alone are spoofable observations,
> not authenticated identity

**所以只靠 tcpdump／Zeek 是拿不到驗收的。** 封包給你 GUID ↔ IP，
但「這個 GUID 屬於哪張憑證」只有握手結果知道。這正是 §0 那個實驗
之所以是最高風險項的原因。

### 2.2.1 乾跑發現：驗收必須**逐 IP**，全域旗標永遠不可能成立

`工具腳本/dryrun_identity_pipeline.py` 用合成觀測跑過 P2 自己的特徵計算，
結果如下（合成資料，非證據）：

| 情境 | 防守方 IP | 攻擊者 IP |
|---|---|---|
| 同機、無安全日誌 | `127.0.0.1` 有 4 個 GUID → 不可封鎖 | — |
| 同機、有安全日誌 | `127.0.0.1` 有 4 個 GUID → **仍不可封鎖** | — |
| 跨主機、有安全日誌 | `10.42.0.11` 有 3 個 GUID → 不可封鎖 | `10.42.0.12` 有 1 個 GUID ＋ 認證 → **可封鎖** |

關鍵在第三列：**即使跨主機，防守方那台仍然有多個 participant 共用一個 IP**
（monitor、IDS、Gazebo），所以 `rtps_ip_multi_guid_ratio` 三個情境都是 **1.0**。

也就是說，契約把 `ip_not_shared_by_multiple_identities` 寫成一個全域布林值，
在任何真實部署裡都**永遠不可能為 true**——防守方自己那台就會讓它變 false。

**正確的語意是逐 IP：** 對每一個候選封鎖目標，檢查

1. 該 IP 只對應一個 GUID，且
2. 該 GUID 有 `authenticated_identity` 記錄。

兩者都成立才可封鎖。同機的問題不是「比例太高」，而是**每一個 IP 都不合格**，
所以沒有任何位址可以封鎖——這與有沒有安全日誌無關（見上表第二列）。

這一點已回報給 Codex（C2C-039），因為它是契約語意問題，不是我的工具問題。

### 2.3 六條網路動作驗收條件

```
unique_guid_to_ip_binding              每個 GUID 唯一對應一個 IP
ip_not_shared_by_multiple_identities   一個 IP 不得被多個身份共用
authenticated_identity_subject_binding 必須有經認證的 subject 綁定
trusted_collector_attestation          收集器本身要有可信簽章
two_consecutive_signed_windows         連續兩個已簽章視窗
authorized_scope_and_allowlist_checks  範圍與白名單檢查
```

第 2 條要求跨主機；第 3 條要求 §0 的實驗成功；其餘四條是收集器的工程。

## 四、風險排序的執行順序

### 階段 0：驗證觀測者能記到握手失敗（**同機，最高優先**）

**不需要第二台機器。** 目的：回答 §0 末尾那個問題。

1. 為觀測者建一個 SROS2 enclave（或先借用既有 enclave 的憑證做第一次測試）。
2. 啟動 Enforce 堆疊。
3. 啟動 `security_observer`，指向該 enclave 與稽核檔路徑。
4. 跑 N28（wrong-CA participant）。
5. 檢查稽核檔是否出現 authentication 記錄。

**判定**：

- 有記錄 → 第三種證據可得，繼續階段 1，而且這本身就是一個可寫進報告的
  **正面**結果（繞過 RMW 限制取得 DDS 層稽核）。
- 無記錄 → 需要再查是「logging plugin 在安全模式下仍不初始化」還是
  「握手失敗不屬於 WARNING_LEVEL」。後者可調 `logging_level`；前者則
  `authenticated_identity` 這一種證據在本技術棧確定不可得，契約要改。

需要：Jesse 對一次 live 操作的授權。約 15 分鐘。

### 階段 1：寫收集器與解碼器（離線）

不需要硬體。可先用**合成觀測**驗證管線（見 §5）。

- RTPS 解碼器：pcap → `spdp_locator`／`sedp_endpoint` 觀測
- 安全層橋接：security log → `authenticated_identity` 觀測
- 收集器簽章：`identity_attestation.json`
- lineage 綁定：`session_id`、`capture_sha256`、`decoder_sha256`、
  `policy_sha256`、`collector_id`、`sequence`、`ts_unix_ns`

### 階段 2：跨主機小樣本（12 場成對）

先驗流程，不求統計量。**需要授權＋第二台機器。**

驗收：`audit_identity_attribution.py` 對這 12 場的
`rtps_identity.jsonl` 計數 > 0，且六條條件逐項有明確通過／失敗理由。

### 階段 3：正式收集（一次收足）

**重點：一次收對，不要分兩次。** 每次加資料都會重畫切分、
讓報告所有數字重來。

場次數依 conformal 的有限樣本下限反推
（`required = ceil(1/alpha) - 1`）：

| normality alpha | 校準場次下限 | 需要的總場次（估） |
|---|---:|---:|
| 0.05（2026-08-25 採用） | 19 | 約 1,400 |
| 0.02（原值，較嚴） | 49 | 約 2,350 |

現有 1,100 場的校準場次是 23（normality）／16（known_attack）。

### 階段 4：重新基準化（只做這一次）

新特徵（含 9 個 identity 特徵）、重跑 family-LOO、重新開一次封存 test、
重畫全部圖表、更新全部文件與帳本。

### 階段 5：nftables 與回應鏈驗收

需要 root，且要在願意被套規則的機器上。

## 五、同機可以先驗什麼、不能驗什麼

| 項目 | 同機可驗？ |
|---|---|
| 安全稽核日誌是否可得（階段 0） | **可以，且必須先做** |
| 觀測記錄的 schema 是否合法 | 可以（合成資料驗管線） |
| 收集器簽章與 lineage 綁定 | 可以 |
| `unique_guid_to_ip_binding` | 可以（同機也有多個 GUID） |
| `ip_not_shared_by_multiple_identities` | **不可以**——同機必然共用 IP |
| 真實 nftables 阻擋 | 不可以 |

用合成資料驗管線是**流程驗證，不是證據**。依專案規則 4，
任何用合成資料產生的結果都不得寫成 live pass，artifact 必須自帶
`synthetic = true` 標記。

### 觀測者的建置與執行

```bash
cmake -S firewall_lab/security_observer -B <build> -DCMAKE_PREFIX_PATH=/opt/ros/jazzy
cmake --build <build>
```

執行需要七個環境變數，缺任何一個都會非零退出（不會靜默用不安全的預設值）：

```
OBSERVER_IDENTITY_CA     OBSERVER_CERTIFICATE     OBSERVER_PRIVATE_KEY
OBSERVER_GOVERNANCE      OBSERVER_PERMISSIONS     OBSERVER_PERMISSIONS_CA
OBSERVER_AUDIT_LOG
```

選用：`OBSERVER_LOG_LEVEL`（預設 `WARNING_LEVEL`）、
`OBSERVER_EVENTS_LOG`（預設 `<audit_log>.events.jsonl`）。

用法：`security_observer <domain_id> <seconds>`（預設 30、60）。
