# 監督器空轉 80 分鐘：一個根因、三個放大器（2026-09-20）

> 早上 09:07 之後，campaign **連續 19 輪、80 分鐘一場都沒產出**，而日誌每輪
> 只寫一句「stack 起不來」。
>
> 根因是 Fast DDS 的共享記憶體段沒被清掉。但真正讓它變成 80 分鐘的，是三個
> 放大器——**每一個都在監督器裡，沒有一個在防禦或攻擊裡**。

## 根因：殘留的 Fast DDS SHM 段

`~/.sros2_live_runtime/permissive.log` 裡是幾百行同一件事：

```
[RTPS_TRANSPORT_SHM Error] Failed init_port fastrtps_port7143:
    open_and_lock_file failed -> Function open_port_internal
```

port 7143–7177 全部開不起來。Fast DDS 的 SHM transport 在 `/dev/shm` 開 port
檔並上鎖；行程被硬殺之後鎖留著，下一個 participant 就拿不到。

**而症狀是 readiness 失敗**——enforce 那邊的日誌讀起來是：

```
[intelligent_defense_node]: 🛡️ D5 monitor heartbeat state=fault:
    啟動後 31.4s 從未收到 monitor 心跳 (>10s)
[sensor_hub_node]: ⚠️ 危險：LiDAR 尚未收到有效資料；IMU 尚未收到有效資料
```

看起來像 monitor 掛了、像 Gazebo 沒出資料。**實際上是所有節點都看不見彼此。**
這是本專案第 N 次「觀測／基礎設施的缺陷偽裝成被觀測系統的問題」。

事後在乾淨狀態下量到：`/dev/shm` 有 **8 個**殘留的 `fastrtps_*` 段。清掉之後
stack 立刻正常啟動，45 秒內就有新場次落地。

## 放大器一：`live_stack.sh stop` 結構上殺不到舊孤兒

`live_stack.sh` 殺的是 **pid 檔記錄的行程群組**（`kill -TERM -- "-$pid"`）。
對它自己啟動的那一輪有效。但是：

```
round N   : 啟動 → 寫 pid 檔 → readiness 失敗 → stop（殺不乾淨，剩幾個）
round N+1 : 啟動 → **覆蓋 pid 檔** → 上一輪的孤兒從此再也找不到
```

於是殘留單調成長，日誌自己記下了這條曲線：

```
36 → 42 → 48 → 54 → 60 → 66      每輪 +6
```

而那些孤兒正是抓著 SHM 鎖不放的人。**放大器與根因互相餵養。**

修法：監督器自己加一道**按名字**的兜底清除（先 TERM 再 KILL），並在清乾淨
之後才清 SHM 段。

⚠️ 按名字殺是危險動作。`STACK_PATTERNS` 只列夠特定的名字——`ros_gz_sim create`
要寫成 `ros_gz_sim`，`create` 這種通用字會誤殺使用者自己的行程。
`test_the_kill_patterns_are_specific_enough` 把這條釘住。

## 放大器二：啟動輸出被整個丟掉

```bash
bash firewall_lab/live_stack.sh start "$1" >/dev/null 2>&1 || return 1
```

所以監督器日誌只寫得出「起不來」，而真正的原因躺在另一個檔案裡沒有人看。
**80 分鐘裡每一輪都印出了幾百行 SHM 錯誤，而它們從來沒有進到我會讀的那個檔案。**

修法：啟動輸出留檔；readiness 逾時就把 stack 日誌的尾巴、`/dev/shm` 的段數與
殘留行程數一起印進監督器日誌。

## 放大器三：重試迴圈沒有停止條件

這是最貴的一個。`while :; do` 裡沒有任何「試了幾次都不行就停」的判斷，
所以它會**安靜地空轉到天亮**。

C2C-049 對跨主機批次就寫過這條原則：

> 無人值守的批次必須會大聲失敗。

那支有兩道自動停止，這一支當初漏掉了。已補 `MAX_BARREN_BATCHES=4`（約 16
分鐘），並在停止時把診斷順序印出來。

## 收尾時我自己製造的第四個問題

重啟腳本裡我寫了 `rm -f /home/jesse/mega_plan.json.lock`，註解是
「前面已確認沒有 campaign 行程」。**而那一步只查了 `run_mega_campaign.sh`，
沒有查 `firewall_lab.campaign`。**

於是舊監督器留下的孤兒 campaign 還活著，新監督器又起了一個，**同一秒有兩場
session 都是 `status=running`**，兩個行程各自把記憶體裡的計畫寫回同一個檔案。

抓到之後：終止孤兒那一個的整個行程群組，保留監督器底下的那一個；檢查磁碟上
沒有半截場次（`manifest.json` 缺失或非 complete 且已停止更新的，0 個）。

**鎖只防得住遵守它的人，而刪鎖的人正是我。** 所以除了鎖之外，監督器現在會
直接數行程：`assert_no_other_campaign` 在啟動任何一批之前執行，發現別的
campaign 就不開始。

## 第五個：改一支正在執行的 bash 腳本

bash 是**邊讀邊執行**的，它在檔案裡保留一個位移。在正在執行的腳本前面插入
幾十行，等於把那個位移指到別的地方。

所以修好之後不能直接讓它繼續跑。處置：停掉監督器（不動正在跑的 campaign——
那一批的資料是好的，硬殺只會多一個半截場次），另起一個 watcher 等那個
campaign 自己結束，再用新版腳本重啟。

## 順帶抓到的一個經典

```bash
count_stack_processes() { pgrep -cf "$STACK_PATTERNS" || echo 0; }
```

沒有命中時 `pgrep -c` **自己會印 0，而且退出碼是 1**，於是 `|| echo 0` 再印
一次——回傳值是兩行，下游的 `[ "$left" -eq 0 ]` 炸成
`integer expression expected`。改用 `| wc -l`，它永遠只印一個整數。

## 驗證

`tests/test_mega_supervisor.py`（9 個）把上面每一條釘住，包括：

| 測試 | 釘住什麼 |
|---|---|
| `test_the_script_parses` | `bash -n`。語法錯誤會讓整夜一行都不跑 |
| `test_every_called_helper_is_defined` | 未定義的函式在 bash 只回 127 然後繼續跑 |
| `test_the_loop_stops_after_barren_batches` | 重試迴圈一定要有停止條件 |
| `test_teardown_escalates_beyond_live_stack` | 先 TERM 再 KILL，不可直接硬殺 |
| `test_the_kill_patterns_are_specific_enough` | 按名字殺不可以用通用字 |
| `test_shm_cleanup_never_runs_while_the_stack_is_alive` | 清掉正在用的段＝把還能救的 stack 弄死 |
| `test_stack_up_reports_why_it_failed` | 啟動輸出不可以整個丟掉 |
| `test_empty_sessions_are_moved_not_deleted` | raw 證據不刪 |
| `test_a_second_campaign_is_refused_even_without_the_lock` | 鎖之外還要數行程 |

⚠️ 其中兩個測試在寫的當下就被自己的**根因說明**咬到——註解裡引用了
`>/dev/null` 與 `wait(timeout=5)`，而斷言是對原始碼做子字串比對。
`_code_only()` 把註解濾掉。**斷言要看程式碼，不是文件**，這是同一天第二次。

## 這一天第三次踩到的同一個坑

用 heredoc 餵 Python 改檔時，字串裡的 `\n` 被 shell 變成**真的換行**，
把一行註解切成兩行——第二行不是註解，於是引號沒有關上，bash 在 150 行之後
才報出 `syntax error near unexpected token ')'`。

那個報錯位置與真正的問題完全無關，只能用「逐行截斷 + `bash -n`」二分出來。
**涉及 `\n` 的修改一律改用編輯工具，不要走 heredoc。**
