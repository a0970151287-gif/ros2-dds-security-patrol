## 0. ⚠️ 先更正我當天稍早寫下的一個結論

我在本輪一開始說：

> Enforce 17 類裡有 5 類恆為 0.000，所以 balanced accuracy 上限是
> 12/17 = **0.7059**，**低於 0.80 的門檻，算術上到不了**。

**那是錯的，而且錯在量測解析度，不在算術。**

`evaluate_pooling_and_temporal.py` 用的是 validation 分區，而
**Enforce validation 每類只有 3 場**。逐類 recall 因此只能是 0、0.333、
0.667、1.000——**一場的差別就是 0.333**，而「3 場全錯」就顯示成 0.000。

換成每類 17 場之後：

| 類別 | validation（n=3） | **CV（n=17）** |
|---|---:|---:|
| `replay` | 0.000 | 0.000 |
| `parameter_tamper` | 0.000 | 0.059 |
| `scan_drift` | 0.000 | 0.118 |
| `cross_channel_relay` | 0.000 | 0.176 |
| **`replay_dos`** | **0.000** | **0.412** |

**五個「死類別」裡有四個根本沒死。** 真正恆零的只有 `replay` 一類，
所以上限是 **0.9412**，不是 0.7059——**門檻沒有被算術擋住。**

> **在 n=3 上宣稱「某一類永遠是零」，等於把三次擲硬幣全反面說成硬幣沒有正面。**

## 1. 換量法：GroupKFold 依場次切，跨 train ＋ validation

- 每一場**恰好被預測一次**，所以逐類 recall 是在全部 17 場上算的。
- 依 `session_id` 分組，同一場不跨折——與既有的防洩漏協定一致。
- **test 完全排除**（Enforce 627 列、Permissive 570 列不進來）。
- 每組 3 個 seed，逐場取多數決。

解析度：每類 3 場 → **17 場**，約 5 倍。

### 洩漏檢查

| 檢查 | 結果 |
|---|---|
| 特徵集 | 32 個真實遙測／網路量；`window`、`window_start_unix`、`session_id`、`scenario_id`、`label`、`split`、`novelty_role` 全在 `NON_FEATURE` |
| 打亂場次標籤（Enforce） | **0.0761**，亂猜 0.0588，佔真實 **13.7%** |
| 打亂場次標籤（Permissive） | **0.0784**，亂猜 0.0667，佔真實 **7.9%** |

打亂的是「場次 → 攻擊類別」這個對應，**攻擊場次裡的 normal 列保持 normal**
——否則對照臂的資料結構與真實臂不同，掉下來就不能歸因於標籤被打亂。

### Permissive 實際上已經解決了

255 場**錯 1 場**。15 類裡 14 類是 1.000，只有 `scan_drift` 是 0.941（16/17）。

⚠️ 這**不能**與活狀態表的 0.8502 相比——那是**逐視窗**、在 **test** 上的數字，
這裡是**場次層級**、在 CV 上的。是兩個不同的任務與兩種不同的評估。

### Enforce 的 0.42 缺口是模型側的

```
1.000  confused_deputy, hmac_forgery, node_churn, service_dos
0.941  command_injection, normal
0.824  discovery_recon
```

**散到其他攻擊類別，不是散到 `normal`** ⇒ 二元偵測抓到了，**壞的是識別**。

## 3. 超參數網格：只有一個旋鈕有用

範圍**在跑之前就宣告**（寫在 `sweep` 腳本頂端），跑完不追加：

```
temporal      : none | d1_m3_x3 | d1_m3_x3_m5_x5
rule          : session_attack_only | session_vote | session_mean
class_weight  : balanced_subsample | none
trees         : 300 | 600          →  3 × 3 × 2 × 2 = 36 組 × 2 模式
```

**判讀用邊際平均，不是挑最高分那一組**——36 組裡取極值本來就會偏高
（第 1 名 0.5606 與第 2 名 0.5571 只差 0.0035）。

| 軸 | Enforce 邊際平均（每組 n=12） | 判讀 |
|---|---|---|
| **時序深度** | none 0.2993 → `d1_m3_x3` 0.4028 → **`+m5_x5` 0.4541** | **有效，兩段都有** |
| 池化規則 | mean 0.3056 → vote 0.3526 → **attack_only 0.4980** | 確認先前結論 |

| 樹數 | 300 → 0.3848、600 → 0.3860 | **雜訊** |

**所以選擇是：加深時序，其餘保留現行值。** 沒有量到差別就不要改——
改了只會多一個之後要解釋的差異。

## 5. 不可宣稱

- **這些是 train ＋ validation 的交叉驗證，不是 held-out test。**
  要變成可引用成績仍然需要一批沒有被花過的 test。進度百分比因此**不動**。
- **設定是在同一批 CV 上選的。** 邊際平均比挑極值穩，但仍有選擇壓力；
  真正的檢定是新 test。
- **場次層級 ≠ 逐視窗。** 0.9961 與 0.5571 都不可與 0.8502／0.2819 相比。
- 出貨模型**一個位元都沒改**（`changes_shipped_defaults: false`）。
  這一輪產出的是「下次重訓要用什麼設定」的證據，不是新模型。
- Permissive 的 0.9961 是 255 場錯 1 場——樣本數撐不起「錯誤率 0.4%」這種精度。
