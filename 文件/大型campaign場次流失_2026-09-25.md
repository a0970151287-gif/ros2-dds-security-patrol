## 二、三個失效模式，數量幾乎相等

把 137 場依它們留下什麼分開：

| | n | 樣子 |
|---|---:|---|
| A | 47 | **完全沒有輸出**（stdout／stderr 都是 0 位元組） |
| B | 48 | **跑完了、印完決策軌跡，仍被殺** |
| D | 42 | 有輸出但沒跑完 |

把三種混成一個 `rc=-9` 的計數，是一個數字藏住三個修法。

**B 類最有訊息量**：

```
歷時 − (declared − reserve)   中位數 −1.22s   ⇒ 攻擊沒有超時
process_wall − declared        中位數 +3.07s   ⇒ 正好是工廠的寬限期
```

⇒ **超時的是收尾，不是攻擊。**

## 三、⚠️ 第一個假設被自己的量測推翻

看到一場 `啟動耗時 5.93s / 預留 4s` 就以為是開機太慢。量完全部：

| | n | 被殺率 |
|---|---:|---:|
| boot ≥ 預留 | 9 | **22.2%** |
| boot < 預留 | 123 | **49.6%** |

**開機快的反而被殺得更多。** 兩組的 boot 中位數都是 0.35–0.37 秒，5.93 秒那場
是離群值。我拿兩個手挑的樣本當成分布——**第四次在同一個問題上用推論代替量測**
（前三次是 C2C-072、C2C-073 與 C2C-074 的前三輪）。

## 四、機制：`_close_within` 的界線不成立

收尾理應被限制在 `CLOSE_BUDGET_SEC = 2.0` 秒：close 丟到 daemon thread，
主執行緒 `done.wait(2.0)` 之後 `os._exit(0)`。那個函式的 docstring 明寫它是
為了繞開「SIGALRM 在 C 擴充裡不會遞送」的陷阱。

**但 daemon thread 繞不開同一個陷阱。** rclpy 的 shutdown 在 C 擴充裡握著 GIL，
主執行緒就連 `done.wait()` 都跑不動——**它要的是同一把鎖**。

裝上逐段計時之後的第一筆：

```
⏱ close 等了 2.76s（預算 2.0s）——主執行緒被擋住,daemon thread 沒有把它框住
⏱ 收尾分段：trace 0.01s close 2.76s 合計 2.77s 距期限 +3.58s
```

**機制確認：界線不成立。** ⚠️ 但幅度還沒量清楚——這一筆只超出 0.76 秒，
而要解釋 4–9 秒的收尾還需要更多樣本，特別是被殺的那些。**尚未下結論，
也還沒有改任何參數。**

## 五、熔斷器沒有壞，而它正是產能塌掉的機制

C2C-079 一度寫「熔斷器永遠不觸發」。**那是錯的**（更正見 C2C-080）：
`completed` 與 `ineligible` 是 `execute_campaign()` 的區域變數，比率本來就
逐批算，而 `mega_campaign.log` 裡有 **21 次**中止。

正確的版本更能解釋產能：

```
SIGKILL 率 ≈ 30%
⇒ 一批 40 場裡,第 5 個不合格平均在第 17 場出現
⇒ 批次在 8–16 場就中止（實測 round 5 enforce 14 場、round 6 enforce 16 場）
⇒ 每次中止都要付一次 stack 起停
```

**不是閘門太嚴，是底下的失敗率太高。** 修好收尾會讓每批從 8–16 場回到接近
40 場——大約三倍。

順帶一個性質：兩個條件是 **AND**，所以第 5 個不合格若出現在第 20 場之後
（`5 > 0.25 × 20` 不成立），批次會**繼續**。它擋的是密集的早期失敗，不是總量。
