# 階段 0：DDS 層認證證據取得成功（2026-08-26）

**結果：正面。** 本專案第一次取得 DDS 安全層的遠端認證拒絕記錄，
帶著攻擊者的 GUID prefix。這解除了身份歸因路徑上最前面、風險最高的那個阻塞。

同時得到一個負面結果：**`dds.sec.log.*` 稽核檔不記錄遠端握手失敗**，
即使等級開到最詳細也一樣——所以先前「配置 sink 就能拿到證據」的假設是錯的，
但換一條路可以拿到。

證據：`文件/階段0_DDS認證證據_2026-08-26/`

---

## 一、問題與先前的認知

P2 契約要求三種 `evidence_kind`，其中只有 `authenticated_identity` 是不可偽造的
（`spdp_locator` 與 `sedp_endpoint` 依契約自己的 claim boundary 就是 spoofable）。
而這個專案從來沒拿到過一筆：1,100 場、249,670 行 adapter 日誌，0 筆。

2026-08-18 查出根因：**經由 ROS 建立的 participant 永遠拿不到稽核日誌。**
`librmw_fastrtps_shared_cpp.so` 啟用安全時會自行組出屬性清單，
其中只有 `dds.sec.auth.*`／`access.*`／`crypto.*`，**沒有 `dds.sec.log.plugin`**，
XML 的 `propertiesPolicy` 不被保留。

那份文件把「不經 ROS，直接用 Fast DDS API」列為不可行，理由是會失去 ROS 生態。
**那個否決針對「取代」整個系統是對的**，但漏了一個變體：不取代任何東西，
**旁邊多加一個觀測者**。

---

## 二、做法

`firewall_lab/security_observer/`：一個用 Fast DDS API 直接建立的 participant。

- 用 SROS2 keystore 的合法憑證加入 domain 30（本次借用
  `security_readiness_probe` enclave）
- 因為不經 rmw，**它自己的屬性不會被覆蓋**，可以同時設安全外掛與 logging 外掛
- 只讀：不發布、不訂閱任何使用者 topic
- 不需要 root
- 缺任何一個憑證環境變數就非零退出（fail-closed，已驗證）

ROS 堆疊完全不需要改動，甚至本次實驗連 Gazebo 都沒有啟動——握手是觀測者與
攻擊者之間直接發生的。

---

## 三、兩個實驗

### 3.1 稽核檔路線：失敗

| 條件 | `dds_security_audit.log` |
|---|---|
| 觀測者本地憑證路徑錯誤 | ✅ 記到 1 筆 `[EMERGENCY] … PKIDH::validate_local_identity` |
| 觀測者正常 ＋ wrong-CA 攻擊者，`WARNING_LEVEL` | ❌ 0 bytes |
| 觀測者正常 ＋ wrong-CA 攻擊者，**`DEBUG_LEVEL`** | ❌ **0 bytes** |

第一列很重要：它證明 **logging plugin 在安全模式下確實初始化了**
（記錄帶 GUID prefix `01.0f.66.7d.…`、entity id、domain、
安全外掛函式名 `PKIDH::validate_local_identity`）。所以 0 bytes 不是
「plugin 沒載入」，而是**這個 plugin 不記錄遠端握手失敗**。

等級由 `EMERGENCY` 排到 `DEBUG`，開到最詳細仍然沒有，所以也不是被過濾掉。

### 3.2 Listener 路線：成功

改用 `DomainParticipantListener::onParticipantAuthentication` 回呼。
它帶 `ParticipantAuthenticationInfo`，內含 `status`
（`AUTHORIZED_PARTICIPANT`／`UNAUTHORIZED_PARTICIPANT`）與遠端 `GUID_t`。

| 條件 | 認證事件 |
|---|---|
| 觀測者 ＋ N28 wrong-CA participant | **2 筆 `UNAUTHORIZED`** |
| **觀測者單獨（對照組）** | **0 筆** |

攻擊組記錄：

```json
{"event":"participant_authentication","status":"UNAUTHORIZED",
 "guid":"a2.5a.10.4e.14.09.dd.6b.d7.33.a8.81|0.0.1.c1"}
```

N28 執行狀態：`rc=124`（timeout 正常結束），attack log 顯示 talker 發了 29 則
——攻擊確實執行滿 30 秒，不是「回報成功但沒跑」。

**對照組是必要的**：沒有它就無法排除「這個回呼對任何東西都回報 UNAUTHORIZED」。
這與 direct-delivery canary 需要合法憑證對照組是同一個道理。

---

## 四、為什麼這個結果重要

契約要的 `authenticated_identity` 觀測需要兩件事：**GUID prefix** 與
**認證結果**。listener 回呼兩者都給，而且是**結構化事件**，不是需要再解析一次
的文字日誌——比原本設想的稽核檔路線更適合當證據來源。

這也修正了先前的判斷：`sros_auth_fail_rate` 與 `sros_permission_deny_rate`
之所以恆為零，**不只是因為沒有 sink**，而是因為 ROS 這一層根本拿不到；
但換一個 participant 就拿得到。

---

## 四之二、雙觀測者實驗：AUTHORIZED 路徑與 subject 來源

第二次實驗同時跑兩個**合法**觀測者（不同 enclave）與一個 wrong-CA 攻擊者，
目的是看 AUTHORIZED 路徑，以及契約要的 `identity_subject_sha256` 從哪裡來。

觀測者 A（`security_readiness_probe`）記到：

```json
{"event":"participant_authentication","status":"AUTHORIZED",
 "guid":"d8.b7.19.e7.25.90.f5.66.28.23.a8.0e|0.0.1.c1"}
{"event":"participant_discovery","status":"0",
 "guid":"d8.b7.19.e7.25.90.f5.66.28.23.a8.0e|0.0.1.c1",
 "claimed_subject":"/CN=/local_outcome_probe"}
{"event":"participant_authentication","status":"UNAUTHORIZED",
 "guid":"a2.5a.10.4e.14.09.ff.76.a1.d8.57.2d|0.0.1.c1"}
```

觀測者 B 對稱地記到 A 的 `AUTHORIZED` 與 `/CN=/security_readiness_probe`，
以及同一個攻擊者 GUID 的三筆 `UNAUTHORIZED`。

### 三個發現

**1. subject 來自 discovery 而不是 authentication。**
`onParticipantAuthentication` 只給 status 與 GUID。憑證 subject 在
`on_participant_discovery` 的 `identity_token_` 裡，屬性名 `dds.cert.sn`。
兩個回呼要合起來用：GUID 當鍵，status 決定那個 subject 算不算「已驗證」。

**2. 攻擊者完全沒有 subject。**
N28 只產生 `UNAUTHORIZED` 認證事件，**沒有任何帶 `claimed_subject` 的
discovery 事件**。所以拿不到它宣稱的身分——連未經驗證的都沒有。

**3. 兩個獨立觀測者看到同一個攻擊者 GUID。**
`a2.5a.10.4e.14.09.ff.76.a1.d8.57.2d` 在 A 與 B 的紀錄裡一致。
這對應契約的 `trusted_collector_attestation` 與
`two_consecutive_signed_windows` 想要的獨立佐證。

附帶觀察（尚未查證成因）：N28 兩次執行的 GUID 前 6 個位元組相同
（`a2.5a.10.4e.14.09`），後 6 個不同。但三個 participant 在同一台機器上
彼此的前綴並不相同，所以**不能**據此宣稱前綴可辨識主機。這只是觀察，
不是結論。

## 四之三、這推翻了封鎖規則，包括我自己寫的那一版

`工具腳本/dryrun_identity_pipeline.py` 初版的 `_blockable` 要求
「該 GUID 有 `authenticated_identity` 記錄」才可封鎖。**那是錯的**——
攻擊者的認證失敗，所以它永遠不會有那筆記錄。要求它有，規則就永遠封鎖不了
任何人。已更正為：

1. 該 IP 只對應一個 GUID（否則封鎖會波及合法 participant），且
2. 該 GUID **沒有** `authenticated_identity` 記錄（不是合法身分）

更正後乾跑給出正確答案：跨主機情境**只有攻擊者那個 IP 可封鎖**，
防守方三個 participant 共用的 IP 被正確拒絕。

**但這暴露了契約的一個缺口。** 契約的三種 `evidence_kind` 裡：

- `authenticated_identity` 需要 subject → 只有合法 participant 才產得出
- 攻擊者只能被記成 `spdp_locator`，而契約自己說那是**可偽造的**

也就是說，**契約沒有任何一種證據類型可以承載「某個 participant 嘗試認證並
被拒絕」**——而那正是封鎖的正當理由。建議新增一種 `rejected_identity`
（帶 GUID ＋ 拒絕時間 ＋ 觀測者身分，不帶 subject，因為沒有）。
已回報 Codex。

## 四之四、endpoint 證據與契約格式轉換（2026-08-26 下午）

### 觀測者能產出第二種證據

加上 `on_publisher_discovery`／`on_subscriber_discovery` 之後，一個合法憑證的
ROS 節點（`listener` enclave）被完整記錄：**40 個 endpoint，各自帶 GUID
（含 entity id）與 topic 名稱**，例如
`rt/rosout`、`rr/listener/get_parametersReply`、`rt/parameter_events`。
那正是契約的 `sedp_endpoint`。

宣告的位址也取到了：`UDPv4:[10.255.255.254]:14912 UDPv4:[172.30.123.103]:14912`。

### 攻擊者連宣告位址都沒有——這是架構層級的發現

| | 認證 | subject | endpoints | 宣告位址 |
|---|---|---|---|---|
| 合法 `/listener` | AUTHORIZED | `/CN=/listener` | 40 | 有 |
| wrong-CA 攻擊者 | UNAUTHORIZED | **無** | 0 | **無** |

`on_participant_discovery` 對認證失敗的 participant **從未觸發**，只有
authentication 回呼會響。所以：

> **觀測者單獨無法把攻擊者對應到任何 IP。**

要拿到攻擊者的來源位址，只能靠封包擷取（SPDP 封包在網路上，不管認證過不過
都看得到）。這替契約的三種證據等級提供了實證依據：

| 來源 | 給得到什麼 |
|---|---|
| 安全觀測者 | 認證判定 ＋ GUID；合法者另有 subject／endpoint／宣告位址 |
| 封包擷取 | 實際來源 IP ↔ GUID（含認證失敗者） |

**兩者缺一不可。** 觀測者知道「誰不合法」但不知道它在哪；封包知道「誰在哪」
但不知道合不合法。

### 契約格式轉換：端到端打通

`工具腳本/observer_events_to_observations.py` 把觀測者事件轉成
`rtps_identity.jsonl`。對 0d 那一輪的實際事件：

```
=== 產生 42 筆觀測（全部通過 P2 驗證器）===
  authenticated_identity   1
  sedp_endpoint            40
  spdp_locator             1
略過 1 項：
  a2.5a.10.4e.14.09.cf.ff.2e.3a.41.f8: 沒有可用的 IPv4 宣告位址
```

再餵進 P2 的 `build_identity_window_features`：

| 特徵 | 值 |
|---|---:|
| `rtps_participant_rate` | 0.125 |
| `rtps_endpoint_rate` | 2.5 |
| `rtps_topic_diversity_ratio` | 0.9 |
| `rtps_authenticated_binding_ratio` | **1.0** |
| `rtps_complete_evidence_ratio` | **1.0** |
| `rtps_ip_multi_guid_ratio` | 0.0 |

安全旗標仍全部為 `false`（`source_ip_attribution_verified`、
`deployment_eligible`、`automatic_ip_block_authorized`）——契約的 fail-closed
設計正確運作。

**這是本專案第一次產出契約合法的 `rtps_identity.jsonl`**，
而且是從真實 live 事件轉出來的，不是合成的。

⚠️ 轉換器刻意**不**替攻擊者編造記錄。它沒有宣告位址、沒有 subject，
契約也沒有「認證遭拒」的類型，所以它被列在略過清單裡而不是塞進觀測檔。

### 「觀測者什麼都沒記到」的根因（2026-08-26 已查明）

0c 那一輪觀測者**完全沒記到攻擊者**，儘管 N28 確實執行（rc=124、發了 19 則）
且與觀測者重疊約 19 秒。當時我猜是 SPDP 週期或啟動順序，**那個猜測是錯的**。

跨主機乾跑時同一個現象再次出現，這次有封包擷取可以對照：兩個 GUID
（觀測者 `a03a1414…`、N28 `a25a104e…`）**同時在 `lo` 上有流量**，重疊 19 秒，
而觀測者的 listener 一筆都沒觸發。所以不是沒重疊，是兩個 process 真的看不見對方。

四種條件對照：

| 條件 | 認證事件 |
|---|---:|
| 同一 shell ＋ source ROS | 2 ✅ |
| **不同 shell ＋ source ROS** | **2 ✅** |
| 不同 shell ＋ 沒 source ROS | **0 ❌** |
| （乾跑：runner 沒 source ROS） | 0 ❌ |

決定變因是 **source ROS**，不是 shell、不是順序。原因在函式庫解析：

```
沒 source ROS : libfastrtps → /opt/ros/jazzy/lib/   libfastcdr → /usr/local/lib/
有 source ROS : libfastrtps → /opt/ros/jazzy/lib/   libfastcdr → /opt/ros/jazzy/lib/
```

`libfastrtps` 是對 ROS 那份 FastCDR 編譯的。換成 `/usr/local` 的另一套之後，
participant 仍然建得起來、安全外掛仍然載入、log 乾乾淨淨、程式跑滿整個視窗——
**只有 discovery 靜默失效**。

這是這個專案最危險的那一類失敗：**「沒有攻擊」與「觀測管線壞掉」外觀完全相同。**
已經被同一類問題咬過的有 N1 的 QoS 不相容、8,192 點 scan 在傳輸層被丟、
marker 全檔掃描撐爆視窗，這是第四次。

修法不是記在文件裡提醒自己，是 fail-closed：`run_crosshost_identity.sh`
在 `set -u` **之前** source ROS（setup.bash 會讀未設定的 `AMENT_TRACE_SETUP_FILES`），
並在 preflight 用 `ldd` 斷言 FastCDR 與 FastRTPS 來自同一個目錄，不符就中止。
已驗證這道 gate 會咬人（`ROS_SETUP=/nonexistent` 時正確中止）。

修正後同機重跑，**兩半第一次對上**：封包看到 2 個 GUID、觀測者判定
1 筆 UNAUTHORIZED、交集 1 個 GUID（先前是 0）。剩下不可封鎖的原因變成純粹的
同機物理限制——`127.0.0.1`、`172.30.123.103`、`10.255.255.254` 每個都掛 2 個
GUID，那正是第二台主機要解決的部分。

## 五、還不能宣稱什麼

1. **這是同機實驗。** 觀測者與攻擊者都在 `127.0.0.1`，所以**仍然無法做
   identity → IP 歸因**。GUID 拿到了，但那個 GUID 對應的 IP 與防守方自己的
   participant 共用，逐 IP 判定仍然不合格。跨主機仍是必要條件。
2. **只有 2 筆，只有一種攻擊類型。** 還沒有配對、還沒有統計量、
   還沒有接進收集器與契約格式。
3. **借用了既有 enclave 的憑證。** 正式收集時觀測者應該有自己的 enclave。
4. **`permission` 層還沒驗。** 本次只證明 authentication 拒絕可記錄；
   契約的 `permission_state` 需要另外驗證（合法憑證但越權的情形）。
