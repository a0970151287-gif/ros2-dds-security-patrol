# 來源位址偽造的加固：封鎖判定加上第四條（2026-08-31）

> 全程離線。未啟動 ROS、未產生任何流量、未使用 `sudo`、未連接第二台主機。
> 原始 pcap 與既有的 `crosscheck.json` 一個位元組都沒有改。

## 為什麼要加

前三條判定擋不住**來源位址偽造**，而那是自動封鎖最糟的失效方向：

1. 同一個 L2 網段上的攻擊者，以**受害者的 IP** 為來源送出帶自己 GUID 的 RTPS
2. 握手必然失敗——防守方的回應依 ARP 送到**受害者**那裡去了
3. 觀測者記下 `UNAUTHORIZED`
4. 封包層把那個 GUID 綁到**受害者的 IP**

前三條全部成立 → **系統宣告一個無辜主機可封鎖**。

2026-08-30 那批 79／80 的陰性對照**測不到它**：對照組是防守方自己
（`192.168.0.129`），不是被偽造的第三方。

## 鑑別方式（完全被動）

擷取檔裡有乙太網標頭，而且兩個方向的 MAC 意義不同：

| 方向 | 欄位 | 這個 MAC 是什麼 |
|---|---|---|
| 收到 `ip.src = X` | `eth.src` | **實際發送者**的 MAC |
| 送出 `ip.dst = X` | `eth.dst` | 防守方**自己的 ARP 解析結果** |

偽造來源時這兩個必然不同——回應會被送到真正持有那個 IP 的主機。所以判準是：

> **`eth.src`（收到 X 的封包）必須等於 `eth.dst`（送往 X 的封包）。**

受害者若根本不存在，防守方連 ARP 都解析不到，就不會有送往該 IP 的單播流量
——那時同樣不可封鎖（**無法驗證，不是驗證通過**）。

不需要送出任何封包，所以不需要 live 授權。

### 三級判定

| verdict | 條件 | 下游 |
|---|---|---|
| `consistent` | 唯一的來源 MAC ＝ 唯一的解析 MAC | 可封鎖（其餘三條也要成立） |
| `spoofing_evidence` | 來源 MAC 與解析 MAC **完全不相交** | **確證偽造**，不可封鎖 |
| `unverifiable` | 單向流量、或多個 MAC 有交集 | 分不出來，不可封鎖 |

`unverifiable` 與 `spoofing_evidence` 分開，是因為實測發現**防守方自己的位址
就會落在前者**：WSL mirrored 讓同一個 IP 同時出現實體網卡 `28:92:00:…` 與
Hyper-V 虛擬網卡 `00:15:5d:…` 的 MAC。判定（不可封鎖）一樣，但理由不能寫成
「這是偽造」——那會是**編造的理由**，與 C2C-048 修掉的那個誤導訊息同一種錯。

**零撤回。** 80 場宣告過的位址全部是 `192.168.0.30`，每一場的鏈路層綁定都是

那批結論在更嚴的規則下站得住，**而且現在更強**——它不再只是「三條成立」，
而是「四條成立，其中一條專門排除了偽造來源」。

每一場的證據已落地為 `link_layer_binding.json`（85 場，1 場無 pcap），
可逐場稽核。彙總在 `文件/鏈路層綁定回驗_2026-08-31.json`。

## fail-closed

`crosscheck_identity_attribution.py` 的 `--link-layer` **不是必填，但沒有它
就沒有任何位址會被判為可封鎖**，而且會明講原因：

```
⚠️ 未提供鏈路層綁定證據，**所有位址一律不可封鎖**。
   來源位址偽造無法排除時那是無法驗證，不是驗證通過。
```

報告 schema 因此升為 `sros2-firewall-identity-crosscheck/v2`——多了一個決定性
欄位，舊版讀者不該把新報告當成同一種東西。

`工具腳本/run_crosshost_identity.sh` 已自動產生並帶入這份證據。讓 runner 自己
做，才不會每次都得記得補跑——而「忘了跑」與「真的無法驗證」在報告上長得一樣。

## 界線（不可宣稱的部分）

- **攻擊者若同時偽造 MAC，這個檢查會被繞過。** 但那樣它也收不到回應，而且在
  WPA2／WPA3 下 AP 以 MAC 對應 station，偽造 MAC 的代價與可見度都更高。
- **這是必要條件不是充分條件。** 它擋掉「偽造來源」這一種失效，不代表通過的
  位址就一定該封鎖——其餘三條仍然要成立。
- **沒有實際做過偽造攻擊。** 上面的偽造情境是單元測試裡的合成資料，不是 live
  證據。要真的驗證，需要在第二台主機上執行來源位址偽造，那是新的 live 授權
  工作。目前只能說「規則會擋下具備該特徵的輸入」，不能說「已在真實攻擊下驗證」。
- `authorizes_action` 仍為 `false`，`executable_classes` 仍為空清單。
