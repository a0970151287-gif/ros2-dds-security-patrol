### 3. `discovery_recon` 被動偵察 ⬅ **下一步**

### 4. 來源位址偽造的加固 ✅ 完成

完整記錄見 [來源位址偽造加固_2026-08-31.md](來源位址偽造加固_2026-08-31.md)。

封鎖判定加上**第四條：鏈路層綁定**。防守方送出時的 `eth.dst` 是它自己的 ARP
解析結果，收到時的 `eth.src` 是實際發送者——偽造來源時兩者必然不同，因為
回應會被送到真正持有那個 IP 的主機。完全被動，不需要送任何封包。

**回頭用新規則驗證 8/30 那批：80 場仍然成立、零撤回。** 那批結論在更嚴的
規則下站得住，而且現在更強。每場的證據已落地為 `link_layer_binding.json`。

三級判定而不是二元：`spoofing_evidence`（確證）與 `unverifiable`（分不出來）
分開，因為防守方自己的位址會落在後者——WSL mirrored 讓同一個 IP 同時出現
實體與虛擬網卡的 MAC。判定一樣，但理由不能編。

⚠️ **沒有實際做過偽造攻擊。** 偽造情境是單元測試的合成資料。只能說規則會擋下
具備該特徵的輸入，不能說已在真實攻擊下驗證——那需要在第二台主機上執行來源
位址偽造，是新的 live 授權工作。**這仍然是滲透測試最該先打的目標。**

## 不要重犯的錯

| 錯 | 教訓 |
|---|---|
| 觀測者釘傳輸 → 合法節點全被判 UNAUTHORIZED | 同機**不可**釘；跨主機**必須**釘。沒有安全預設值 |
| campaign 不啟動 stack | 它假設 external stack，少了就 `not_eligible:runtime_telemetry` |
| 只重跑受益類別 | 會造出「哪些場次有觀測者」的假象提升。用 `check_channel_coverage.py` 擋 |
| 用平均值比較兩臂 | 一個離群值就能編出不存在的擾動。用中位數 |
| 警告而不阻擋 | 觀測者沒起來只印警告 → 壞資料留在結果裡。要作廢那一對 |
| Zeek 每場都警告校驗和，沒有人讀 | 工具的 stderr 有存進 `zeek_process.json`，但沒有任何檢查看它 |
| 修好資料後表變小就以為修壞了 | 舊表的時間解析度是 bug 的副產物；先問「舊的為什麼會那樣」 |
