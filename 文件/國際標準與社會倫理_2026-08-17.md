# SROS2 智慧防火牆：國際標準、社會影響與工程倫理

更新日期：2026-08-17  
用途：專題報告、簡報、答辯與「國際視野與社會關懷」評分證據。

## 1. 專題定位

本專題不是宣稱以單一 AI 模型取代 ROS 2 的安全機制，而是建立一條可稽核的縱深防禦鏈：

```text
DDS／SROS2 預防
  -> HMAC 與 D1-D6 應用／行為驗證
  -> Zeek 與多模態 AI 偵測
  -> 白名單、信心門檻、cooldown、timeout、復原
  -> 有證據且可撤銷的受限回應
```

對移動機器人而言，錯誤封鎖、錯誤急停與放任攻擊都可能造成實體風險。因此本專題把「安全降級、人工可介入、可撤銷、可追溯」視為與偵測率同等重要的研究目標。

## 2. 與國際規範的對照

### 2.1 OMG DDS Security 1.2

OMG 於 2026 年 2 月列出 DDS Security 1.2 正式版本。規範以外掛介面描述 Authentication、Access Control、Cryptographic、Logging 與 Data Tagging 等安全能力。

本專題對照如下：

| DDS Security 能力 | 本專題做法 | 目前證據邊界 |
|---|---|---|
| Authentication | SROS2 Identity CA、逐 enclave 憑證 | keystore／政策稽核與 Enforce readiness 已有；不讀取或匯出私鑰 |
| Access Control | Permissions CA、逐節點最小 topic 權限 | policy／enclave 產生與靜態稽核已有；仍需直接 delivery canary 補 live 結果 |
| Cryptographic | DDS discovery／data 保護 | 可由受控封包擷取與設定佐證；跨主機封包驗收尚未完成 |
| Logging | 嚴格來源驗證的 telemetry adapter | Fast DDS security audit sink 目前未建立，因此兩個 deny 特徵標為 `source_unavailable`，不得把 0 當成「沒有拒絕」 |
| Data Tagging | 未列入本階段 | 明確標示 out of scope，不把 HMAC envelope 誤稱 DDS Data Tagging |

官方來源：

- OMG, [DDS Security 1.2 specification](https://www.omg.org/spec/DDS-SECURITY/1.2/About-DDS-SECURITY)

### 2.2 ROS 2／SROS2 官方設計

ROS 2 的 DDS Security 整合文件說明，ROS 2 使用 PKI-DH 認證、Permissions access control 與 AES-GCM-GMAC authenticated encryption；SROS2 則提供 keystore、enclave 與 `ROS_SECURITY_STRATEGY=Enforce` 等工具與執行模式。

本專題採用：

- Identity CA 與 Permissions CA 分離。
- 每個節點／context 使用獨立 enclave 與最小權限。
- Enforce 為預防層，AI 只處理剩餘風險與跨層異常。
- 對同機 Fast DDS shared-memory 的封包可見性限制保持誠實；官方文件亦指出，同機 shared memory 可能使網路介面無法擷取實際資料流。

官方來源：

- ROS 2 Design, [ROS 2 DDS-Security integration](https://design.ros2.org/articles/ros2_dds_security.html)
- ROS 2 Jazzy, [Understanding the security keystore](https://docs.ros.org/en/ros2_documentation/jazzy/Tutorials/Advanced/Security/The-Keystore.html)
- ROS 2, [Examining network traffic](https://docs.ros.org/en/ros2_documentation/rolling/Tutorials/Advanced/Security/Examine-Traffic.html)
- ROS 2 Design, [ROS 2 Robotic Systems Threat Model](https://design.ros2.org/articles/ros2_threat_model.html)

### 2.3 NIST AI RMF 1.0

NIST AI RMF 1.0 將可信任 AI 的特性包含 valid and reliable、safe、secure and resilient、accountable and transparent、explainable and interpretable、privacy-enhanced，以及 harmful bias managed。NIST 目前亦明載 AI RMF 1.0 正在修訂，因此本專題把 1.0 當作現階段治理基線，而非聲稱已符合尚未完成的新版。

| AI RMF 核心功能 | 本專題落實 |
|---|---|
| GOVERN | 威脅模型、禁止事項、資料／模型／動作政策 hash、明確 non-deployable gate |
| MAP | 分開 normal、known attack、unknown attack、source unavailable 與 attacker-IP attribution 風險 |
| MEASURE | session-grouped split、PR-AUC、balanced accuracy、macro-F1、FPR、coverage、事件級指標與重現性稽核 |
| MANAGE | observe-only 起步、白名單、cooldown、timeout、重啟復原、人工批准與 rollback |

官方來源：

- NIST, [Artificial Intelligence Risk Management Framework 1.0](https://www.nist.gov/publications/artificial-intelligence-risk-management-framework-ai-rmf-10)
- NIST, [AI RMF overview and revision status](https://www.nist.gov/itl/ai-risk-management-framework)
- NIST AIRC, [AI RMF Core: Govern, Map, Measure, Manage](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/)

### 2.4 IEC 62443 系列

IEC 62443 面向工業自動化與控制系統。它強調資產擁有者、服務提供者、產品供應者的分工，以及技術、程序、實體與補償性控制的組合；IEC TS 62443-6-1:2024 另強調可重複、可重現的評估方法。

本專題不宣稱取得 IEC 認證，只借用可驗收的工程思想：

- 將 Raspberry Pi 目標設計成受控 gateway，而非只在端點 `input` chain 封鎖。
- 分離預防、偵測、回應、復原與稽核。
- 以隔離、無外部路由的自有雙主機，重現每個跨主機案例。
- 每個成果附 session、命令、stdout／stderr、PCAP、hash、觀察與 rollback。

官方來源：

- IEC, [IEC 62443-2-4:2023](https://webstore.iec.ch/en/publication/67631)
- IEC, [IEC TS 62443-6-1:2024](https://webstore.iec.ch/en/publication/67462)
- IEC, [IEC PAS 62443-1-6:2025 for IIoT](https://webstore.iec.ch/en/publication/102885)

## 3. 社會關懷與利害關係人

| 利害關係人 | 可能傷害 | 本專題的保護方式 |
|---|---|---|
| 操作者／旁觀者 | 誤判造成機器人突然動作或無法停止 | velocity guard、急停優先、低信心只告警、禁止連續危險輸出 |
| 系統管理者 | 誤封合法設備、無法復原 | allowlist、protected source、TTL、cooldown、原子 nonce、重啟復原 |
| 資料提供者 | PCAP／日誌暴露網路與身分資訊 | 只在自有隔離環境收集、秘密 `<REDACTED>`、資料最小化、限制匯出 |
| 研究與評審 | 過度宣稱導致錯誤決策 | 將 synthetic、offline、loopback、local live、cross-host、kernel acceptance 分層標示 |
| 維護人員 | 黑箱 AI 無法追查 | 保存 features、模型／政策 hash、門檻、reason code、evidence ledger |

## 4. 自動封鎖的倫理與安全原則

自動封鎖只有在下列條件全部成立時才可能開啟：

1. 模型通過獨立 final holdout，而非僅 validation 或看過的 development test。
2. `network_block` 具備獨立 attacker-IP attribution ground truth。
3. 來源不在 gateway、loopback、管理主機、機器人必要節點與保護清單。
4. 同一來源的 ticket 通過簽章、nonce、時效、次數、全域容量與 cooldown。
5. 真實 kernel backend 完成阻擋、歸零、TTL 解除、重啟復原及 rollback 驗收。
6. 隔離雙主機且無外部路由，PCAP 能證明封包沒有離開授權範圍。
7. 人工可覆寫且所有動作可稽核。

目前上述條件尚未全部完成，所以正式候選固定：

```text
deployment_eligible = false
executable = false
adapter = none
autonomous_ip_block_ready = false
```

## 5. 責任揭露文字（可直接放簡報）

> 本專題的 AI 候選目前只提供離線／observe-only 判斷。它不會直接封鎖 IP，也未取得跨主機、Raspberry Pi gateway 或 production nftables 部署資格。尚未可觀測的 SROS2 deny 不會被補成 0；尚未執行的 live 驗收不會被補造成 pass。

## 6. 國際與社會價值

本專題的價值不在宣稱「擋住所有攻擊」，而在把 ROS 2 安全機制、網路觀測、機器人行為與 AI 風險管理整合成可驗證的流程。這種方法可延伸至智慧製造、校園服務機器人、醫療物流與倉儲自動化；在擴充前必須依場域重新做威脅建模、資料治理、安全驗收與人工責任分工。
