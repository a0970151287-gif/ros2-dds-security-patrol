# 重訓那天，未知攻擊那一半沒有路（2026-10-03）

C2C-091 的演練證明過一件事：**那種缺陷只有真的走一次才現形**（當時抓到的是
我把子命令名字記錯，而那在真跑那天會是第一個絆腳處）。所以在 campaign 還在跑
的時候，把「重訓那天會不會卡住」逐項查完。

本輪**沒有執行任何訓練、沒有碰任何 holdout**，全程唯讀。

---

## 一、先關掉一個懷疑：`undecided` 不會擋住重訓

C2C-086 寫「註冊裡是 `undecided` 的項目**拒絕執行**」，而 r4 的
`ood_scorer_enforce` 正是 `undecided`（C2C-088 把 Enforce 的 24 格掃完之後，
那個值的理由升級成「這個選擇在宣告的格子裡不可能有影響」）。
所以我懷疑重訓會因此整個拒絕跑。

**去讀那 20 行之後，不會**：

```python
EXECUTED_SETTINGS  = ("formulation", "model", "temporal_expansion", "feature_variant")
DELEGATED_SETTINGS = ("ood_scorer_permissive", "ood_scorer_enforce",
                      "unknown_session_pooling", "blind_spot_features")

undecided = [k for k in EXECUTED_SETTINGS if settings[k]["value"] == prereg.UNDECIDED]
```

那個檢查**只掃 `EXECUTED_SETTINGS`**，而 OOD scorer 在 delegated 那一組。
設計是對的，懷疑是錯的。

⚠️ 這是本輪第三次「先查證再下結論」擋住一個錯的結論（前兩次是 10-02 的
`pgrep` 自我配對與時間戳切 16 個字元）。

## 二、但那個 delegation 指向一個不存在的路

`retrain_from_registration.py` 的 docstring 明寫：

> 只做**識別**（多類）那一半。未知攻擊那一半的設定由 family-LOO 那套工具評估，
> 硬塞進來只會讓兩件事互相綁死。

那個**範圍切分本身是對的**。問題在被委派過去的那一套：

| | 識別（多類） | 未知攻擊（open-set） |
|---|---|---|
| 一次性機制 | **`seal_holdout.py`**（封印 → 開封一次，而且**在讀 test 列之前**拒絕） | 只有「輸出檔已存在就拒絕覆寫」 |
| 執行者 | `retrain_from_registration.py` | `evaluate_openset_holdout.py` |
| 需要的輸入 | 特徵表 ＋ 註冊 ＋ 封印 | **已簽章的 hierarchical bundle**（`hierarchical_model.joblib`） |
| 表述 | **`session_aggregate`**（2026-09-16 選定） | **逐視窗**（舊的 hierarchical 線） |
| 註冊的那四項設定 | ✅ 逐字執行 | ❌ 只被檢查、**不被執行** |
| 產物保存模型嗎 | **❌**（`joblib`／`pickle`／`save` 出現 **0** 次） | 讀既有 bundle |
| family-LOO 那套評的是 | — | **validation**，不是 holdout |

三個獨立的後果：

### 後果一：那支「重訓」不保存模型，所以下游拿不到任何東西

它擬合 → 在封印的 holdout 上評估 → 寫一份 JSON → **丟掉模型**。
作為**一次性評估**那是對的（模型不可能被偷偷重用），
但它意味著「可部署的模型從哪裡來」是一個**還沒有答案的獨立問題**。

### 後果二：註冊的未知攻擊設定沒有任何封印 holdout 的路徑

`ood_scorer_permissive: max_softmax` 與 `unknown_session_pooling: k_of_n_k2`
是 C2C-076／084 選出來、並在**新資料存在之前**凍結進註冊的。
而要在 holdout 上驗證它們，唯一的一次性工具是 `evaluate_openset_holdout.py`，
而它要的是 **hierarchical bundle**——也就是**舊表述 ＋ 舊 OOD 頭設計**。

⇒ **那兩個凍結的設定，在重訓那天沒有辦法被一次性地驗證。**

### 後果三：未知攻擊那一半的一次性保護是弱的，而它已經失效過

`evaluate_openset_holdout.py` 的三道保護是：輸出已存在就拒絕、先驗證 novelty
協定四個計數全為零、記下 bundle 與特徵表的 sha256。

**防止重複使用的只有第一道，而換一個 `--output` 路徑就能再跑一次。**

這不是假設性的：活狀態表的待辦自己寫著
「**一批沒有被花過的 open-set holdout**——現有的已用第三次，數字不可引用」。

> **強機制（封印）存在，而它從來沒有被接到這一半。**

## 三、所以未知攻擊那一列在重訓那天不會動

那一列的 100% 定義是「整個模型 open-set recall ≥ 0.70」，而：

| 可能的來源 | 為什麼不算 |
|---|---|
| family-LOO（`evaluate_parallel_gate_loo.py` 等） | **validation**，不是 holdout；CLAUDE.md 一貫不計分 |
| `evaluate_openset_holdout.py` ＋ 新的 hierarchical bundle | 那是**舊表述**，而且註冊的兩個設定不在它的路上 |
| 註冊的重訓路徑 | **不產出 open-set 數字，也不保存模型** |

⇒ **3.4 天的新資料會讓識別那一半第一次有足夠解析度，而未知攻擊那一半
仍然只有 validation 數字。** 這與 C2C-096 查到的 gate 分歧是同一個形態：
**選定的表述與既有的驗收機制長在兩棵不同的樹上。**

## 四、要決定的事（我沒有做）

兩個選項，而它們的代價不同：

| 選項 | 做什麼 | 代價 |
|---|---|---|
| **A** | 把 `seal_holdout.py` 接到 open-set 那一半，並讓它吃 `session_aggregate` | 需要一個新的評估器；而**若兩半共用同一批 holdout，封印的「只開一次」會擋住第二半** ⇒ 要先決定共用還是各自封印 |
| **B** | 維持現狀，open-set 只報 family-LOO validation，並在帳本明寫它**不是** holdout | 未知攻擊那一列**永遠停在 70%**，不論資料多少 |

⚠️ **A 裡面那個「共用還是各自封印」是真的取捨**：各自封印等於把 holdout 切兩半，
兩邊的解析度都降低；共用則需要一個「同一個封印可被兩個評估器各開一次」的機制，
而那會削弱「只開一次」這個性質本身。

⚠️ 這兩個選項都涉及**驗收機制**，而 B 等於接受一列永遠不動、A 等於改變
「一次性」的定義 ⇒ **留給 Jesse。** 本輪只把它變成可見的。
