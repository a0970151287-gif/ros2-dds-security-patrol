## 1. 為什麼要重判

活狀態表的「攻擊面覆蓋」寫著：

> `spdp_flood`／`baseline_poisoning`／`verify_flood` 三支彼此不可分——
> 它們只留下**防禦的通用反應**（守衛零速＋一則 alert），沒有自己的痕跡

而那句話撐起了更強的一句：「至少 4 類在目前的觀測層結構上做不到」。

這個判定來自 `check_evidence_exclusivity.py`，而**它只看遙測**。
那三支是 DDS 層的洪水／隱身攻擊，指紋本來就該在封包層。
2026-09-02 那批 smoke 每一場都有 `traffic.pcapng` 與 `zeek/`——gate 從來沒看過它們。

所以我去看了。

## 2. 第一個缺陷：`verify_flood` 送出 1,223 萬筆，一個都沒離開行程

攻擊自己的日誌：

```
QoS reliability = BEST_EFFORT
⏹ 結束：12231436 筆 / 25.0s = 489257 msg/s
```

同一場的 stderr：

```
New subscription discovered on topic '/security/heartbeat',
requesting incompatible QoS. No messages will be sent to it.
Last incompatible policy: RELIABILITY
```

封包層（我自己用 `capinfos` 重數，不引用先前的摘要）：

| 場次 | 封包數 |
|---|---:|
| normal ×3 | 3,320 / 3,375 / 3,375 |
| **verify_flood** | **3,390** |

**1,223 萬筆訊息，比正常多 15 個封包**（對最高的那一場）。訊息從來沒有離開行程。

這是本專案第七次同一個形態（N1 的 QoS、8,192 點 scan 在傳輸層被丟、
marker 全檔掃描撐爆窗、FastCDR 不一致讓 discovery 靜默失效、`wait_for` 被刪、
發送端字彙表缺一項）：**「攻擊沒送到」與「防禦擋下了」在資料上長得一模一樣。**

已修（commit `cd8ee1b`）：flood 之前必須確認至少一個 QoS 相容的訂閱者配對上，
沒有就以非零碼結束。`get_subscription_count()` 只算配對成功的訂閱者。

## 3. 第二個缺陷：整批的擷取看不到 ROS 2

第二個缺陷是在查第一個的時候撞出來的。`odom_spoof` 的日誌寫著

```
✅ N34 結束：送出 1480 筆偽造 odometry
```

而那一場只有 **3,336** 個封包——**比三場正常裡的兩場還少**。
1,480 筆訊息不可能只佔 0 個封包。

拆開擷取檔的組成（`tshark -e ip.dst -e _ws.col.Protocol`）：

| 場次 | 總封包 | 目的位址 | 協定 |
|---|---:|---|---|
| normal | 3,320 | `239.255.0.7` ×3,186、`239.255.0.1` ×134 | UDP 3,186／RTPS 134 |
| verify_flood | 3,390 | 同上結構 | UDP 3,240／RTPS 150 |
| odom_spoof | 3,336 | 同上結構 | UDP 3,186／RTPS 150 |
| spdp_flood | 3,336 | 同上結構 | UDP 3,186／RTPS 150 |
| node_churn | 3,515 | 同上結構 | UDP 3,240／**RTPS 275** |

**每一場都是 100% 多播，一個單播封包都沒有。** 而且：

- `239.255.0.7`（埠 10317／10318）是 **Gazebo 的 gz-transport**，跟 DDS 無關。
  它佔了每一份擷取的 **96%**。
- `239.255.0.1:14900` 是 RTPS 的 SPDP 多播，每場只有 134–275 個。

原因在 manifest 裡的 dumpcap argv：

```
smoke   : /usr/bin/dumpcap -q -i eth1 -f udp portrange 7400-15200 …
正式批  : /usr/bin/dumpcap -q -i lo   -f udp portrange 7400-15200 …
```

**同機的 ROS 2 流量走 loopback，擷取開在區網介面上。** 漏到 `eth1` 的只有多播
discovery，使用者資料一筆都沒有。

而這是**我自己的工具寫的**：`工具腳本/run_candidate_smoke.sh` 第 18 行的用法
範例就寫著 `bash 工具腳本/run_candidate_smoke.sh eth1`，第 39 行把介面設成
必填並建議 `eth1`。2026-09-02 那一批就照著跑了。

## 4. 我在不知情時做的那個量測，結果本身也說了同一件事

在發現擷取無效之前，我已經用那批資料算完了兩版網路層排他性
（`文件/網路層排他性_候選重判_2026-09-15.json` 與 `…_逐視窗_…json`）。
兩份都保留，但**都作廢**。值得記下來的是它們失敗的方式：

| | 判準 | 結果 |
|---|---|---|
| v1 | 整場 `[min, max]` 與正常完全不重疊 | 六類全部 0——**判準的錯**：每場都有攻擊前後的安靜視窗，min 必然落回正常範圍 |
| v2 | 逐視窗落在正常包絡外 | 六類都「超過雜訊地板」（10–12 個特徵 vs 地板 9） |

v2 看起來像是推翻了原判定。但**再問一個問題就垮了**：這些特徵有沒有專屬性？

```
六類全部都違反的特徵：10 個（共 12 個）
每一類的專屬特徵    ：0、0、0、0、0、0
兩兩 Jaccard 相似度  ：最低 0.83；15 對裡有 4 對完全相同
```

**沒有任何一類有專屬訊號**——包括 `node_churn`。而 `node_churn` 是已經通過
gate、已經進出貨 catalog 的那一支，也是唯一在封包層真的看得出來的
（RTPS 275 對正常 134）。

> **一個連已知可分的類別都分不出來的方法，說「不可分」時沒有資訊量。**

地板 9 也是同一件事的另一面：三場正常互比分別違反 9、2、4 個特徵，而候選是
10–12——**margin 只有 1 到 3 個特徵，n=3**。

## 5. 所以現在知道什麼、不知道什麼

| 類別 | 遙測層判定 | 網路層 | 正確說法 |
|---|---|---|---|
| `verify_flood` | **作廢** | **作廢** | 攻擊從未送達，**未評估** |
| `spdp_flood` | 成立（37 個 participant 真的建了） | **作廢** | 遙測層不可分；封包層**未評估** |
| `baseline_poisoning` | 成立 | 作廢 | 它**設計上就是隱身的**（日誌：「隱身退場」），不可分是**正確答案** |
| `node_name_evasion` | 成立 | 作廢 | 同上（「monitor 從未發過 alert」） |
| `cmd_vel_race` | — | — | 與 `cmd_vel_injection` 同機制，不受影響 |
| `odom_spoof` | `not_evaluated` | 作廢 | 不變 |

所以活狀態表那句「至少 4 類在目前的觀測層結構上做不到」要拆成三種：

1. **2 類是設計上隱身**（`baseline_poisoning`、`node_name_evasion`）——
   判定正確，而且那正是它們的威脅價值。
2. **2 類未評估**（`verify_flood`、`spdp_flood`）——不是做不到，是還沒量到。
3. `cmd_vel_race` 的同機制論述不受本輪影響。

⚠️ 還有一件沒解釋的事：`spdp_flood` 建了 37 個 participant、維持 25 秒，
SPDP 每 5 秒一次的話至少該有一百多則宣告，而 `eth1` 上的 RTPS 多播只比正常多
16 個。擷取無效足以解釋「看不到使用者資料」，**不足以解釋多播也幾乎沒增加**。
這一點留著，重跑時要一起看。

## 6. 修法：兩道 fail-closed，都驗過會咬人

### 6.1 `工具腳本/audit_capture_scope.py`（新增）

只用擷取檔自己回答「這一批看得到同機 DDS 的使用者資料嗎」：

| verdict | 條件 |
|---|---|
| `void_no_unicast` | 單播封包 = 0 |
| `degraded_low_unicast` | 單播佔比 < `--min-unicast-ratio`（預設 0.5） |
| `skipped_not_eligible` | 場次未完成或未進訓練——本來就沒有擷取，不是缺陷 |
| `ok` | 其餘 |

判準是**佔比**不是總封包數，因為多播會把數字撐起來：3,320 個封包看起來很忙，
而它一個單播都沒有。

內建有效性檢查：多播分類器先對一組已知答案自我驗證，錯了就 **exit 3**。
（`test_sanity_check_catches_a_broken_classifier` 用變異測試確認它會咬。）
另外「整批都被跳過」會回 2，因為那等於什麼都沒檢查。

### 6.2 `工具腳本/run_candidate_smoke.sh`（修改）

- 介面預設改成 `lo`，用法範例的 `eth1` 改掉並寫明為什麼。
- 非 `lo` 的介面**直接拒絕**，除非明示
  `SMOKE_ALLOW_NON_LOOPBACK=i_know_this_cannot_see_same_host_dds`。
  實測 `eth1` 與錯誤的 ack 值都回 **exit 2**，而且是在跑任何攻擊之前。
- 批次跑完後自動跑擷取範圍稽核，無效就 **exit 3** 並明說
  「gate 的遙測判定仍然成立，但任何以網路特徵做出的判定都不可引用」。

這條規則其實早就存在——`firewall_lab/formal_preflight.py` 的
`same_host_loopback` 要求 `capture_interface == "lo"`。**正式路徑有，
smoke 路徑沒有套用它。**

攻擊面覆蓋維持 **74%（17／23）**。這一輪沒有新增任何一個可產生資料的類別，

要真的評估，需要用 `lo` 重跑那一批 smoke——**那需要 Jesse 對該次 live 操作的
明確授權**，本輪沒有執行。

## 8. 給下一次的提醒

1. **擷取介面不是一等公民。** 它只埋在 `manifest.result.capture_process.argv`
   裡，沒有任何一步在特徵抽取時檢查它。這次是靠「1,480 筆訊息對 0 個封包」
   這個算術矛盾才撞出來的，而那需要攻擊剛好會回報自己送了幾筆。
   多數攻擊不會。
2. **「比正常多一點」要先問「正常自己差多少」。** 三場正常之間就差 55 個封包
   （3,320 對 3,375），而 `verify_flood` 只比最高的那場多 15 個。
3. **陰性對照要挑「已知會過」的那一個。** 這一輪真正的關鍵不是候選全部沒有
   專屬特徵，是 **`node_churn` 也沒有**——它已經通過 gate 進了出貨 catalog。
