# 歸因驅動封鎖：跨主機執行手冊

> 這一條鏈需要兩台機器同時在場、**需要 Jesse 對該次操作的明確授權**，
> 而且核准片語**必須由人打**。這份手冊的用途是讓那一次成功，而不是第四次。

- 建立：2026-09-25
- 前置工具：`工具腳本/{run_crosshost_identity.sh,run_attribution_driven_block.py}`
- 邊界：`executable_classes` 仍為空、`LIVE_NFT_ACTIVATION_ALLOWED` 仍為 False。
  這是**人核准的驗收**，不是自動封鎖。

---

## 〇、為什麼需要手冊

2026-08-29 那一輪失敗了三次，**全部是時序**：

| 輪 | 原因 |
|---|---|
| 1、2 | 攻擊端根本沒執行 |
| 3 | 防守窗 18:34–18:37，攻擊 18:45 —— **差 7 分 44 秒** |
| 4 | 窗開 600 秒 ✅ |

第三輪一度往錯方向走：攻擊端逐包證明 76 個單播 RTPS 離開了網卡，防守端一個
都沒收到，「方向被丟棄」看起來是唯一解釋。**用擷取檔自己的絕對時間一比就清楚
——零重疊。** 根因是兩個代理靠人轉述，一來一回好幾分鐘，而窗只開 2–3 分鐘。

C2C-049 的結論寫在這裡：**兩邊對齊 UTC 的絕對邊界，不要用相對 sleep。**
80 輪跨 8 小時、偏移恆為 −1、零漂移。

## 一、角色與前提

| | 機器 | 角色 |
|---|---|---|
| 防守 | Pi 5 或筆電 | 觀測者 ＋ 擷取 ＋ 交叉比對 ＋ nftables |
| 攻擊 | 另一台 | N28 wrong-CA participant，**自己生 CA、自己簽** |

攻擊機**沒有**防守方的 keystore、私鑰或 enclave。這是威脅模型的定義，
不是方便起見。

⚠️ 兩台的 ROS 版本不同（Pi：sros2 0.13.6／Fast DDS 2.14.6；
筆電：0.13.5／2.14.5）。跨主機時記住這件事。

⚠️ 同網段 Wi-Fi 的多播實測 0/25 不通，靠 unicast initial peer。換環境要重驗。

## 二、第一步：收一份 v2 歸因報告

在防守端跑既有流程（它**已經**會帶 `--link-layer`，所以輸出就是 v2）：

```bash
bash 工具腳本/run_crosshost_identity.sh
```

攻擊端在**同一個 UTC 邊界**上啟動 N28。兩邊都對齊絕對時間：

```bash
# 兩台都先確認時鐘
date -u

# 對齊到下一個整分鐘再開始,不要互相等對方回話
```

**窗至少開 600 秒。** 2–3 分鐘的窗是那三次失敗的直接原因。

### 收完之後，先驗證證據本身

```bash
python3 工具腳本/run_attribution_driven_block.py \
    --attribution <session>/crosscheck.json \
    --interface <防守端介面> --dry-run \
    --output /tmp/preflight.json
```

`--dry-run` **完全不碰核心**，也不需要 root 與片語。四項全過才往下走：

| 項目 | 不過的意思 |
|---|---|
| `attribution_report_schema_v2` | 報告是 v1 —— 跑的是舊流程 |
| `attribution_verified_and_single_target` | 歸因沒成立，或有多個目標（用 `--target` 指定） |
| `target_independently_reblockable` | 四條判定有一條不成立 |
| `target_is_not_self_or_gateway` | 目標是自己、SSH 對端或閘道 —— **絕對不要繞過** |

⚠️ 歷史報告（2026-08-30 那批）需要先跑
`工具腳本/regenerate_crosscheck_v2.py`，而且它們**只能用來演練**：
第 7、9 項需要攻擊端**當下**在送流量。

## 三、第二步：跑那條鏈

**需要 root，而且需要 Jesse 對該次操作的明確授權。**

```bash
sudo python3 工具腳本/run_attribution_driven_block.py \
    --attribution <session>/crosscheck.json \
    --interface <防守端介面> \
    --authorized-scope 192.168.0.0/24 \
    --protected-source <防守端自己>/32 \
    --output 文件/歸因驅動封鎖_<日期>/report.json
```

程式會等 stdin 上的核准片語。**由人打，這支程式不會替他打。**

`--authorized-scope` 是必填：backend 的範圍檢查不可以是空的，
否則任何位址都在範圍內。

### 攻擊端要配合兩次

程式會印出提示並等核心計數器動：

1. **封鎖生效後** —— 攻擊端持續送流量，計數器必須動（第 7 項）
2. **撤銷之後** —— 攻擊端再送一輪，計數器**必須不動**（第 9 項）

第 9 項與第 7 項成對。只量「元素不見了」不夠——集合空了而規則仍在丟包，
在遙測上看起來會像撤銷成功。

## 四、收尾（每一項都要確認）

```bash
sudo nft list ruleset | grep -A3 sros2_ticket_guard   # 應該什麼都沒有
ip -4 route show default                              # 預設路由還在
```

程式的 `finally` 會移除專用規則集，但**確認過才算收尾**。
票帶 TTL，所以就算行程死掉核心也會自己到期——那是第三道保證，
2026-09-24 在真核心上量過。

## 五、成功長什麼樣

報告的 `summary.chain_demonstrated` 為 `true`，九項全過。
`authorization` 那一段會如實記著：

```
subject_came_from : attribution evidence digest
authority_came_from: human approval phrase on stdin
```

**這兩行不要拿掉。** 歸因報告自己寫著 `authorizes_action: false`——
它說的是「證據支持指認這個位址」，不是「可以對它做什麼」。
對象來自證據，權限來自人。
