# C2C-095 的事前預測判定：負載在爬，而失敗率沒跟著（2026-10-07）

2026-10-02，Enforce 的場次流失從 34.7% 掉到 0/80，但**歸因分不開**——
N37 Observer 的三個開關與機器負載在同一次重啟一起上線。
當時寫下一個可證偽的預測，並明說「要跑滿數小時才可判定，本輪不宣稱答案」：

> **若成因是負載**，Observer 的 `import` 耗時會隨輪次爬升，
> 而 `attack_process` 失敗率跟著回到 >10%。
> **若成因是那三個開關**，失敗率應與執行時長無關地維持 <5%。

今天的 campaign 從 `14:41Z` 跑到 `19:40Z`（約 5 小時、154 場已判定），
三個判準都能從現有產物讀出。**判定的結果是：那個預測的兩半分裂了。**

---

## 一、⚠️ 第一版分析踩進了 C2C-095 自己記過的陷阱

把 154 場混在一起分段，`import` 中位數看起來是：

```
0.55 → 0.51 → 0.52 → 0.51 → 0.68 → 0.62      首段→末段 +23%
```

看起來像時間趨勢。但逐段的模式組成是：

```
第 1–2 段：全 permissive
第 4–6 段：全 enforce
```

**那正是 C2C-095 當時親手指認過的混淆**（它寫「五分位看起來像時間趨勢是混淆——
Q1／Q2 全 permissive、Q4 全 enforce」）。我差一步就用同一個錯誤去判定它自己的預測。

---

## 二、分模式之後，趨勢是真的

| | 首段 → 末段 | 變化 | 失敗率 | `import` p90 / max |
|---|---|---:|---:|---|
| **permissive**（n=68） | 0.62 → 0.51s | **−18%** | **0 / 68** | 1.64 / 3.54s |
| **enforce**（n=66） | 0.49 → **0.67s** | **+35%** | **0 / 66** | 2.69 / **16.62s** |

**permissive 沒有爬升（反而降），enforce 有。** 所以那個 +35% 不是模式混淆的
產物——在同一個模式內部它是真的。

---

## 三、判定

| 預測的那一半 | 結果 |
|---|---|
| 「`import` 耗時隨輪次爬升」 | **成立**（enforce +35%，且非混淆） |
| 「失敗率跟著回到 >10%」 | **否證**（0/154，三的法則上界 **1.9%**） |
| 「失敗率與執行時長無關地維持 <5%」 | **成立** |

⇒ **預測裡那個邏輯連結斷了**：`import` 爬升**不蘊含**失敗率上升。

正確的結論不是「負載不存在」，而是：

> **C2C-090 補上的那三個開關（`start_parameter_services=False`、
> `enable_rosout=False`、關掉 type description）讓 Observer 對負載變化
> 有韌性，而不是讓負載消失。**

兩個互相競爭的假設各對一半：**負載那一半的觀測成立，開關那一半的結論成立。**

⚠️ 這也更正了我在 C2C-090 寫的一句話。當時量到「84% 的時間在 `import`，
不在 `Node()` 的六個 parameter service」，並據此說那三個開關「**不是主因**」。
就「哪一步最慢」而言那句話仍然對；但就「失敗率為什麼歸零」而言，
現在的證據指向它們——因為負載明明在爬，失敗卻沒有發生。

---

## 四、仍然要盯的訊號

```
enforce  import  中位 0.59s   p90 2.69s   max 16.62s
permissive       中位 0.51s   p90 1.64s   max  3.54s
```

**長尾還在**，而且是 enforce 專屬的（max 差 4.7 倍）。這與 C2C-096 量到的
「enforce 專屬的成本在 DDS 呼叫的**尾部**」一致——`Node` 的 p90 enforce 對
permissive 是 3.6×，而與 DDS 無關的 `import` p90 只有 1.1×。

⇒ **目前的 0% 失敗率是「尾部還沒有長到致命」，不是「尾部消失了」。**
若日後 enforce 的 `import` max 繼續往上走，這個判定要重新檢視。

---

## 五、不可宣稱

- **n=154（enforce 66、permissive 68），約 5 小時。** C2C-095 自己記過一個
  教訓：當時 `0/80` 的三的法則上界 3.7% **被下一個 80 場的 5.0% 推翻**。
  這次上界 1.9% 更緊，但同樣的事可以再發生一次。
- 合併重啟後的兩個窗是 **4/234 = 1.7%**（10-03 的 4/80 ＋ 今天的 0/154）。
- `import` 的 +35% 是**三段中位數**的比較，不是迴歸；n 不足以定斜率。
- 這個判定**只涵蓋 `attack_process` 這一種失效**。readiness 逾時那一類在這
  5 小時內是 0 次，但它的成因（C2C-090 記的「為什麼逐輪變慢」）仍然未解。
- **沒有任何程式變更**；這一輪是讀既有產物，出貨設定一個位元未改。
