# IDS 與 SROS2 的協作設計

> 問題：兩層各做各的。SROS2 只決定「憑證過不過」，IDS 只產生「這像攻擊」。
> 中間沒有通道，所以 IDS 偵測到也做不了事——這就是 IDS 變不成 IPS 的原因。

---

## 一、先把現況講準

### 1.1 「完全不通」不正確——已經有一條在運作

| 路徑 | 狀態 | 量測 |
|---|---|---|
| 偵測 → 速度守衛歸零 | **可運作** | 六次量測 0.0187–0.2100 秒 |
| HMAC 驗章 → 丟棄偽造訊息 | **可運作** | 內鬼測試 11 則擋下、0 則接受 |
| 偵測 → 封鎖來源 | **不通** | `executable_classes = []` |

所以缺的不是「任何阻止能力」，是**網路／DDS 層的阻止能力**。

### 1.2 SROS2 的限制是「靜態」，不是「不夠嚴」

SROS2 的判定依據是憑證與 permissions 檔，**在執行前就決定好**。它無法對行為
反應。N29 內鬼實驗證明了這一點：**持合法憑證的攻擊者每次都通過 SROS2**，
擋下他的是 HMAC，不是 SROS2。

所以 IDS 要補的不是「SROS2 擋不住外人」，是**「SROS2 擋不住行為變壞的自己人」**。

### 1.3 IDS 的限制是「看不到身份」

IDS 的世界是 ROS topic 與遙測事件，**裡面沒有任何 DDS 身份**。
它可以說「這個視窗像攻擊」，但說不出「是哪一個 participant 幹的」。

**這才是最根本的斷點**：就算給 IDS 一個封鎖按鈕，它也填不出要封鎖誰。

## 二、可用的阻斷原語，以及它們的代價

| 手段 | 依據 | 可逆 | 需要 root | 需要 IP 歸因 | 現況 |
|---|---|---|---|---|---|
| 應用層丟棄 | GUID／來源 | ✅ | 否 | 否 | 要自己做 |
| `ignore_participant()` | GUID | ❌ **不可逆** | 否 | **否** | Fast DDS 內建 |
| `ignore_topic/publication/subscription` | — | — | — | — | **`RETCODE_UNSUPPORTED`** |
| SROS2 permissions 重簽 | 憑證 | ✅ | 否 | 否 | 無熱重載 |
| nftables | IP | ✅ | **是** | **是** | IP 歸因 0／1,101 |

Fast DDS 2.14.5 的 header 原文：

```
Locally ignore a remote domain participant.
@note This action is not reversible.
```

`ignore_participant` 是唯一**不需要 IP 歸因也不需要 root** 的 DDS 層阻斷，
但它不可逆——而本專題的題目是「**可恢復**安全回應」。

**這本身是一個可以寫進論文的發現：DDS 標準提供的阻斷原語不滿足可恢復性要求。**

---

## 三、設計原則：**動作的不可逆程度，必須配得上證據的確定程度**

這是整個接法的核心，也是它不只是「把兩條線接起來」的原因。

> 不可逆的動作，只能由**不可能誤判**的證據觸發；
> 可能誤判的證據，只能觸發**可撤銷**的動作。

套到這兩層上，剛好對得起來：

| 證據來源 | 性質 | 可否誤判 | 允許的動作 |
|---|---|---|---|
| SROS2 認證失敗 | 密碼學 | **不可能**——憑證鏈要嘛通要嘛不通 | 可以用不可逆的 `ignore_participant` |
| IDS 行為偵測 | 統計 | **可能**（處女 holdout recall 0.0273） | 只能用可撤銷的應用層丟棄 |

這不是折衷，是**兩層各自的證據性質決定了它們該有多大的權力**。

而且這解釋了一件原本看起來矛盾的事：`ignore_participant` 的不可逆性，
**對認證失敗的對象反而不是問題**——因為那個判斷不會錯。

## 四、三層回應鏈

```
證據強度                動作                        可逆   延遲
─────────────────────────────────────────────────────────────
密碼學：認證失敗    →   DDS ignore_participant      ❌     即時
行為：IDS 高信心    →   應用層黑名單（丟棄訊息）    ✅     毫秒
網路：持續濫用      →   nftables 丟封包             ✅     即時
                                                    （需 root ＋ IP 歸因）
```

**升級規則**：只能由下往上，而且每一層都要有各自的證據。
IDS 的判定**永遠不能**直接觸發第一層——那會讓一個統計模型擁有不可逆的權力。

## 五、要接起來，缺的是什麼

### 5.1 Half A：讓 IDS 看得到身份

IDS 現在完全不知道 GUID 的存在。

**接法**：security observer 已經拿得到每個 participant 的 GUID、認證判定、
subject 與 endpoint（2026-08-26 實測）。把這些事件**發進既有的遙測通道**
（`SROS2_FIREWALL_TELEMETRY_SOCKET`，Unix datagram ＋ JSON），
IDS 就會在同一條串流裡看到它們，與 HMAC 結果、guard 狀態並列。

不需要新的 IPC，不需要改 IDS 的資料來源——**重用既有基礎設施**。

需要的改動：

1. `firewall_lab/live_telemetry_collector.py` 的 `EVENT_DETAIL_KEYS`
   新增 `dds_identity` 事件類型
2. observer 發送該事件

### 5.2 Half B：讓 IDS 有動作通道

三層各自需要：

| 層 | 需要 |
|---|---|
| 應用層黑名單 | monitor／guard 端維護一個可撤銷的 GUID 黑名單 |
| DDS ignore | observer 端在認證失敗時呼叫（**只由密碼學證據觸發**） |
| nftables | 跨主機 ＋ root ＋ IP 歸因，**目前全部缺** |

### 5.3 訂閱端拿不拿得到發送者 GUID（2026-08-26 已實測，更正初版）

本文初版寫「rclcpp/rclpy 沒有把 DDS 層的來源身份傳上來」。**那是未經查證的
臆測，而且是錯的。** 實測結果分兩半：

| 層 | `publisher_gid` | 實測 |
|---|---|---|
| `rmw_message_info_t`（C） | 有欄位，16 bytes | — |
| **rclpy** | **沒有露出** | message_info 只有 `publication_sequence_number`、`received_timestamp`、`reception_sequence_number`、`source_timestamp` 四個鍵 |
| **rclcpp** | **有，而且 rmw_fastrtps 確實有填** | `publisher_gid=010f667d5c038e040000000000001403 populated=yes impl=rmw_fastrtps_cpp` |

驗證工具：`firewall_lab/security_observer/gid_probe.cpp`
（只訂閱、不發布，不影響受測系統）。

**所以第二層是做得成的，但有一個具體代價：必須用 C++ 寫。**

現況是 ROS 這一側全部是 Python——`monitor_node.py`、`velocity_guard_node.py`
都是。要讓「可撤銷的黑名單」成立，選項是：

| 作法 | 代價 |
|---|---|
| 把過濾／守衛改成 C++ | 要重寫一個既有元件，但取得完整 GUID |
| 擴充 rclpy 讓它露出 `publisher_gid` | 動到 ROS 本體，超出專題範圍 |
| 由 C++ 觀測者做「過濾轉送」 | 改變資料路徑並增加延遲，且觀測者不再是唯讀 |

第一個最實際。速度守衛本來就是**唯一已經在做可撤銷阻止**的元件
（latch／release，六次量測 0.0187–0.2100 秒），把它改成 C++ 之後就能
依 publisher GUID 丟棄訊息——那正是第二層需要的東西。

### 5.4 一個附帶觀察（尚未查證，不可當結論）

實測到的 GUID prefix 有兩種形態：

- 未成功啟用安全的 participant：`010f667d…`（兩次不同執行都相同）
- 已啟用安全的 participant：`a25a104e…`／`a03a1414…`／`d8b719e7…`／`b604d120…`
  （彼此不同）

**可能**是 Fast DDS 在安全模式下用隨機前綴以避免洩漏主機身份。若屬實，
這對歸因是雙面的：好處是攻擊者無法從 GUID 推出你的主機，壞處是**你也無法
從 GUID 推出攻擊者的主機**，來源歸因只能靠封包層的實際 IP。

**這只是觀察，成因未查證，不可寫成結論。**

## 七、這個設計對論文的意義

原本的貢獻是「SROS2 預防 ＋ AI 偵測」兩件事並列。加上這個接法之後，
可以講成一個更完整的論述：

> 預防層（SROS2）的判斷是密碼學的、確定的，但它是靜態的，
> 擋不住行為變壞的合法節點；
> 偵測層（AI）能看行為，但它的判斷是統計的、會錯。
> 因此**兩層的權力必須依證據性質分配**：確定的證據可以觸發不可逆的動作，
> 不確定的證據只能觸發可撤銷的動作。
> 本研究實作了這個分層回應鏈，並指出 DDS 標準的阻斷原語
> （`ignore_participant`）因不可逆而不足以支撐可恢復的回應。
