# 300 場重跑：執行手冊與可否證預測

日期：2026-08-20
狀態：**計畫與檢核器已就緒並自我驗證**；執行需要 Jesse 授權 live。

---

## 一、為什麼是 300 場而不是 1,100 場

正式資料集有三個 scenario 的**攻擊專屬證據是空的**，成因是兩個已修好的 bug；
其餘 800 場不受影響，重跑它們沒有意義。

| scenario | 場次 | 失效原因 | 修正 |
|---|---:|---|---|
| `heartbeat_replay` | 100 | N1 是 BEST_EFFORT publisher 對 RELIABLE subscriber，DDS 直接不投遞 | QoS 改為 RELIABLE ＋ TRANSIENT_LOCAL |
| `parameter_tamper` | 100 | `parameter_call` hook 掛在 rcl read-only 拒絕之下 | hook 移到服務層 |
| `parameter_flood` | 100 | `get_parameters` 當時沒有任何 hook | 六個 parameter service 全部包裝 |

這些場次對**二元偵測仍然有效**（流量層訊號是真的），但對**攻擊識別**等於沒有
內容——而 `replay`（0.375）與 `parameter_tamper`（0.429）正好是識別率最差的兩類。

計畫沿用原本的 `seed`、`scenario_id`、`security_mode` 與 `expected_action`，
所以這是**受控比較**：唯一的變因是那兩個修正，不是重新抽樣。

## 二、三個可否證的預測

**這是重跑的重點。** 不是「再收點資料看看」，而是一個假設寫在前面、跑完就能
判定成立或推翻的實驗。

| # | 預測 | 若被推翻代表 |
|---|---|---|
| 1 | `parameter_tamper`／`parameter_flood` 的 Permissive 場次 `parameter_call` > 0 | 修正沒生效，或攻擊沒打到節點 |
| 2 | `heartbeat_replay` 的 Permissive 場次出現 `nonce_reuse_or_capacity` | 重放仍未送達，或被時間戳先擋 |
| 3 | **（對照組）** `sros2_deny` 維持 0 | 環境有其他改變，前兩項的因果不成立 |

第 3 項沒有被修，所以應該維持不變。**若它也「改善」了，代表變的是別的東西**，
那前兩項就不能歸功於修正——這道對照是用來防止把環境漂移誤讀成修正生效。

### 檢核器已在現有資料上自我驗證

拿**未重跑**的 1,100 場跑一次，結果正是目前的已知狀態：

```
  1. parameter_call > 0（Permissive）: 0  ❌ 被推翻
  2. nonce_reuse_or_capacity > 0（Permissive）: 0  ❌ 被推翻
  3. sros2_deny 維持 0（對照組）: 0  ✅ 成立
```

這證明檢核器**會咬人**，不是只會蓋章。重跑後前兩項應翻成 ✅。

## 三、執行步驟

### 1. 產生計畫（已完成，可重跑）

```bash
python3 工具腳本/build_rerun_plan.py
```

輸出 `firewall_lab/campaign_rerun_300.json`，並用正式載入器
`load_campaign_plan` 驗證格式：300 場、Permissive 150／Enforce 150。

### 2. 記錄重跑前的基線

```bash
python3 工具腳本/verify_rerun_predictions.py --dataset firewall_lab/dataset_live
```

把輸出存起來——之後要用 `--baseline` 做前後對照。

### 3. 執行（**需要 Jesse 授權 live**）

⚠️ **三個前置條件，缺一場場都會失敗**（2026-08-21 實跑時逐一踩到）：

| 前置 | 症狀 | 原因 |
|---|---|---|
| `FIREWALL_LIVE_RUNTIME` 要在 Linux fs | `OSError: [Errno 95] Operation not supported` | Unix datagram socket 不能建在 Windows 9p 掛載上 |
| **ROS stack 必須先自己起來** | `not_eligible:runtime_telemetry`，`telemetry_events=0` | **orchestrator 不會啟動 stack**，它只跟隨 stack log、起 collector 與攻擊行程 |
| 攻擊腳本收尾要有硬上限 | `not_eligible:attack_process`，rc=-15／-9 | 收尾與 orchestrator 的時間預算競速 |

第二點最容易誤導：collector 會正常建 socket、攻擊會正常執行、rc=0，看起來一切
順利，但遙測是空的。原本 1,100 場是在 stack 已經在跑的情況下執行的，這一步當時
沒有寫進手冊。

實跑用的包裝腳本（自己帶起 stack、等 readiness 再開始）：

```bash
export FIREWALL_LIVE_RUNTIME=/home/jesse/.local/share/sros2-firewall/live_runtime
bash firewall_lab/live_stack.sh start <mode>
# 等 log 出現 "本機 Permissive readiness 通過" 或 "SROS2 Enforce readiness 通過"
```

一次一個 security mode，外部 stack 才不會漂移：

```bash
python3 -m firewall_lab.campaign run \
  --plan firewall_lab/campaign_rerun_300.json \
  --dataset <重跑輸出目錄> \
  --security-mode permissive \
  --capture-interface <介面> \
  --confirm-isolated-lab
```

Enforce 同上，改 `--security-mode enforce`。

⚠️ `--capture-interface` 是必要的：沒有封包擷取的場次不具訓練資格。

### 4. 檢核預測

```bash
python3 工具腳本/verify_rerun_predictions.py \
  --dataset <重跑輸出目錄> \
  --baseline firewall_lab/dataset_live
```

### 5. 完整性稽核後才進訓練

重跑資料一樣要過 `verify_manifest_evidence()` 的 fail-closed 檢查
（大小一律檢查，hash 用 `--verify-evidence-hashes`）。

## 四、預期成本與風險

| 項目 | 估計 |
|---|---|
| 執行時間 | 約 4–5 小時（300 場，一次一個 mode） |
| 磁碟 | 每場約 17 MB（依現有 19,204 artifact／1,101 場推估），總計約 5 GB |
| 風險 | 低：不觸碰原始 `dataset_live`，輸出到新目錄 |

**不要覆寫原始資料集。** 舊的 300 場是「bug 存在時長什麼樣」的唯一實證，
也是前後對照的基準。

### N1 收尾為什麼要設硬上限

Enforce 下攻擊者沒有憑證，N1 的 `RELIABLE + TRANSIENT_LOCAL` publisher **永遠配
不到訂閱者**，`destroy_node()` 可能卡在等待樣本處置。實測 31 場 enforce
`heartbeat_replay`：**rc=0 有 28 場（約 40.2 秒）、SIGTERM 2 場、SIGKILL 1 場**。
一場失敗就讓整批 campaign 中止（fail-closed），而 `--retry-failed` 會先跑那一場，
於是永遠卡在同一個地方。

修法刻意**不縮短攻擊視窗**：攻擊仍跑滿 40 秒，只是清理改在背景執行緒、最多等
2 秒就 `os._exit(0)`。縮短攻擊時間也能避開，但會讓後半場次與前半的視窗長度不
一致，在資料裡留下一個不必要的變因。

> 攻擊此時已經結束，**清理不該決定一場資料算不算數**。
