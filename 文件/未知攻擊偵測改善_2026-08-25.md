# 未知攻擊偵測改善（2026-08-25）

本輪目標：把 open-set recall 從 0.5499 拉起來。結果是**一個成功、一個上限、一個代價**，
三件事都必須一起講，只講第一件會誤導。

所有實驗離線完成：未啟動 ROS runtime、未產生攻擊流量、未使用 `sudo`。
完整測試 **615 passed、0 failed**。

---

## 一、先講結論

| 主張 | 證據 | 成立範圍 |
|---|---|---|
| 現行 OOD 頭接近亂猜 | leave-one-class-out macro AUC **0.5381**，六類中四類 < 0.5 | Permissive，訓練列 |
| 換成距離式評分大幅改善 OOD 頭 | 可及列 recall **0.6134 → 0.9891** | Permissive，原 holdout |
| 整個模型 open-set 隨之上升 | **0.5499 → 0.8850** | 同上，**該 holdout 第二次使用** |
| 但改善**不會轉移**到二元閘門漏掉的類別 | 全新 holdout：0.0182 → 0.0410 | Permissive，處女 holdout |
| 代價是已知攻擊識別下降 | 認對 **0.7019 → 0.5581** | Permissive，validation |
| Enforce 完全無效 | 三種評分器全新 holdout 上 0.38–0.59 | Enforce |

**一句話**：OOD 頭本身修好了，但整體 open-set recall 的上限是**二元閘門**，
而且改善要用已知攻擊的識別率去換。是否值得，是部署姿態的取捨，不是技術上的最佳解。

---

## 二、現行 OOD 頭為什麼接近亂猜

### 2.1 門檻的定法本身就沒有未知參與

`hierarchical_training.py:1176-1192`：IsolationForest 擬合在**所有已知攻擊**的訓練列上，
門檻取那些列分數的 `maximum_known_attack_ood_fpr` 分位數。也就是說門檻**只由已知攻擊
長什麼樣決定**。而那個 budget 被硬性限制在 `(0, 0.10]`，實測 0.05 → 0.10 只讓門檻從
−0.5581 動到 −0.5296；同時 family／leaf 的 coverage 是 1.000，階層棄權那條路從不觸發。
三條通往「未知」的路，實際只有一條在跑。

### 2.2 用 leave-one-class-out 當模擬未知量出真正的取捨曲線

對每個已知攻擊類別 c：把偵測器重新擬合在「已知攻擊減去 c」上，用它評 c 的列
（模擬未知）與其餘已知列（已知）。**只用監督訓練列**，holdout 完全不參與，
所以不污染後續評估。已知分數一律 out-of-fold（`GroupKFold`，同一場不跨 fold），
否則質心由擬合列自己定義、門檻會偏低、未知拒絕率被灌水。

工具：`工具腳本/calibrate_ood_threshold.py`

Permissive 逐類結果：

| 類別 | 模擬未知中位數 | 已知中位數 | AUC |
|---|---:|---:|---:|
| `replay` | −0.5664 | −0.4460 | 0.9726 |
| `parameter_tamper` | −0.5286 | −0.4327 | 0.8937 |
| `replay_dos` | −0.4489 | −0.4598 | 0.4361 |
| `message_dos` | −0.4254 | −0.4604 | 0.3207 |
| `command_injection` | −0.4379 | −0.4560 | 0.3123 |
| `identity_abuse` | −0.4306 | −0.4605 | 0.2934 |
| **macro** | | | **0.5381** |

**六類中有四類 AUC 低於 0.5**——被抽掉時它們看起來**比已知攻擊還正常**。
對這四類，加大 budget 沒有任何用處。

### 2.3 `message_dos` 推翻了「證據排他性」的簡單解釋

`message_dos` 的 closed-set test recall 是 **0.970**，因為它有專屬的
`oversized_message_ratio`。但它的 OOD AUC 只有 **0.3207**。

所以瓶頸不是「沒有專屬證據」，而是**評分方式**：IsolationForest 是密度式的，
只有比已知攻擊**更極端**的樣本才會被判成異常。`replay` 與 `parameter_tamper` 之所以
被抓到，是因為它們在重跑後有極端的特徵值（`parameter_call` 210,614 次）；
`message_dos` 大多數視窗的 `oversized_message_ratio` 是零，落在中央密集區。

**安全上這是最糟的失效方向——安靜的新型攻擊看不見。**

### 2.4 一個附帶發現：平淡的已知類別會遮蔽平淡的未知類別

把 `command_injection` 與 `identity_abuse` 也移出擬合集之後，同一個 IsolationForest
對 `message_dos` 的 AUC 從 0.3207 跳到 **0.8506**。已知攻擊的流形只要涵蓋了那塊
「平淡」區域，落在同一區的新型攻擊就會被吞掉。已知類別越多樣，open-set 越難。

## 三、換評分器：兩場對抗性驗證

工具：`工具腳本/compare_ood_scorers.py`

三種候選，都只需要已知類別的標籤，不需要未知樣本，不違反 open-set 設定：

- `isolation_forest`：現行做法，密度式。
- `max_softmax`：1 − 已知類別的最大預測機率（OOD 標準基線 MSP）。
- `mahalanobis`：到最近的已知類別中心的馬氏距離，共用組內共變異。

### 3.1 選擇規則先寫下來再跑

**規則：取 LOO 中該候選表現最差的兩類當全新 holdout。** 這兩類完全退出擬合與
LOO 選擇，是最不利於它的情況。兩個候選各做一次，避免只針對其中一個。

- 測試 A（針對 mahalanobis 最差的 `identity_abuse` 0.6656、`command_injection` 0.7223）
- 測試 B（針對 max_softmax 最差的 `parameter_tamper` 0.6720、`replay_dos` 0.8830）

### 3.2 結果

| 評分器 | 測試 A macro AUC | 測試 B macro AUC | **最差情況** |
|---|---:|---:|---:|
| isolation_forest | 0.4316 | 0.6834 | 0.4316 |
| max_softmax | **0.9950** | 0.6900 | 0.6900 |
| **mahalanobis** | 0.8781 | **0.8935** | **0.8781** |

max_softmax 在測試 A 幾乎完美（recall@0.05 = 1.0000），但被針對時從 0.995 崩到 0.690。
**Mahalanobis 是唯一兩場都守住 0.87 以上的。** 安全系統該看的是最差情況，所以選它。

成本對齊之下（同一個已知誤否決 budget），Mahalanobis 是現行做法的 3–6 倍：

| budget | 測試 A：IF → Maha | 測試 B：IF → Maha |
|---|---|---|
| 0.05 | 0.0195 → **0.3290** | 0.1199 → **0.6972** |
| 0.10 | 0.0391 → **0.4593** | 0.2988 → **0.7337** |
| 0.20 | 0.1401 → **0.8567** | 0.6565 → **0.8699** |

### 3.3 兩種評分器的失效方向互補

- IsolationForest 抓得到**極端**的未知（`parameter_tamper`、`replay`），抓不到平淡的。
- max_softmax 抓得到**模稜兩可**的未知，抓不到極端的——樹模型對訓練範圍外的值
  仍然會自信地分到某一枝（`parameter_tamper` AUC 僅 0.6000）。
- Mahalanobis 對兩者都還可以：距離同時因「極端」與「偏離每個中心」而增加。

合併兩者是合理的後續方向，但那是在看過上表之後才想到的，需要自己的乾淨驗證，
本輪不宣稱。

## 四、接進訓練線與整個模型的數字

`hierarchical_model.py` 對偵測器只做 duck-typing 檢查（要有 `score_samples`，
且**越低越異常**），所以新增一個包裝類別就能接上，**模型端一行都不用改**。

- 新增 `firewall_lab/ood_scorers.py`：`MahalanobisNoveltyDetector`。
- `hierarchical_training.py` 新增 `--attack-ood-scorer {isolation_forest,mahalanobis}`，
  **預設維持 isolation_forest**，讓既有 artifact 逐位可重現；改動必須明示。
- 新增 `tests/test_ood_scorers.py`，9 個測試鎖住方向、奇異共變異、缺標籤、
  單一類別、未擬合、特徵寬度、以及「預設沒有被改掉」。

控制良好：binary／family／leaf 三層的門檻與指標**逐位相同**（threshold 0.3773／
0.5664／0.9481、accepted_precision 0.9792），差異完全隔離在 OOD 頭。

### 4.1 原 holdout（`sensor_spoof`、`service_dos`）

| | IsolationForest | Mahalanobis |
|---|---:|---:|
| **整個模型 open-set recall** | 0.5499 | **0.8850** |
| normal 誤判為 unknown | 0.0116 | 0.0299 |
| 自信誤填成 `parameter_tamper` | **231** | **0** |
| 二元閘門 recall（上限） | 0.8920 | 0.8920 |
| OOD 在可及列的 recall | 0.6134 | **0.9891** |

⚠️ **這是該 holdout 的第二次使用。** 評分器完全用訓練列選出（LOO ＋ 兩場對抗性
驗證，全部是訓練列），holdout 從未參與選擇。但我知道它上一次的失敗形態是
「自信誤填成已知類別」，**搜尋方向受了那個知識影響**。這是弱形式的污染，
必須揭露；因此下一節才是可引用的乾淨數字。

### 4.2 處女 holdout（`command_injection`、`identity_abuse`）

兩種評分器各訓練一次，其餘設定完全相同。這組 holdout 從未在整個模型層級評估過。

| | IsolationForest | Mahalanobis |
|---|---:|---:|
| 整個模型 open-set recall | 0.0182 | 0.0410 |
| **二元閘門 recall（上限）** | **0.2620** | **0.2620** |
| OOD 在可及列的 recall | — | 0.1565 |

**改善沒有轉移。** 439 列裡有 **324 列（73.8%）被二元閘門判成 `normal`**，
OOD 頭連看都沒看到。工具：`工具腳本/diagnose_openset_paths.py`。

逐類拆解更清楚：

```
command_injection  binary_missed 218 / 222   ← 幾乎全部漏在閘門
identity_abuse     binary_missed 106, ood_missed 96, flagged 15
```

還有一個結構性的不利：**通過二元閘門的列，正是最像已知攻擊的那些列**，
所以它們對 OOD 頭來說也最難。兩個階段互相拉扯。

## 五、代價：已知攻擊識別下降

已知攻擊的非訓練列（n=577，Permissive）：

| | IsolationForest | Mahalanobis |
|---|---:|---:|
| 誤否決為未知 | 0.1213 | **0.2652** |
| 認對 | **0.7019** | 0.5581 |
| 認錯成別類 | 0.1768 | 0.1768 |

宣告的 budget 是 0.05，**實際落在 0.121 與 0.265——兩者都超標，Mahalanobis 超得更多**。
門檻取自 threshold_validation 列，跨場次轉移不良。

**Mahalanobis 分得比較開，但校準得比較差。** 這是一個獨立於評分能力的缺陷，
應該用 conformal 或 session-level 的校準去修，而不是靠調 budget。

## 六、Enforce：三種評分器都沒用

全新 holdout（`command_injection`、`identity_abuse`）：

| 評分器 | macro AUC |
|---|---:|
| isolation_forest | 0.3802 |
| max_softmax | 0.5867 |
| mahalanobis | 0.4276 |

六類 LOO 也一樣（0.52–0.55）。原因與識別率低是同一個：SROS2 在 handshake 就擋掉
攻擊，應用層證據根本不存在，只剩流量形狀。**分得出「有攻擊」（binary PR-AUC 0.9774），
分不出「哪一種」，也就分不出「沒見過的那種」。** 這不是評分器的問題。

## 七、誠實的進度陳述

未知攻擊這一項的數字現在是**依 holdout 類別而定的區間**，不是單一值：

- `sensor_spoof`／`service_dos`：**0.8850**（二元閘門 recall 0.8920）
- `command_injection`／`identity_abuse`：**0.0410**（二元閘門 recall 0.2620）

0.70 的門檻在前者達成、在後者遠遠未達。**寫報告時不可以只引前者。**

真正被量出來的是一個更有用的結論：**整個模型的 open-set recall 上限是二元閘門
對未見類別的 recall，而那個 recall 由該類別有沒有專屬證據通道決定。**
換 OOD 評分器解決了閘門之後的那一段，解決不了閘門本身。

## 八、下一步（依價值排序，都不需要 live 授權）

1. **二元閘門才是瓶頸。** 目前它為了 normal FPR ≤ 0.02 而收得很緊
   （threshold 0.3773、normal_fpr 0.0157）。對未見類別放寬閘門、再靠 OOD 頭
   把已知類別擋回去，是可以用 LOO 協定離線評估的。
2. **修 Mahalanobis 的校準**：宣告 0.05、實際 0.265。用 conformal 或 session-level
   分位數重新定門檻，而不是調 budget。
3. **合併互補的兩種評分**（密度 ＋ 信心）。需要自己的乾淨 holdout。
4. `command_injection` 與 `identity_abuse` 需要封包層 RTPS 觀測才可能有專屬證據；
   那是新的觀測層，不是調參能解決的。
