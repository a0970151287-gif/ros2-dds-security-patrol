# 封印接到 open-set 那一半（2026-10-03，經 Jesse 批准）

C2C-097 查到的缺口：識別那一半有一條不可分割的路徑，而未知攻擊那一半的
一次性保護**只有**「輸出檔已存在就拒絕覆寫」——換一個 `--output` 路徑就能再跑
一次。而那不是假設性的：待辦自己寫著「現有的已用第三次，數字不可引用」。

> **強機制（封印）存在，而它從來沒有被接到這一半。** 這一輪接上了。

時序是這一項被排在最前面的理由：campaign 約 3 天後產出新資料，而**封印必須在
那批資料被切分之前就位**，否則新 holdout 會以同樣的方式被燒掉。其他待決項
什麼時候決定都一樣，只有這一項等待的代價收不回來。

## 一、⚠️ 更正我自己給 Jesse 的子建議

我建議「把 holdout 切半、各自封印」，並說代價是解析度。**量完之後兩個都不對**：

| 表 | `split == test` 場次 | novelty holdout 場次 | **交集** |
|---|---:|---:|---:|
| refresh permissive | 45 | 40 | **6** |
| refresh enforce | 51 | 40 | **6** |
| merged permissive | 84 | 100 | **16** |

`novelty_role` 與 `split` 是**正交**的——那兩個留出類別散在 train／validation／
test 三處。所以：

- **不是**同一批場次 ⇒ 不需要「一個封印開兩次」那種鬆綁；
- **也不是**不相交的兩半 ⇒ 「切半」這個說法本身就不成立。

正確的結構是**一個封印綁一個 scope**：

```
seal_holdout.py --scope test              → split == test（識別那一半，預設）
seal_holdout.py --scope novelty_holdout   → novelty_role == novelty_holdout_candidate
```

兩個封印因此並存而互不擋住對方，而「只開一次」這個性質**完全不必被鬆綁**，
解析度也**沒有任何損失**。

⚠️ 缺 `scope` 欄的封印一律當成 `test`——那不是「未知就猜」，那是 **provenance**：
這個欄位 2026-10-03 才加，之前的封印在定義上就只封 test。而**不認識的** scope
一律**拒絕**，絕不退回預設（兩條各有一個測試，釘住這個差別）。

## 二、⚠️ 另一個結構更正：兩半用不同表述是設計如此

C2C-097 我寫「選定的表述與既有的驗收機制長在兩棵不同的樹上」，語氣上像是缺陷。
查下去**不是**：

```
max_softmax 與 k_of_n_k2 是在 evaluate_unknown_at_full_resolution.py 上量出來的,
而它走 load_codex_module() ⇒ **Codex 的 parallel-gate 線**,不是 session_aggregate。
```

所以註冊的 OOD 設定**本來就屬於** hierarchical 線。兩半用不同表述是一致的，
不是不一致：

| | 表述 | 設定來源 |
|---|---|---|
| 識別（多類） | `session_aggregate` ＋ RF | 2026-09-16 選型 |
| 未知攻擊（open-set） | hierarchical parallel gate | 2026-09-24／25 的 `max_softmax` ＋ k=2 |

⇒ **缺口比我說的更窄更乾淨：只缺封印。**

```
排除擬合   → 用**場次**（整場都不准進 fit／threshold／reference）
評估 recall → 用**類別**（只有留出類別的攻擊列才是「未知攻擊」）
```

而 `evaluate_openset_holdout.py` 一直都是按 label 選的——我沒有照它。
