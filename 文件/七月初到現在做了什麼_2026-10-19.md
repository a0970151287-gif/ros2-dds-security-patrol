## 〇、數字從哪來

這個專題有一份叫 `CLAUDE.md` 的交接文件，裡面逐則記錄了每一輪做了什麼。
但**它的紀錄從 2026-08-11 才開始**——也就是 7 月初到 8 月中那五週完全沒有紀錄。

所以這份文件的時間軸、規模與節奏**全部從 git 重新量**，不是去抄那份交接文件：

| 要知道的事 | 怎麼量的 |
|---|---|
| 每一天有幾個 commit | `git log --format='%ad' --date=short` 逐日計數 |
| 某一天的 repo 長什麼樣 | `git ls-tree -r <那個 commit> --name-only` 逐目錄數檔案 |
| 總共改了多少 | `git diff --shortstat`（起點對下面釘住的那個 commit） |
| 7 月那五個 commit 做了什麼 | 逐字讀它們的 commit 訊息 |
| 各組件的驗收數字 | 引用 `CLAUDE.md` 的狀態表與各份 JSON 產物 |

⭐ **規模的量測刻意釘在 commit `acaa253`**（2026-10-19，這份回顧開始寫之前最後一個
實質工作的 commit）。理由很簡單：**一份回顧不該把自己算進規模裡**——
這份文件本身與它的簡報也是 commit，如果量到 HEAD，每改寫一次數字就會變。
釘住之後任何人都可以重跑並得到一樣的值。

**標註規則**：下文凡是寫「量到」的，都有產物或 git 指令可以重跑；
凡是寫「推算」的，是從已量到的數字算出來的，我會說清楚算式。

## 一、一句話版本：程式沒變，變的是「怎麼證明它有效」

> **會擋攻擊的程式，七月初就差不多寫完了。
> 之後三個半月，全部花在「證明它真的有效」上面——而那比寫它難得多。**

這句話不是感想，是可以直接從 git 看出來的。把起點（`fa6b58c`，2026-07-04）
跟 `acaa253`（2026-10-19）的檔案數並排：

| 目錄 | 它放什麼 | `fa6b58c` | `acaa253` | 倍數 |
|---|---|---:|---:|---:|
| `src/` | **防守端的 ROS 2 節點**（真正在擋攻擊的程式） | 37 | 45 | **1.2×** |
| `展示指令/` | 啟動腳本 | 20 | 23 | 1.15× |
| `紅隊測試/PoC腳本/` | 攻擊腳本 | 25 | 35 | 1.4× |
| `firewall_lab/` | **資料工廠、特徵、決策、證據治理** | **0** | **84** | — |
| `工具腳本/` | 量測與稽核工具 | 3 | 90 | 30× |
| `tests/` | 測試檔 | 2 | 105 | 52.5× |
| `文件/` | 報告、帳本、實驗紀錄 | 14 | 567 | 40.5× |
| **全 repo** | | **150** | **1,035** | **6.9×** |

測試的**項目數**從 **24 個長到 1,767 個**。

⭐ **真正會擋攻擊的那部分只長了 1.2 倍，而驗證它的那部分長了 30 到 52 倍。**

整段期間的總變更量（量到）：

```
git diff --shortstat fa6b58c acaa253
  976 files changed, 342,406 insertions(+), 1,500 deletions(-)
```

**刪除只有 1,500 行。** 也就是說這不是「寫錯再重寫」，是一直往外長——
長出來的東西幾乎全部是「怎麼知道它有效」。

那個從 0 變成 84 個檔案的 `firewall_lab/`，白話說就是一座**實驗工廠**：
它負責排程一場一場的攻防、錄下每一場的所有證據、算出特徵、
檢查證據完不完整、以及在證據不完整時**拒絕讓那一場進訓練**。
它本身一行都不在機器人上跑。

## 二、時間實際上花在哪

先看節奏。每個月新增的 commit 數（量到）：

| 月份 | 新 commit | 在幹嘛 |
|---|---:|---|
| 7 月 | **5** | 把安全設定做對，然後**等機器跑資料** |
| 8 月 | **131** | 建資料工廠、跑 1,100 場、修兩個收集器 bug |
| 9 月 | **103** | 模型選型、修量測工具、攻擊面擴充 |
| 10 月 | **80** | 修工程問題、跑完 3,837 場、驗收與理解 |

這 107 天**新增 318 個 commit**（累計從 31 到 349）。
逐月那四個數字相加是 319，差的那一個是起點 `fa6b58c` 自己——它也在 7 月那 5 個裡面。

⚠️ **這一項更正了本文前一版**：前一版寫「新增 319（累計 35 → 354）」，
而重跑 `git rev-list --count` 量到的是 **318（31 → 349）**。
前一版那兩個累計值沒有對帳成功，這一版以重跑的值為準。

### 2.1 四個桶，依它們真正吃掉的東西排序

**① 做假攻擊、收資料——吃機器時間，不吃人的時間**

這是四個桶裡**佔掉最多日曆天**的一個，而它幾乎不需要人在旁邊。
做法是：讓程式自己扮演攻擊者去打自己的機器人，每一場錄下所有證據。

四批資料加起來 **6,154 場**（1,101 ＋ 306 ＋ 910 ＋ 3,837，四個數字都量到，
這個和是算術加總）。光是最後那批 3,837 場，用量到的 37–39 場／小時**推算**
就是**約 100 小時（4 天多）**的純執行時間，而且必須連續跑。

⚠️ 6,154 是**執行過的場次數，不是獨立樣本數**——那 306 場是刻意的受控重跑，
在特徵層**替換掉**原本 1,100 場裡對應的 300 場，不是額外加上去的。
拿它當「機器花了多少時間」是對的，拿它當樣本數是錯的。

所以 7 月那個月只有 5 個 commit **不是停工**，是機器在跑而人在等。

**② 修量測工具——這是最吃人的時間的一個**

而且是最不直覺的一個。舉三個真的發生過的例子：

- 攻擊程式**回報送出 1,223 萬筆訊息，實際上一筆都沒離開那個程式**。
  原因是它跟防守端的通訊設定不相容，底層直接不投遞。
  而資料上看起來跟「防守端完美擋下了 1,223 萬筆攻擊」一模一樣。
- 錄封包的工具**開在錯的網路介面上**，於是整批資料裡 96% 是模擬器的無關流量，
  真正要看的流量**一個都沒錄到**。而日誌一切正常。
- 一個檢查工具**去讀一個不存在的欄位**，於是它對 2,053 場資料全部回報
  「沒問題」。**一個不可能成功的查找，回傳了令人安心的答案。**

這類事情**累計發生 31 次**，第五節有完整說明。

**③ 跑實驗、然後推翻自己——吃腦力**

模型那一半的工作有一半是在否證自己上一輪的結論。
最極端的一次是：**一個先前看起來完美（1.0000）的成績，被證明從來沒有在
度量它宣稱的那件事**。第六節講這個。

**④ 寫文件——比想像中多**

`文件/` 從 14 個長到 567 個。但大多數不是「報告」，而是**實驗紀錄**：
每一輪的預測、量到的數字、以及哪個假設被推翻了。
真正的報告類產出是四樣：長篇報告、簡報、證據總帳、答辯腳本。

### 2.2 六段空窗，每一段都對得上一件事

git 上有六段三天以上沒有 commit 的空窗，而每一段都**不是停工**：

| 空窗 | 天數 | 那段時間在做什麼 |
|---|---:|---|
| 07-05 → 08-05 | **32** | 等資料（正式 campaign 尚未開始，在做前置） |
| 08-08 → 08-13 | 6 | **1,100 場正式 campaign 在跑** |
| 09-05 → 09-14 | 10 | 等新一批資料 ＋ 分析 |
| 09-28 → 10-01 | 4 | 大型 campaign 在跑 |
| 10-04 → 10-07 | 4 | 跨主機實驗的準備與排程對齊 |
| 10-12 → 10-14 | 3 | 3,837 場跑完，準備重訓 |

⚠️ 這個對應是**從 commit 主旨推的**，不是工時表——空窗兩端的 commit 在講什麼，
就認定那段時間在做那件事。

另一側，單日最多的三天：**08-18 的 27 個**、09-02 的 21 個、09-25 的 20 個。
08-18 那天正是查出兩個收集器 bug 的那一天。

## 三、六個階段，白話版

**階段 0 — 起點（07-04 → 08-05，5 個 commit）**

7 月初做的事是**把安全設定做對**，而起因是一次自己打自己的實驗：

把簽發憑證的那把金鑰設成所有人可讀，偽造就成功了；
而只從網路上攻、拿不到那把金鑰的攻擊者**進不來**。
⇒ **要害是金鑰的保管，不是協定本身。**

於是 `42da766` 把兩種憑證的簽發權分開（身份用一把 CA、權限用另一把），
把原本用通用符號開放的權限收緊成逐項列舉，並寫了 28 項離線稽核。
另外修掉一支攻擊腳本自己會崩潰的 bug（雷射掃描的角度上下界相等時除以零）。

⚠️ Windows 那一側的加固**結構上做不了**：腳本量到自己沒有管理員身分，
所以它誠實地不做，而不是假裝做了。

機器學習那一半當時的狀態：**連「有沒有人在攻擊」這一題都還不行**。
用自己的弱標籤資料，PR-AUC（一個 0 到 1 的分數，越高越好）從 **0.20 進到 0.25**；
而同一套方法在公開的 RTPS 攻擊資料集上是 **0.98**。
**自己的資料對公開資料集差這麼多，就是後面三個半月要回答的第一個問題**（§四）。

**階段 1 — 資料工廠（08-06 → 08-21，33 個 commit）**

08-06 整條流程第一次在單機上跑通。08-13／14 跑出 **1,100 場、0 錯誤、
19,204 個證據檔、0 個雜湊失配**。

08-17 量到一件決定後面所有事的性質：**從網路流量就能認出系統是不是開了安全模式**
（可分離度 0.9451，門檻 0.70）⇒ 兩種模式必須分開訓練，不能混在一起。

08-18（27 個 commit，全期最高）查出兩個收集器 bug，而第二個值得單獨講：

> 重放攻擊的腳本用的通訊設定與防守端不相容，**底層直接不投遞**。
> 50 場裡 50 場都有不相容的日誌，而 9,502 筆簽章檢查**全部是通過**。
> ⇒ **防重放的主要防線，在正式資料裡一次都沒有被走過。**

08-21 用同樣的設定重跑 300 場，兩個被修好的類別從 0.375／0.429 升到
**1.000／1.000**，而**沒有被修的那些類別沒有動**——這一點很重要，
因為它證明提升來自那兩個修正，不是來自「新資料比較乾淨」。

**階段 2 — 證據治理與跨主機（08-25 → 09-04，69 個 commit，全期最密）**

這段在回答一個問題：**「這個 IP 真的是攻擊者嗎」要怎麼證明。**

08-26／27 第一次拿到底層協定的遠端認證證據——做法是在旁邊多跑一個
觀測程式，而不是去改原本的系統。08-29 第一次有一場資料的
「來源 IP 已驗證」是真的（先前 1,101 場全部是假）。

08-30 做了一次 **8 小時無人值守、80 輪**的跨主機實驗：**79 輪成立、
79 個互不相同的攻擊者識別碼、而 80 輪裡沒有一次把自己的 IP 誤判成攻擊者**。

⚠️ 08-31 查出一個會讓既有結論失效的缺陷：**1,400 場的網路分析全部少帶一個參數**，
導致封包被整批丟掉，連線數**虛增 7.96 倍**；而且切時間窗的方式也錯了
（真實流量跨 46 秒，但所有連線的起點擠在前 9 秒）。
修法是改成逐封包切窗，而**任何引用網路特徵數值的既有結論都要重做**。

**階段 3 — 模型選型與量測工具（09-15 → 09-27，49 個 commit）**

這段在問「換一個模型會不會更好」，而答案幾乎都是「不會」：

- 原本的評估**每個類別只有 3 場**，所以「3 場全錯」就顯示成 0.000。
  換成 17 場之後，**真正永遠為零的類別從 5 個變成 1 個**。
- 類神經網路（TCN／GRU）**六次比較沒有一次贏過樹模型**。
- 24 個不同的學習法比下來，**前七名的差距只有 0.02**——大約就是雜訊。
- 真正有用的不是換模型，是**換問題的問法**：從「一個時間窗一次判斷」改成
  「一整場一次判斷」，Enforce 模式進步 **0.093**。

⚠️ 而這段最重要的發現是：**切資料的工具不會洗牌、也不吃隨機種子**，
所以前面好幾輪的排名**全部來自同一個偏斜的切法**。修好之後排名重排，
**原本的第 1 名掉到第 4**。這是第 13 次量測工具自己壞掉。

另外把 Enforce 模式的未知攻擊偵測**掃完了整個格子**：3 種評分器 × 8 種規則，
**24 格全部是 0.0000**。這是一個乾淨的否定結果——那條路在應用層已經沒有東西可調。

**階段 4 — 工程問題與跨主機鏈（10-02 → 10-11，40 個 commit）**

這段幾乎全是工程問題，而三個都值得講：

- **三層等待窗反過來了**：最內層 120 秒先到期，而最外層的 200 秒永遠用不到。
  日誌寫「系統起不來」，但**系統其實是好的，是被自己的保險機制刻意停掉的**。
- **94 個殘留程序**，而它們是 campaign 自己的攻擊腳本留下來的。
  清理規則有 16 條，**16 條全部只涵蓋防守端**。
- **特徵抽取把整台機器卡住 71 分鐘**。原因不是程式吃太多記憶體，
  是虛擬機沒有設上限，於是它拿走主機一半的記憶體**而且不還**。

而這段最大的成果是 **10-08 那條鏈第一次完整跑完，九項檢查全過**：
攻擊 → 證明這個 IP 是攻擊者 → 下封鎖 → 確認封包真的被丟掉 → 撤銷 → 確認恢復。

⭐ 其中一項值得單獨講：**那張封鎖票上的證據編號，就是那份歸因報告檔案自己的
指紋**（SHA-256）。所以「是這份證據授權了這次封鎖」可以事後用密碼學證明，
不是靠日誌的自述。

⚠️ 第一次跑的時候核准片語是程式代打的，所以**後來請 Jesse 本人親手輸入重跑一次，
九項再次全過**。而**兩次產物裡那個「人工核准」欄位逐字相同**
⇒ **程式分不出是誰按下去的**，所以這件事只能由外部紀錄承載。

10-11 16:49:23Z 最後一批資料跑完，**3,553 場合格**
（Enforce 20 類／1,947 場／每類中位 78.5；Permissive 18 類／1,606 場／中位 77.0）。
⭐ 而這個數字被**兩條互相獨立的方法算出來，逐位相同**；
完成時間的預估誤差是 **1 分 23 秒**。

**階段 5 — 驗收與理解（10-15 → 10-19，27 個 commit）**

10-15 把考卷封起來（四份 holdout 封印），跑完整條驗收流程，
**第一次拿到「只讀過一次」的成績**。

而 10-16 之後的那幾輪全是**理解**而不是改進：每一輪都先寫下預測再去量，
而幾乎每一輪的主要假設都被自己的量測否證。

## 四、整個專題的中心難點

> **「這裡有人在攻擊」很好判斷。「是哪一種攻擊」很難。**

⚠️ 但要先更正一個容易被誤讀的對照。7 月初那個 **0.25 對 0.98**
**兩個都是「有沒有人在攻擊」的分數**（PR-AUC），不是「是哪一種」——
所以當時的落差不在「二元對多類」，而在**自己的資料對公開資料集**：

| 時間 | 題目 | 分數 |
|---|---|---:|
| 2026-07-04 | 有沒有人在攻擊（自己的弱標籤資料） | **0.25** |
| 2026-07-04 | 有沒有人在攻擊（公開的 RTPS 攻擊資料集） | **0.98** |

**也就是說，七月初連「有沒有人在攻擊」這一題，在自己的資料上都還不行。**

三個半月之後，那一題解決了，而難點整個轉移：

| 題目（2026-10-15，只讀過一次的封印考卷） | Permissive | Enforce | 門檻 |
|---|---:|---:|---:|
| 有沒有人在攻擊 | **1.0000** | **0.9151** | — |
| **是哪一種攻擊** | **0.4655** | **0.4228** | **0.80** |

（Permissive 與 Enforce 是兩種安全模式，模型分開訓練。）

**同一批資料、同一批模型，一個接近滿分，一個不到一半。**

### 4.1 為什麼「是哪一種」這麼難：五層原因

這五層是三個半月逐層剝出來的，不是一開始就知道：

**第一層：標籤跟證據對不上。**
最早的資料裡，有 300 場的「定義性證據」整個是空的——
參數竄改攻擊的遙測掛在一個攻擊流量到不了的層，而重放攻擊根本沒送出去。
⇒ 修好之後那兩類從 0.375／0.429 變成 **1.000／1.000**。

**第二層：網路那半邊的資料是壞的。**
1,400 場的分析少帶一個參數，連線數虛增 7.96 倍。
⇒ 修好之後，**升最多的正好是當時最難的那兩類**。

**第三層：有些攻擊根本沒有專屬的痕跡。**
這一層是真正的天花板。一個攻擊類別要被認出來，必須留下**只有它會留下的痕跡**。
而量下去發現，Enforce 模式下有八個類別**沒有任何專屬痕跡**，
兩兩之間 28 組全部分不開。

**第四層：防禦越有效，可用的痕跡越少。**
這一層最反直覺。Enforce 模式會把攻擊者在握手階段就擋掉，
所以它**連應用層都進不來** ⇒ 應用層什麼都看不到。

> 量化之後：**Enforce 模式下，整個 18 項的應用層遙測對「是哪一種攻擊」
> 只值 0.0009。** 幾乎是零。
>
> **安全機制生效的直接後果，就是識別率的上界。** 這是一個取捨，不是缺陷。

**第五層：先前的高分是「同一批環境」的上限。**
這一層 10-16 才查明，第六節講。

### 4.2 最值得講的一句話：偵測不到，但擋住了

有一類攻擊是「拿到合法憑證的內部人去偽造簽章訊息」。對它做了一次完整的掃描：

> 掃過全部 138 個特徵欄位，**它與正常流量的最大可分離度是 0.0507**，
> 而理論上限是 0.5。對照同一張表上另外三類攻擊是 0.4960 到 0.5000。

⇒ **它是這批資料裡唯一一個、在觀測到的整個特徵空間裡與正常流量不可區分的
攻擊類別。** 機制也說得通：它有合法憑證所以不產生認證失敗、流量是加密的、
訊息很小、而簽章拒絕發生在應用層——而第四層剛說過那一層看不到東西。

**而防禦仍然擋住了它。**

在一場單機驗證裡量到：**11 則偽造訊息被拒、0 則被接受，
而下一則真訊息照常通過。**

> **偵測不到，但擋住了。**
>
> 這是整個專題最值得講的一句話——它正好說明為什麼要做分層防禦，
> 而不是只做一個 AI 偵測器。

## 五、花最多時間、卻最看不見的：量測工具自己壞掉 31 次

這個專題記下的 31 次事件都是同一個形狀：

> **「防禦沒有反應」與「量測管線壞掉」，在資料上長得一模一樣。**

六個具體的例子：

| 看到的 | 實際上 |
|---|---|
| 報告送出 1,223 萬筆訊息 | **一筆都沒離開那個程式**（通訊設定不相容） |
| 整批資料的封包都錄到了 | **錄在錯的網路介面上**，真正要看的流量 0 個 |
| 2,053 場全部「正常」 | 檢查程式**去讀一個不存在的欄位** |
| 排名第 1 的模型 | 切資料的工具**不洗牌**，排名全部來自一個偏斜的切法 |
| 某個檢查「咬住了 ✅」 | 它在那一臂**本來就沒有判別力**，所以必然為真 |
| 一個檔案縮到只剩 6 bytes | 我的診斷腳本**把錯誤訊息切斷了**，原檔完好 |

最後一個特別值得記：**一個會截斷輸出的診斷工具，會製造出比沒有輸出更糟的東西**
——它讓一個完好的檔案看起來像資料損毀。

⇒ 這也是為什麼後面每一輪都先問「這個量測本身可信嗎」再問「結果是什麼」。

## 六、三個我自己推翻自己的時刻

**① 那個 1.0000 從來沒有度量過它宣稱的東西**

有一批 640 場的資料，模型在上面的交叉驗證分數是 **1.0000**——完美。
後來換到 3,553 場的新資料上，同樣的設定只有 **0.5124**，
而封印 holdout 上是 **0.4655**。

我第一個解釋是「交叉驗證沒有轉移到真實測試」。**那個框架是錯的。**
正確的分解是：

```
交叉驗證 0.5124 -> 封印 holdout 0.4655    差 -0.047   轉移得很好
640 場 1.0000  -> 3,553 場 0.5124        差 -0.49    落差在這裡
```

**落差不在「驗證到測試」，在兩批資料之間。**

而真因是量出來的，不是猜的：那 640 場是**同一天、連續幾個批次**跑完的，
所以每一場的「背景環境」幾乎一樣。把新資料也限制在**單一個 3 小時的批次**裡：

| | 類別之間 ÷ 類別之內 | 最近鄰正確率 |
|---|---:|---:|
| 640 場那批（單批次） | **2.141** | **0.9490** |
| 新資料，只取一個 3 小時的窗 | **2.177** | — |
| 新資料，全部 18.2 天 | **0.588** | **0.4670** |

⭐ **把新資料限制在一個批次裡，它的幾何就變成 640 場那批的幾何。**

⇒ **那個 1.0000 是「同一個環境下攻擊可以被完美分開」，是單批次上限，
不是泛化能力。** 而建立在它上面的模型選型，內部比較仍然有效，
但「它在部署時也最好」從來沒有被驗證過。

**② 兩個「沒有專屬證據」的類別，往相反方向走**

8/21 的報告寫過一句話：某兩個類別沒有專屬的證據通道，而這「強化了核心論證」。
封印 holdout 上，那兩個類別一個是**全表最高**（0.9091／1.0000），
另一個掉到 0.2727／0.1818。

查下去，原因是**那句話當時只量了應用層遙測，而它們其實在相反的通道上**：
一個是網路通道的類別，一個是遙測通道的類別。

⚠️ 而答案六週前就半寫在自己的紀錄裡——修好網路通道的那一輪，
它自己量到並點名了「升最多的正好是這兩類」。
**一個只往前看新證據的盤點，看不到舊紀錄裡已經寫下的反例。**

**③ 「上界不是保證」，而我引用了這個教訓還是犯了**

統計上有個常用的保守估計：如果 80 次都沒失敗，真實失敗率的上界約 3.7%。

| 當時 | 算出的上界 | 下一批實測 |
|---|---:|---:|
| 0 失敗／80 場 | 3.7% | **5.0%** |
| 0 失敗／154 場 | 1.9% | **7.2%** |

第二次是我自己做的，**而我在做之前還引用了第一次的教訓**。
真因是我取樣的那 154 場**全部落在退化開始之前**。

## 七、我們怎麼確保數字是真的

這是三個半月裡最大的方法論變化。白話版：

**① 把考卷封起來（從 09-26 起）**

做法是：在訓練之前，先把要當測試的那些場次**列成清單、算出指紋、封起來**。
之後只能**拆一次**，拆過就記錄為已拆，第二次執行直接被拒絕。

為什麼需要：先前的測試資料已經被反覆看過，而「看過之後再調參數」
會讓分數變好但不代表能力變好。

⭐ 10-15 第一次用上它，拿到這個專題第一個 **`independent_final_test: True`**
（意思是：設定在資料存在前就凍結並雜湊、封印在訓練前綁住場次清單、
只拆過一次，三件事都可以事後驗證）。

**② 先寫下預測再去量（10-17 起八輪）**

做法更硬：每一輪的預測寫成一份文件，**單獨提交成一個 commit**，
而 commit 訊息逐字寫著「**刻意不含任何結果**」。

⇒ **git 歷史自己證明註冊先於量測**，不需要相信任何人的自述。

⚠️ 而這套做法**連續有四輪是我自己註冊的檢查有設計缺陷**：
統計量退化、兩個不同尺度放在一起比、一個沒有判別力卻印出「咬住 ✅」的檢查、
以及漏掉一種形狀完全相同的失效。

⭐ **但每一輪的缺陷都變成下一輪的事前檢查，而它咬到了**：
為了抓第一個缺陷而設計的檢查，實測把平手從 **11 個降到 0 個**、
組內變異從 **50.7% 降到 1.3%**。

⚠️ 最新那一輪的缺陷還沒有對應的檢查，我沒有假裝它已經解決。

**③ 每一個宣稱都釘住它引用的檔案（從 08-25 起七份）**

叫做「證據總帳」：每一條宣稱列出它依據哪些檔案、那些檔案的大小與指紋，
整份再取一次指紋。之後任何人可以反向驗證。

而它**刻意不可覆寫**——引用的檔案後來長大了，反向驗證就會失敗，
而那時的處置是**出一份新的，不是去改舊的**。目前有 r3 到 r9 七份。

**④ 不完整的證據直接不准進訓練（從 08-17 起）**

一場攻防如果證據檔少一個、或大小跟紀錄不符，就不准進訓練集。
實測對 1,100 場是「1,100 接受、1 拒絕」，而被拒絕的那一場正是真的有問題的那一場。

**⑤ 連續 14 輪 `holdout_reads: 0`（從 10-16 起）**

意思是：這些輪次的分析**一列測試資料都沒有讀**。所以它們可以自由地推翻自己，
而不會消耗掉任何一次性的驗收機會。

| 項目 | 現況 | 100% 的定義 |
|---|---:|---|
| 資料集 | **95%** | 完整、可驗證、可重現的成對資料 |
| 攻擊偵測（有沒有人在攻擊） | **95%** | 一次性測試上的分數達標 |
| 攻擊識別（是哪一種） | **60%** | 達 0.80（現在 0.4655／0.4228） |
| 未知攻擊 | **55%** | 達 0.70（現在 0.1645） |
| 回應／執行 | **95%** | 整條鏈有實測（已達成，但無模型判定參與） |
| 單機防禦驗證 | **89%** | 九項全過（現在 8／9） |
| 跨主機／硬體 | **95%** | 三台機器 ＋ 真核心防火牆（已達成，但不是長時間測試） |
| 攻擊面覆蓋 | **87%** | 23 條規則都有腳本能產生資料（現在 20／23） |
| 文件／簡報 | **100%** | 報告、簡報、證據總帳、答辯腳本都涵蓋現況 |

**整體 771 ÷ 9 = 85.67%。**

整段期間的軌跡（量到，取自狀態表）：

```
55% (08-18) -> 68% (08-25) -> 71%->70% (08-28) -> 72% -> 76% (08-29)
-> 78% (08-30) -> 76% (09-02) -> 79% (09-15) -> 83% -> 85% (09-24)
-> 87.33% (10-07) -> 84.56% (10-15) -> 85.67% (10-19)
```

⭐ **這裡面有三次往下修，而沒有一次是因為東西壞了。**

**① 08-28：71% → 70%。** 新增「單機防禦驗證」一列。
那九項驗證一直都在做，只是從來沒有被計分，所以 5／9 進步到 6／9
在總分上完全看不見。加上它之後總分降低。原文寫著：

> 把一直存在但沒被計分的軸攤開，不應該讓總分變好看，會降低才是對的。

**② 09-02：78% → 76%。** 新增「攻擊面覆蓋」一列，同一個原則。

**③ 10-15：87.33% → 84.56%。** 這一次最重要：**第一次拿到只讀過一次的成績**，
而那個成績遠低於門檻（識別 0.4655／0.4228 對 0.80；未知攻擊 0.1645 對 0.70）。

⚠️ **驗收門檻一個字都沒有改。** 改的是百分比去跟上證據：

> 證據等級提高而數字變差，要反映出來。

⇒ 所以如果有人問「為什麼分數變低了，是不是做壞了」，答案是：
**先前那些高分是在較弱的證據等級上拿到的，而 0.4655 是唯一可以用來預期部署
表現的那一個。**

## 十、還沒做成的，也講清楚

**① 它還不能自動封鎖。** 而這是刻意的。

那條鏈九項全過，但**沒有任何模型判定參與其中**：
封鎖的對象來自歸因證據，動手的權限來自人親手輸入的核准片語。
授權執行的攻擊類別清單目前是**空的**，而真核心封鎖的總開關是 **False**。

剩下的阻塞**不是「機制行不行」，是「誰有權觸發」**。

**② 「是哪一種攻擊」還不夠好。** 0.4655／0.4228 對門檻 0.80。
而第四節的第三、四層說明了它的一部分是硬邊界，不是調參可以解決的。

**③ 未知攻擊偵測只有 0.1645。** 其中 Enforce 模式那一半**連評估都跑不了**——
24 格全零之後，那個選擇在宣告的範圍內不可能有影響。

**④ 跨主機只做過一次，不是長時間測試。** 一個目標、一張票、
存活時間 90 秒、1 個封包被丟棄、一種攻擊、**沒有正向對照**
（也就是沒有驗證過「合法的遠端程式不應該被封鎖」）。

**⑤ 攻擊面 20／23。** 缺的三類逐個查過，**沒有一個是「要寫新腳本」**：
一個其實已經在跑只是標籤不同，一個的訊號與地板相同，
而第三個是**規避成功**——它成功繞過了白名單比對，所以產生不了資料。
**那不是偵測不到，是那個規避手法有效，而那是結果不是缺口。**

**⑥ 既有 1,101 場資料的來源歸因缺口沒有補。** 新資料不會回頭修好舊資料。

**⑦ 兩個 campaign 修正的效果分不開。** 失敗率從 7.2% 降到 0（784 場），
但兩個修正**同時上線**，所以不知道是哪一個、或兩個都需要。

**⑧ 文件那一列的 100% 是關於「現在」的。** 它量的是四項是否涵蓋現況，
下一輪有新結果時它會再掉——10-18 就是這樣掉到 95% 的，而成因是
**一個只檢查自己動到的列的盤點**。
