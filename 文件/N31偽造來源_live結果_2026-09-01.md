## 三、為什麼是弱形式，以及不隱瞞這一點

`spoofing_evidence` 需要來源 MAC 與**解析 MAC 不相交**，而解析 MAC 要靠防守方
真的送封包給 `.200`。實測 `送往 .200 = 0 個`。

靜態 ARP 是有效的（`192.168.0.200 dev eth1 lladdr 02:00:00:00:be:ef PERMANENT`），
Fast DDS 就是沒送。最合理的解釋是我們**重放同一個錄下來的 SPDP 五次**，
位元組完全相同，被當成重複封包，沒有走到握手回應那一步。

要拿到強形式，攻擊端要讓每次的 GUID／序號不同，那是另一輪 live。
**在那之前，`來源位址偽造加固_2026-08-31.md` 的證據等級是：**

| 等級 | 狀態 |
|---|---|
| 記憶體合成列 | ✅ |
| 真 pcap ＋ 真 tshark 解析路徑 | ✅ |
| **真實偽造流量 → 前三條全過、第四條擋下** | ✅ **2026-09-01** |
| 真實偽造流量 → `spoofing_evidence`（強形式） | ⛔ 未取得 |

## 四、live 測試給了一個合成測試想不到的東西

```
192.168.0.200   來源 MAC e8:65:38:20:23:2f   同 MAC 其他 IP: ['192.168.0.30']
192.168.0.30    來源 MAC e8:65:38:20:23:2f   同 MAC 其他 IP: ['192.168.0.200']
```

**同一張網卡同時宣稱兩個同網段位址，其中一個正是攻擊者自己的。** 那是偽造的
**正面證據**，而且早就被 `check_link_layer_binding.py` 記錄下來——只是判定
邏輯沒有用它，給出的理由是「取不到解析 MAC」這種 absence of evidence。

合成測試發現不了：合成資料裡每個位址都只有一張網卡，因為我寫的時候沒想到
攻擊者會同時用兩個身分。

已接進判定：

- `mac_claims_multiple_addresses` 布林欄位
- 判定不是 `consistent` 時，把它併進 `reasons_inconsistent`，理由從
  「查不到」變成「這張網卡還宣稱了 X，封鎖此位址擋不住那個發送端」
- **verdict 刻意不升級成 `spoofing_evidence`**：路由器與 NAT 本來就會用一張
  MAC 送出許多來源位址，單獨不足以斷定
- 資訊放在獨立的 `notes`，因為 `192.168.0.30` 自己是 `consistent` 卻同時在
  偽造別人——那條資訊不該寫進「為什麼判定不自洽」

## 五、途中查清楚的兩個環境事實

**一、mirrored 模式下 Windows 與 WSL 的鄰居表是分開的。**
`New-NetNeighbor`（Windows 側）加的靜態 ARP **對 WSL 完全沒有作用**：讓 WSL
送封包給 `.200`，它的表出現 `INCOMPLETE`，代表它自己在做 ARP。觀測者跑在
WSL 裡，所以只有 WSL 那筆算數。

**二、TCP inbound 被 Hyper-V 防火牆全擋。**
`DefaultInboundAction = Block`，而既有規則只有 UDP 14900–14999。跨機傳檔因此
完全不通，症狀是**逾時而不是 refused**。加一條 TCP 規則後立刻通。

## 六、量測側的三個失敗，全部是「執行了、沒有錯誤、就是沒作用」

| # | 現象 | 真因 |
|---|---|---|
| 1 | 跨 session 訊息 `success: true` 但對方沒收到 | 我這邊的清單裡是**過期登錄**，活的 session 打不到 |
| 2 | `curl` 逾時 | Hyper-V 防火牆沒有任何 TCP inbound 規則 |
| 3 | `ip neigh replace` 以 root 執行、無錯誤、無效果 | 貼到了別的地方；而**從來沒有人看過輸出** |

第 3 項的解法是給一條**自我驗證**的指令（執行完立刻 `ip neigh show`），一跑
就知道。這個專案反覆栽在同一件事上：**失敗訊息聽起來完全合理，或根本沒有訊息。**

⚠️ 我自己也犯了一次：重開擷取的腳本帶 `rm -f`，等於每次重開就抹掉前一個窗的
證據，而那個窗正好涵蓋攻擊機下載腳本的時間。已改成寫帶時間戳的新檔、舊的全留。
