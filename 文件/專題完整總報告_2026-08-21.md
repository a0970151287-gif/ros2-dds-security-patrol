## 摘要

本專題在 ROS 2 Jazzy／Fast DDS 上建置房間級 DDS 智慧防火牆，整合 SROS2 存取控制、
應用層 HMAC 簽章、行為 IDS 與機器學習偵測，並以 1,399 場真實 live 攻防資料驗證。

**核心貢獻不是模型準確率，而是一個可否證的因果發現：**

> 多類攻擊識別的天花板由**證據排他性**決定——某個攻擊類別若沒有專屬的可觀測
> 訊號，任何模型都分不出它；而修好證據通道之後，**正是那些類別**的識別率上升。

這個主張以一個事前登記預測的重跑實驗驗證：修復兩個遙測缺陷後重跑 300 場，
三個預測全部成立，包含一個刻意設置、**確實沒有變動**的對照組。Permissive 的
多類 balanced accuracy 由 0.5587 升至 **0.8619**（封存 test，僅開啟一次），
而事前預測「不會改善」的 `identity_abuse` 仍為 0.467。

同時取得三項**負面但可發表**的結果：DDS Security 稽核日誌在本技術棧無法啟用、
anti-replay 實際上由時間戳窗與最小權限 ACL 生效而非 ReplayCache、
以及防禦有效性與事後可識別性之間存在可量化的張力。

## 一、專題範圍與證據邊界

### 1.1 範圍取捨

依教授「專注 DDS、把核心做深」的指示：

| 類別 | 內容 | 處置 |
|---|---|---|
| 🟥 核心 | 紅隊攻擊、Zeek DDS 層偵測、緊急停止聯動、偵測率／誤報率驗證 | 全部投入 |
| 🟧 加分 | HMAC envelope v3、行為 IDS D1–D6、SROS2 Enforce、ML-IDS | 縱深防禦與 AI 主軸 |
| 🟦 未來工作 | 強化學習巡邏、多場景泛化、LLM 模糊測試 | 明確排除 |

### 1.2 實驗性質

**受控實驗室內的真實攻防**，不是紙上推演。紅隊 PoC 實際建立 ROS 2 節點、發布
topic、呼叫 service、送出 DDS／RTPS 流量；證據保存受害端 log、封包擷取與遙測。

被保護的 TurtleBot3 是 Gazebo 模擬機器人。因此「攻防封包與程式真實執行」
**不等於**「已在實體機器人或生產工廠驗證」。所有 live 證據皆為同一主機 loopback。

### 1.3 威脅敘事原則

依 2026-06-04 教授評審意見，威脅敘事為**軟體模組對軟體模組**：攻擊方是未授權
程式（rogue process），受害方是被命名的軟體模組，攻擊一律透過介面
（DDS topic／service、Linux 檔案／process）發生。

## 二、系統架構與防禦分層

五層防禦互補，AI 不是唯一防線：

| 層 | 機制 | 擋什麼 | 本專題的實測證據 |
|---|---|---|---|
| L1 傳輸／身分 | SROS2 Enforce（雙 CA、per-node enclave） | 無憑證參與者連 handshake 都建不起來 | 未授權送達數 **0** |
| L2 訊息真實性 | HMAC envelope v3（channel＋nonce＋ts） | 有憑證但無金鑰的內鬼 | 偽造 **11 拒／0 收** |
| L3 輸入驗證 | SensorHub 邊界檢查 | 超長輸入 | **7 拒／0 收**，行程存活 |
| L4 行為偵測 | 行為 IDS D1–D6 ＋ ML-IDS | 通過前三層但行為異常 | 見第六節 |
| L5 回應 | 已驗章 guard、Ed25519 短效票證 | 誤封與不可撤銷 | 停車延遲 **0.019–0.210 秒**（八次量測） |

**分層防禦第一次被直接量到**（而非推論）：攻擊者持**合法 SROS2 憑證**（模擬節點
被攻陷）但沒有 HMAC 金鑰時，SROS2 放行了他，HMAC 仍然全數擋下，而下一則真訊息
照常通過。

偽造刻意用攻擊者自己生成的金鑰去簽**格式完全正確**的信封。否則會被判
`malformed_envelope`——那證明的是解析器擋住畸形輸入，不是簽章檢查擋住偽造，
是兩道不同的防線。

## 三、資料集

### 3.1 規模與完整性

| 項目 | 數值 |
|---|---|
| 正式 campaign | 1,100 場（Permissive 550／Enforce 550） |
| 重跑補正 | **300 場**（2026-08-21） |
| 進入特徵表 | 1,099 場、**15,174 個視窗** |
| 排除 | 1 場（釘住的 manifest 失配，raw 保留不刪） |

排除採「釘住」機制：registry 記錄完整失配指紋（manifest 與實際的 bytes／sha256），
**只有當下觀察到的失配與釘住的完全相同、且是唯一問題時才排除**。不同大小、不同
檔案、或多一個問題都仍 fail-closed。套用的排除逐一寫入 `feature_build.json`。

### 3.2 300 場重跑：一個可否證的實驗

三個 scenario 的攻擊專屬證據原本是空的，成因是兩個已修的缺陷：

| scenario | 場次 | 失效原因 |
|---|---:|---|
| `heartbeat_replay` | 100 | 攻擊端 BEST_EFFORT publisher 對 RELIABLE subscriber，DDS 直接不投遞 |
| `parameter_tamper` | 100 | `parameter_call` hook 掛在 rcl read-only 拒絕**之下** |
| `parameter_flood` | 100 | `get_parameters` 當時沒有任何 hook |

重跑沿用原本的 `seed`、`scenario_id`、`security_mode`，**唯一變因是那兩個修正**。
原始 `dataset_live` 完全未動，作為對照基準保留。

**預測寫在跑之前：**

| # | 預測 | 結果 |
|---|---|---|
| 1 | `parameter_call` > 0（Permissive） | ✅ 0 → **210,614** |
| 2 | `nonce_reuse_or_capacity` > 0（Permissive） | ✅ 0 → **312** |
| 3 | **（對照組）** `sros2_deny` 維持 0 | ✅ 0 → 0 |

第 3 項刻意設為對照：它沒有被修，所以不該動。**它確實沒動**，因此前兩項可歸因
於修正，而不是環境漂移。檢核器先在未重跑的舊資料上自我驗證，當時正確報出前兩項
「被推翻」——證明它會咬人，不是只會蓋章。

### 3.3 遙測來源的誠實標記

重跑後重新量測，「18 項中 8 項恆為零」降到 **5 項**：

| 特徵 | Permissive 非零率 | 狀態 |
|---|---:|---|
| `parameter_call_rate` | 24.15% | 復活 |
| `nonce_reuse_ratio` | 2.32% | 復活 |
| `heartbeat_gap_sec` | 0.05% | 復活（本來就稀疏，只在 fault 轉換時發） |
| `sros_auth_fail_rate` | 0 | **來源不可得**（見 8.2） |
| `sros_permission_deny_rate` | 0 | 同上 |
| `scan_static_ratio` | 0 | detector d3 從未 fire |
| `channel_mismatch_ratio` | 0 | 時間戳檢查先攔下 |
| `qos_drop_ratio` | 0 | loopback 上確實沒掉包，映射正確 |

**「來源不可得」不可回填成「量測到零」。** 前者是沒有觀測，後者是觀測到沒有事件。

## 四、SROS2 模式必須分開訓練

跨模式可分離度 **0.9451**（門檻 0.70）：分類器能從 14 個網路特徵認出安全模式，
其中 10 個單獨就做得到。刪掉最強的幾個也無效——留下最乾淨的六個仍有 0.857，
而攻擊偵測從 0.950 掉到 0.748。

**這是真實效應，不是採集缺陷**：DDS Security 加密探索、增加握手、拒絕未授權對等點，
流量本來就長得不一樣。

因此不再要求單一模型跨越兩種模式，改為**分模式各自評估**：
「在這個安全政策下能不能偵測攻擊」是可回答且誠實的問題，而成對 campaign 支持
問它兩次。

## 五、核心發現：識別率由證據排他性決定

### 5.1 主張

前一版報告已指出「資料瓶頸，不是演算法瓶頸」，論據是三種不同典範（RandomForest、
IsolationForest、SMOTE）的 recall 都卡在同一量級，以及同一模型換到外部乾淨資料
（HCRL RTPS）PR-AUC 由 0.25 跳到 0.98。

**重跑把這個論證由相關性升級為因果**：不只是「資料品質有限」，而是
**特定證據通道的損壞限制了特定類別，修好之後正是那些類別上升**。

### 5.2 證據

Permissive final test 逐類 recall：

| 類別 | 舊 test | 新 test | 有無重跑 | 有無專屬證據 |
|---|---:|---:|---|---|
| `replay` | 0.375 | **1.000** | ✅ | 修好後有 |
| `parameter_tamper` | 0.429 | **0.988** | ✅ | 修好後有 |
| `service_dos` | — | **0.975** | ✅ | 修好後有 |
| `sensor_spoof` | — | **1.000** | ❌ | 本來就有（`hmac_failure_rate`） |
| `message_dos` | — | **0.970** | ❌ | 本來就有（`oversized_message_ratio`） |
| `replay_dos` | — | 0.933 | ❌ | 本來就有（`alert_reflection_ratio`） |
| `command_injection` | — | **0.513** | ❌ | **沒有** |
| `identity_abuse` | 0.233 | **0.467** | ❌ | **沒有** |

三組完全對齊。混淆矩陣顯示剩餘錯誤集中在 `command_injection`／`identity_abuse`／
`normal` 三者之間——正是證據通道**沒有**被修的那些類別。

### 5.3 排除批次效應

那 300 場是同一天連續跑的，環境同質，因此「提升來自批次指紋」必須排除。
Permissive validation 消融：

| 特徵集 | balanced accuracy |
|---|---:|
| 只有 network | **0.3235** |
| 只有 telemetry | **0.8484** |
| fusion | 0.8602 |

若提升來自批次效應，**network 特徵應該也會變好**——流量形狀與時序是批次指紋
最可能出現的地方。它沒有。提升集中在 telemetry，正是被修好的那條通道。

⚠️ 此消融只排除「流量層批次指紋」一種通道。那 300 場的 `code_revision` 與日期
分布確實與其餘 800 場不同，這個限制應保留在報告中。

## 六、模型結果

### 6.1 Final test（封存 test，僅開啟一次）

| | Permissive (fusion) | Enforce (network) |
|---|---:|---:|
| balanced accuracy | **0.8619** | 0.4155 |
| macro F1 | **0.8630** | 0.4115 |
| binary attack PR-AUC | **0.9900** | 0.9774 |
| attack recall | 0.9341 | 0.9362 |
| normal false positive rate | 0.0879 | 0.0767 |

validation 0.8823 對 test 0.8619，**差距 0.02**——選型沒有過擬合 validation。

Permissive 首次通過三道部署 gate：balanced accuracy ≥ 0.80、macro F1 ≥ 0.80、
未知攻擊 recall ≥ 0.70。

### 6.2 Enforce：偵測得到，識別不出

Enforce 的 balanced accuracy 只有 0.4155，但 binary PR-AUC **0.9774**、
attack recall 0.9362。重跑實測 Enforce 的 `parameter_call` 與 nonce **全部維持 0**。

原因：SROS2 在 DDS handshake 就拒絕無憑證攻擊者，訊息到不了應用層，
**應用層證據根本不存在**，只剩流量形狀可用。

> **這個不對稱是結果，不是缺陷。** 它量化了「防禦有效」與「事後可識別性」之間的
> 張力：防禦越早擋下攻擊，能用來分類攻擊種類的證據就越少。

### 6.3 未知攻擊：兩種模式失敗在不同的地方

以完全未被任何階段看過的兩個類別（`sensor_spoof`／`service_dos`，共 100 場）
評估**整個模型**：

| | Permissive | Enforce |
|---|---:|---:|
| **open-set recall** | **0.5499** | **0.6583** |
| 誤填成已知攻擊類別 | **231** | 76 |
| 漏成 normal | 78 | **416** |
| normal 誤判為 unknown | 0.0116 | 0.0278 |

兩者都低於 0.70 門檻，也都低於異常偵測頭報的 0.7627——那個數字只回答
「像不像正常」，而整個模型還要通過 family 與 leaf 兩層，那兩層會把沒見過的攻擊
往最接近的已知類別推。**拒絕把未知套進已知，是 open-set 更難的一半。**

Enforce 反而較高，因為它的遙測是空的：模型沒有足夠的已知類別訊號可以攀附，
比較不會自信地誤填；代價是更容易整個漏掉。
**Permissive 失敗在「誤填」，Enforce 失敗在「漏掉」。**

協定可驗證地乾淨：supervised train／calibration／selection／threshold 四個計數
全為零。前提是分層架構當初在**看過歷史 test** 的情況下設計，因此 artifact 仍記
`independent_final_test=false`。

九項驗收目前 **5／9** 有單場完整 live 證據：

| 項目 | 關鍵數字 |
|---|---|
| `normal_traffic_preserved` | 未授權 publisher **0**；final `/cmd_vel` 唯一合法來源 |
| `unauthorized_participant_denied` | 未授權送達數 **0**；state digest 未變 |
| `hmac_forgery_dropped` | 偽造 **11 拒／0 收**；下一則真訊息仍被接受 |
| `oversized_input_dropped` | 超長輸入 **7 拒／0 收**；SensorHub 存活 |
| `velocity_guard_zeroed` | 已驗章鎖定 → 零速，**0.019–0.210 秒**（八次量測） |

目前未產出。

**四項未取得，其中三項的阻塞原因本身是防禦有效的證據：**

| 項目 | 阻塞原因 | 代表什麼 |
|---|---|---|
| `replay_dropped` | ACL 強迫跨行程，超過新鮮度窗 | 最小權限讓重放來不及發生 |

只有 `velocity_guard_recovered` 是真正的工程缺口（受控接縫觸發不穩定）。

## 八、負面結果（可發表）

### 8.1 anti-replay 不是靠 ReplayCache 生效

重放**確實抵達**驗證器，但兩場實測共 24 次重放全部落在 `timestamp_violation`，
`nonce_reuse_or_capacity` **0 次**。四種排法都輸掉同一場競速。

時間戳窗（alerts 10 秒、心跳 3 秒）加上最小權限 ACL 讓重放**來不及發生**：
要夠快必須側錄與重放在同一行程，但沒有任何 enclave 同時擁有某個安全頻道的發布與
訂閱權。**ACL 強迫攻擊者跨行程，而跨行程的成本超過新鮮度窗。**

附帶：alerts 是 TRANSIENT_LOCAL，後加入的訂閱者先拿到 durability 快取裡的**陳舊**
alert——攻擊者就算側錄到真品，拿到的也是過期品。

### 8.2 DDS Security 稽核日誌在本技術棧無法啟用

屬性設定經二進位驗證正確，未啟用 SROS2 時可成功初始化；一旦啟用 SROS2，
`rmw_fastrtps_shared_cpp` 自行組出 participant 的安全屬性清單，其中**不含 logging
plugin**，XML profile 的 `propertiesPolicy` 不被保留。

因此 `sros_auth_fail_rate` 與 `sros_permission_deny_rate` 標記為**來源不可得**，
不是「量測到零」。這也說明為何 `identity_abuse` 無法靠「補設定」改善——
需要換觀測層（封包層 RTPS）。

### 8.3 量測工具本身的四個缺陷

這些都會**偽裝成「防禦沒反應」**，值得單獨記錄為方法論教訓：

| 缺陷 | 症狀 |
|---|---|
| 等待器每輪重讀整份 JSONL | 22 秒的等待做出 137 秒的窗，撞上安全上限 |
| 窗起點行號取在 marker 前／後 | 取前匹配到窗外舊事件；取後漏掉 marker 落地那 0.7 秒的轉換 |
| marker 輔助函式全檔掃描 | 開窗與關窗本身就撐爆窗（80.3 秒 → 7.5 秒） |
| 攻擊訊息過大 | 8,192 點的 scan 在傳輸層就被丟掉，**看起來像防禦擋下了** |

> **共同教訓：「訊息沒送達」與「防禦擋下了」在遙測上完全一樣。**
> 要證明某道防線有效，必須先確認攻擊真的抵達了那道防線。
