# 三支新攻擊的 gate 結果：只有一支可用，而原因值得寫進論文

> live smoke 經 Jesse 對本次操作明確授權（2026-09-02）。同機、Permissive、
> domain 30。ROS stack 已停止。產物：`~/candidate_smoke_20260902T081833Z/`

## 我的事前預期，兩半都錯

跑之前寫下：

> N34（`odom_spoof`）最可能過——它有專屬特徵 `odom_cmd_mismatch_ratio`
> 且語意精確；N33 與 N35 最可能彼此分不開，因為兩者都是「大量 participant
> 活動」，只差時間分布。

實際：

| | 預期 | 實際 |
|---|---|---|
| `odom_spoof` | 最可能可用 | **通過個別判定但不可分** |
| `node_churn` ←→ `spdp_flood` | 最可能分不開 | **可分** |
| 唯一可用的 | — | **`node_churn`** |

## 結果

三支都通過個別判定（對基線排他），但兩兩比對之後：

```
node_churn   vs 其他四支     ✅ 全部可分
odom_spoof   ←→ spdp_flood   ⛔ 共用 7 個（全部）
odom_spoof / spdp_flood / baseline_poisoning / verify_flood
                             ⛔ 四支互相分不開
```

**只升級 `node_churn`。攻擊面覆蓋 16 → 17／23。**

## 為什麼四支分不開：防禦的反應是通用的

四支共用的訊號**全部是防禦的反應**，不是攻擊自己的痕跡：

```
guard_output.angular_z=0&blocked=False    守衛輸出零速
hmac_result.channel=alerts                發了一則警報
hmac_result.channel=alerts&outcome=accepted
hmac_result.channel=alerts&reason=accepted
```

`node_churn` 獨有的則是**它自己的足跡**：

```
participant_change            5
participant_change.count>0    5
unknown_node                  3
unknown_node.count>0          3
authenticated_action.action=guard_lock  3
```

> **攻擊只有在留下自己的痕跡時才可識別；只是觸發了防禦，是不夠的。**

這與本專案 2026-09-01 量到的 SROS2 均勻拒絕是**同一個結構**：
防禦運作得越一致，可偵測性越高、可識別性越低。差別只在那次是身份層，
這次是應用層的守衛與警報。

## ⚠️ 同日稍晚的更正：`odom_spoof` 那一節的成因寫錯了

本文原本寫「它的定義性特徵是 `odom_cmd_mismatch_ratio`，來源是
`control_observation` 事件，而這一場的計數是 0」。**來源那半是錯的。**

`control_observation` 是**已退役的事件型別**：全 repo 沒有任何發送端，
1,100 場裡 0 筆，而 `M1_loopback_pilot發現_2026-08-06.md` 明寫它被
`guard_input`／`guard_output` 取代。`features.py:1064` 顯示真正餵
`odom_cmd_mismatch_ratio` 的是**偵測器 d6**。

d6 在全資料集出現在 **49／1,101 場**，特徵非零率 Permissive 1.02%、
Enforce 0.47%——所以那個通道是活的，**我第一次抽 40 場沒抽到而已**。

### 真正發生的事

odom_spoof 那一場 fire 的是 **d4（publisher violation）**，incident ＋
recovery 各一次。**防禦偵測到了 `/odom` 上有兩個發布者**——那是正確行為，
只是走的不是我預測的偵測器。

### ⚠️ 再更正一次：我上一段說「特徵名與來源不符」也是錯的

上一版寫「d6 是 scan／odom 一致性，不是 odom 與 cmd_vel 的比對，所以特徵名
與來源語意不符」。**讀完 d6 的實作之後，那句也錯了。**

d6 檢查**兩件事**，第二件正是 cmd／odom 不一致：

```python
# (a) odom 顯示有移動 + scan 完全靜止 → 不一致
if avg_lin > 0.05 and max_scan_diff < 0.002: ...
# (b) cmd 持續正向但 odom 沒動
if avg_cmd > 0.05 and avg_lin < 0.005:
    return True, "cmd v=… 持續正向但 odom 靜止"
```

**`odom_cmd_mismatch_ratio` 這個名字是對的**，它對應 case (b)。沒有語意不符。

### 那 N34 為什麼沒觸發 d6

- **case (a) 由構造上不可能**：N34 發布的 odom twist 是**零**，
  而 (a) 要求 `avg_lin > 0.05`。攻擊本身排除了這條路。
- **case (b) 需要機器人正被指令前進**（`avg_cmd > 0.05`）。d6 沒有 fire，
  代表這個條件沒有滿足。

### 但這一點我**無法從證據驗證**，那是一個可觀測性缺口

`guard_input` 事件的 details 只有 `accepted_count`——**只記數量，不記速度值**。
所以無法從錄下來的遙測判斷當時 `cmd_vel` 到底是多少，也就無法確認偵測器
為什麼沒有 fire。

**遙測沒有記錄偵測器實際使用的數值。** 這與本專案反覆遇到的形態同類：
證據不足以診斷證據本身。要修的話是讓 `guard_input` 記下速度的摘要統計
（例如視窗內的最大值與均值），但那會改變特徵契約，不在本輪範圍。

所以 `odom_spoof` 的狀態仍是 `not_evaluated`，但理由要改成：
**它的攻擊被 d4 抓到而不是 d6，而 d4 的訊號沒有進入它的排他集合。**

## `odom_spoof` 的失敗是量測缺口，不是定論

它的定義性特徵是 `odom_cmd_mismatch_ratio`，來源是 `control_observation`
事件。這一場的計數是：

```
control_observation   0
```

**訊號通道在這個 scenario 的條件下是死的。** 我事前查到它在 1,100 場裡有
1.66% 的視窗非零，就假設它是活的——但那些場次的機器人**正在巡邏**，
才有 cmd_vel 與 odom 可以比對。smoke 場次裡沒有真實運動，比對從未發生。

所以 `odom_spoof` 的正確狀態是 **`not_evaluated`**，不是 `rejected`：

- 它通過的那些訊號是防禦的通用反應，不是它自己的
- 它自己的訊號通道整場沒有事件
- 要真的評估它，smoke 必須讓機器人實際移動

**這是我第二次假設「特徵在歷史資料裡非零 ⇒ 通道是活的」而出錯**，
前一次是 `hmac_result.channel`（正常流量也在那些頻道驗章，所以不排他）。
正確的問法是「**在這個 scenario 的條件下**，這個通道會不會有事件」。

## 攻擊面的現實上限

| 類別 | 狀態 |
|---|---|
| 出貨可產生 | **17／23** |
| `odom_spoof` | 需要會動的 smoke 才能評估 |
| `spdp_flood`、`baseline_poisoning`、`verify_flood` | 與彼此不可分——**要嘛合併成一類，要嘛找出新證據** |
| `node_name_evasion` | 完全沒有專屬訊號 |
| `cmd_vel_race` | 與 `cmd_vel_injection` 同機制（N9 已是後者的 runner） |

所以 **23／23 在目前的觀測層不是「還沒做」，而是結構上做不到**——
這直接影響部署 gate `all_policy_classes_present`，它要求完全相等。

## 不可宣稱

- 每支只跑**一場**。訊號的存在性成立，穩定性沒有驗過。
- `odom_spoof` 與 `spdp_flood` 的腳本本身沒有問題（都 `rc=0`、跑滿 30 秒），
  問題在它們的可觀測後果。
- 進度：攻擊面覆蓋 70% → **74%**（16／23 → 17／23），整體維持 **77%**。
