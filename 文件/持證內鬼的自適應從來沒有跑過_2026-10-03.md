# 持證內鬼的自適應從來沒有跑過，而那是威脅模型在運作（2026-10-03）

判定 C2C-095 那個事前預測時，逐步計時（C2C-090 加的）把兩件被混在一起的事
分開了。**兩件都不是我預期的。**

本輪**未修改任何程式**，全程離線唯讀。

## 一、先判定那個預測：兩邊都不乾淨

預測（寫在知道答案之前）：

> 若成因是**負載** → Observer 的 `import` 耗時隨輪次爬升，而
> `attack_process` 失敗率跟著回到 >10%
> 若成因是**那三個開關** → 失敗率與執行時長無關地維持 <5%

實測（13:33Z 重啟後 173 場 complete）：

| 判準 | 預測「負載」 | 預測「開關」 | **實測** |
|---|---|---|---|
| 失敗率 | >10% | <5% | **5.0%**（正好在邊界） |
| `import` 中位，逐五分位 | 爬升（曾量到 12.8 倍） | 平 | 0.55→0.57→0.62→0.72→**0.71s**（+30%） |
| 失敗場的 `import` | 明顯較慢 | 無關 | 4 場裡 **3 場正常**（0.68／0.78／0.81s） |

**兩個預測都沒有乾淨地贏。** 而決定性的新事實是：**失敗跟著模式，不跟著時間。**

| | n | 失敗 |
|---|---:|---:|
| enforce | 80 | **4（5.0%）** |
| permissive | 93 | **0（0.0%）** |

五分位看起來像時間趨勢（0／0／0／5.7／5.7%），**但那是混淆**：Q1／Q2 全是
permissive、Q4 全是 enforce。

### ⚠️ 這推翻我自己在 C2C-095 發布的上界

C2C-095 用 0／80 的三的法則給出 **3.7%** 的單側 95% 上界。
**下一個 80 場是 5.0%，超出那個上界。**

合併兩個重啟後的窗：**4／160 = 2.5%**（09:32Z 的窗 0／80，13:33Z 的窗 4／80）。
⇒ 規劃該用 **2.5%** 而不是 0%。對預測的影響很小
（1,602 × 0.975 ≈ 1,562 對原本估的 1,543），**但那個「決定性」的說法要收回**：
0／80 決定性地否證了 34.7%，**它不是零的證據**。

| 場次 | 最後印出 | `import` | ⇒ 卡在 |
|---|---|---:|---|
| `sensor_status_spoof` | `rclpy.init 0.01s` | 4.95s | **`Node(...)`** |
| `heartbeat_replay` | `rclpy.init 0.00s` | 0.78s | **`Node(...)`** |
| `mission_spoof` | `rclpy.init 0.00s` | 0.81s | **`Node(...)`** |
| `discovery_recon` | `sub:alerts 0.35s` | 0.68s | **第二個 `create_subscription`** |

⚠️ 而 `sub:alerts` 在 C2C-091 量到 **0.02s**，這裡是 **0.35s（17 倍）**。

**「六個參數服務」那個假設因此被排除**：那三個開關
（`start_parameter_services=False`、`enable_rosout=False`、關掉 type description）
**確實在程式裡**（`N37_adaptive_attacker.py:367-369`），而 3／4 仍然卡在 `Node()`。

成功場次的逐步耗時（逐模式）把形狀量了出來：

| 步驟 | enforce 中位／p90／max | permissive 中位／p90／max | **p90 比** |
|---|---|---|---:|
| **`Node`** | 0.13／**0.50**／2.11s | 0.11／0.14／0.62s | **3.6×** |
| `sub:cmd_vel` | 0.01／0.04／0.36s | 0.00／0.01／0.05s | **4×** |
| `import`（與 DDS 無關） | 0.70／0.81／4.95s | 0.57／0.73／2.39s | **1.1×** |

**中位數不分辨**（`Node` 1.18× 而與 DDS 無關的 `import` 也是 1.22×
⇒ 那是一般性的 enforce 開銷），**尾部分辨**：`Node` 的 p90 是 3.6× 而
`import` 的 p90 只有 1.1×。

⇒ **enforce 專屬的成本在 DDS 呼叫的尾部**，而 5% 的失敗率正是尾部現象的形狀。
⚠️ 把它歸因到「SROS2 安全握手」仍然是**推論**——量到的是「卡在 `Node()` 或
`create_subscription`、`import` 正常、只在 enforce」。

## 三、⚠️ 而把那 4 場分出來之後，露出一件完全不同的事

enforce 場次的輸出形狀（重啟後 67 場有攻擊行程）：

| 形狀 | n | 意思 |
|---|---:|---|
| 五步全到 ＋ `觀測者就緒` ＋ `DECISION_TRACE` | 45 | 正常 |
| `import`+`rclpy.init` ＋ 就緒 ＋ **`可觀測=False`** ＋ TRACE | **18** | **`Node()` 拋例外被接住** ⇒ 攻擊照跑、**場次合格**、觀測者是瞎的 |
| 卡在 `Node()`，無「就緒」 | 3 | rc=-9 |
| 卡在第二個 subscription | 1 | rc=-9 |

**那 18 場不是隨機的 26.9%，是兩個 scenario 的 100%：**

```
insider_parameter_write   盲打 12／12
insider_hmac_forgery      盲打  6／6
其餘 17 個 scenario × 兩個模式  盲打 0／121
理由（N37 自己印的）: RCLError: error creating node: couldn't find all security files!
```

permissive：**0／72**。

**回溯整個 `dataset_mega`**（逐步計時與 `可觀測` 旗標是 2026-10-02 加的，
所以只有之後的場次可判讀）：

| scenario | 盲打 | 可判讀 | 早於旗標 |
|---|---:|---:|---:|
| `insider_parameter_write` | **22** | 22（**100%**） | 25 |
| `insider_hmac_forgery` | **17** | 17（**100%**） | 24 |
| 其餘 17 個 scenario | **0** | **790** | — |

⚠️ 那 49 場早於旗標的內鬼場次**沒有被直接觀測到**。機制（keystore 在、
而 14 個 enclave 裡沒有 `/n37_probe`）是**keystore 的性質而不是場次的性質**，
所以它應該對全部成立——**但那正是我在 C2C-089 必須撤回的那種論證形式**
（C2C-083 用「機制是決定性的」支撐 n=13 的 100%，而 600 場上是 87.3%）。
所以：**39／39 是觀測，49 場是推論。**

### 機制與我的推理相反：有憑證才會瞎

| 攻擊者 | 環境（C2C-053） | `Node("n37_probe")` |
|---|---|---|
| 無憑證外部者 | `attacker_environment`——**沒有 keystore** | 安全層不啟用 ⇒ **成功** |
| **持證內鬼** | `insider_environment`——**有 keystore** | Enforce 下要一個名為 `/n37_probe` 的 enclave，而那 14 個裡沒有 ⇒ **fail-closed** |

> **部分憑證比沒有憑證更嚴格。** 完全沒有 keystore 會讓安全層整個不啟用，
> 而有 keystore 卻沒有對應的 enclave 會 fail-closed。

### 而這是威脅模型在正確運作，不是缺陷

內部威脅模型的定義是「攻擊者**竊取某個既有節點的憑證**」（C2C-019）。
一個偷到節點 X 憑證的人，**不可能同時是 `n37_probe`**。所以觀測者瞎掉是
那個模型的**正確後果**，而 N37 自己也這樣寫：

```
⚠️ 觀察不到任何東西（…）——盲打模式。Enforce 下這是預期的。
```

⚠️ **不應該為了讓它看得見而去 policy 裡加一條 `/n37_probe` 的 enclave。**
那會給攻擊者一個它在這個威脅模型下不該有的視野，而 C2C-044 加
`/parameter_write_probe` 是反過來的情況（讓**請求**合法抵達，好驗證 rcl 那一層）。

## 四、真正的缺陷：N37 誠實地記了，而沒有人讀

N37 自己記在三個地方：

```
N37_adaptive_attacker.py:518   盲打={not observer.ok}
N37_adaptive_attacker.py:601   "blind": not observer.ok        ← DECISION_TRACE
N37_adaptive_attacker.py:508   ⚠️ …盲打模式。Enforce 下這是預期的。
```

而下游：

```
firewall_lab/ 裡 "blind" 作為被消費的欄位      : 0 次
firewall_lab/ 裡 DECISION_TRACE               : 只出現在 orchestrator 的註解
manifest / training_gate / features           : 都不知道這件事
```

⇒ **資料集裡所有持證內鬼場次的攻擊者都是盲打的，而那是一個系統性的性質，
完全沒有被記錄。**

那兩個類別正是：

- 只在 Enforce 下有意義（`runner_requires_enforce`），
- C2C-056 量到「身份訊號 = 0 ⇒ 正常」那個盲點**正好落在它們身上**，
- 而 C2C-053 的整個內部威脅論述都建立在它們上面。

**所以「自適應攻擊者」這個標籤對它們從來沒有成立過，而沒有任何產物說出這件事。**

⚠️ **正確的修法是記錄，不是放寬。** 把 `blind` 從 DECISION_TRACE 拉進 manifest，
讓這個性質可稽核。那**不改變任何攻擊行為**，也不給攻擊者任何新視野。

⚠️ 要不要讓它**影響訓練閘**是另一個問題，而那是**改變通過標準**：
盲打場次的攻擊本身是真的（HMAC 偽造、參數寫入都確實執行），
所以判它不合格會丟掉真實證據 ⇒ **留給 Jesse。**

## 五、已實作（2026-10-03，經 Jesse 指示）

### `orchestrator.py`：三個刻意的決定，各有一個測試

```
_read_adaptive_blindness(session_dir, *, adaptive, attack_result)
manifest.result["adaptive_observer"] = {...}
```

| 決定 | 為什麼 | 變異檢定 |
|---|---|---|
| **三值，不是布林** | 「判不出來」**不可以**讀成「觀測者是好的」——那正是這整件事的失效形態 | 把 `blind: None` 全改成 `False` ⇒ **11 個測試失敗** |
| **不進 `gate_failures`** | 記錄不是放寬。盲打場次的攻擊是真的執行了 | 兩個測試釘住閘仍是**恰好六項**、而且不含 `blind`／`adaptive_observer` |
| **永不拋** | 一份壞掉的日誌不可以毀掉一場 live 場次 | 五種畸形輸入（500 個 `{`、JSON 物件而非陣列、`[null, 3, "x"]`、NUL 位元組、空 payload） |

另外記了 `blind_steps`／`total_steps`（**不把混合情形折疊成一個布林**，
而那正是這整件事要揭露的那種異質性）與 `observer_error`
（那行 `RCLError` 正是指認出機制的東西）。

⚠️ **執行中的 campaign 吃不到這個欄位**：它在 13:33Z 啟動時就 import 了
`orchestrator`，所以新欄位要到**下一次重啟**才出現。而**不值得為了加一個欄位
去重啟**——既有場次的資料本來就在 `attack.stdout.log` 裡。

### `工具腳本/audit_adaptive_blindness.py`：既有場次，唯讀

既有 manifest **依規則不回溯**（C2C-069、C2C-085）：manifest 記的是當時的判定，
改寫它會讓它與自己的 `code_revision` 不一致。所以用一支平行的稽核工具
——與 `zeek_checksum_fixed/`（C2C-050）、`crosscheck_v2.json`（C2C-079）同一形狀。

它**匯入** `_read_adaptive_blindness` 而不是寫第二份解析（C2C-060 記過
兩份實作會慢慢分歧），所以稽核與 manifest **在結構上必然一致**，
而一個測試釘住這件事。

**全資料集結果（2026-10-03）：**

| | |
|---|---:|
| complete 場次 | 2,053 |
| **可判定** | **1,524** |
| **盲打** | **113（可判定的 7.41%）** |
| `insider_hmac_forgery` | **55／55** |
| `insider_parameter_write` | **58／58** |
| **其餘全部 scenario** | **0／1,411** |
| 判不出來 | 529（`normal_patrol` 無攻擊行程 335、無決策軌跡 192、空軌跡 2） |

⇒ **證據從 39／39 變成 113／113**。先前那個 39 是我的臨時腳本要求 2026-10-02
才加的逐步計時字串；稽核改用 `DECISION_TRACE` 的 `blind` 鍵，而 N37 早就在記它。

⚠️ 那 192 場「無決策軌跡」正是被 SIGKILL 的那些——**軌跡隨行程一起消失**，
所以它們在這個軸上永遠判不出來。

### ⚠️ 而這支工具第一版自己就犯了同一個錯

它讀 `manifest["adaptive"]`，而旗標住在 **`manifest["randomization"]["adaptive"]`**。
於是它回報 **2,053 場全部 `not_adaptive`**——**一個不可能成功的查找回傳了令人安心
的答案**，正是這支工具存在要揭露的那種失效。

修正時把同一個三值紀律套到上一層：**欄位不在 ⇒ `unknown`，不是 `not_adaptive`**。
兩者意思不同（「這個 runner 按定義沒有軌跡」對「紀錄搬家了而我們判不出來」），
折疊它們會讓「有多少場次判不出來」這個問題不可回答。
變異檢定把 bug 放回去 ⇒ **8 個測試失敗**。

這是本輪第二次我自己的探針壞掉（第一次是時間戳切 16 個字元）。
