# 網路特徵的四個缺陷與修正（2026-08-31）

> 全程離線。未啟動 ROS、未產生攻擊流量、未使用 `sudo`、未連接第二台主機。
> 原始 pcap、`zeek/`、`manifest.json` 一個位元組都沒有改。

## 摘要

修一個缺陷暴露了第二個，第二個更根本；補上量體特徵時查出第三個；而第四個是我自己在修的過程中引入的，靠一個類別掉 0.68 才發現。

| # | 缺陷 | 影響 |
|---|---|---|
| 1 | Zeek 沒加 `-C`，校驗和卸載的封包被整批丟棄 | 位元組／封包／duration **全部未設定**；連線數虛增 **7.96 倍** |
| 2 | 網路特徵按 **流的起點**分窗 | 一條 50 秒的流只落進一個 8 秒視窗——**時間解析度是缺陷 1 的副產物** |
| 3 | 放大比用五元組反轉配對回流 | RTPS 回應來自臨時埠，實測 462 個五元組裡反轉配對 **0** 個，該特徵恆為零 |
| 4 | 比例特徵改成按五元組加權（**我引入的**） | 「九成封包打在 SPDP 埠」被去重成「用過 SPDP 埠」；Enforce `command_injection` 掉 0.68 |

修掉缺陷 1 之後每場視窗數從 7 掉到 3、攻擊視窗少了 87%。**那不是修壞了，
是修好資料才讓分窗方式的錯誤露出來**——舊表之所以有 7 個視窗，是因為被丟棄
的封包把一條長流碎成幾千筆短紀錄，剛好散佈在整場上。

兩個都修完之後，時間解析度**完整取回**（逐類攻擊視窗數與舊表逐位相同），
而且量體資料是正確的。

## 缺陷 1：Zeek 校驗和卸載

### 證據

Zeek **自己每一場都警告過**，警告就存在各場的 `zeek_process.json` 裡：

> Your trace file likely has invalid UDP checksums, most likely from NIC
> checksum offloading. ... packets with invalid checksums are discarded

1,100 場的 argv 一模一樣，沒有一場帶 `-C`。

同一份 pcap（`20260813T080943935043Z_oversized_scan_4d59dce0`）：

| | 不加 `-C` | 加 `-C` |
|---|---:|---:|
| conn 筆數 | 3,932 | **462** |
| `orig_bytes` | 未設定 | 21,440 |
| `orig_pkts` | 0 | 130 |
| `duration` | 未設定 | 34.7 |
| `history` | `CC`（校驗和錯誤） | `D` |
| 連線狀態 | `OTH` | `S0` |

全資料集：conn 列數 **3,324,190 → 417,840**（7.96× 膨脹）。
重跑的 300 場另外是 326,238 → 38,930（8.38×）。

**比拿不到位元組更嚴重的是連線數。** `conn_count` 與 `conn_rate` 是一直在用的
特徵，它們量到的是校驗和造成的流碎裂，不是連線行為。

### 修法

`工具腳本/rebuild_zeek_checksum.py` 用同一份 pcap 加 `-C` 重跑，
沿用該場當初的 `udp_inactivity_timeout`。

**不覆寫原始證據**：`zeek/conn.log` 的大小與 SHA-256 記在 `manifest.json` 裡，
覆寫會讓 `verify_manifest_evidence()` 對整個資料集失敗。重建結果寫到平行目錄
`zeek_checksum_fixed/`；manifest 只檢查它自己列出的檔案。原始壞資料保留，
它是「缺陷長什麼樣」的唯一實證。

fail-closed：`-C` 生效時 Zeek 就不會再發那則警告，所以「新 stderr 仍含警告」
直接代表旗標沒吃到，該場標為 `flag_ineffective` 而不是靜靜收下。rc≠0、
conn.log 空、位元組欄位仍全空同理。實跑 **1,100／1,100 ok**、1 場無 pcap。

## 缺陷 2：按流起點分窗

### 為什麼修好缺陷 1 反而讓表變小

`conn.log` 一筆代表**整條流**，時間戳是**起點**。同一場：

| | 舊（損壞） | 新（`-C`） |
|---|---:|---:|
| conn 筆數 | 3,932 | 462 |
| 流**起點**跨度 | 51.4 秒 | **9.0 秒** |
| 起點落在哪些 8 秒視窗 | 0–6 | **只有 0–1** |

真實流量跨度是 **46 秒**（逐封包量測的中位數），但流的起點全部擠在前 9 秒。
所以「按 conn.log 的 ts 分窗」量到的是**這個視窗裡開始了幾條流**，
不是**這個視窗裡有多少流量**。

**舊表每場 7 個視窗的時間解析度，是缺陷 1 的副產物。**

### 修法

`工具腳本/extract_packet_windows.py` 對每場跑一次 `tshark`，把逐封包的
`(時間, 來源, 目的, 來源埠, 目的埠, 長度)` 存成 `packet_windows/packets.tsv.gz`。
**只抽取、不聚合**——分窗與特徵怎麼算是下游的決定，原始逐封包紀錄留著才能
重算與稽核。

`features.py` 新增 `--network-source {conn,packet}`（**預設仍是 `conn`，
出貨行為未變**）。封包版的計數單位是**視窗內的五元組**：一條流跨 7 個視窗
就在 7 個視窗各出現一次，帶著它在那個視窗裡實際傳的位元組。

- `conn_count` = 這個視窗裡**活躍**的五元組數（不是流的起點數）
- `orig_bytes` = 來源在這個視窗裡實際送出的位元組
- `interarrival_cv`／`burstiness` 用**逐封包**時間戳，那才是流量形狀

抽取量：dataset_live **9,966,923 個封包**（每場中位數 10,012，跨度中位數
46.1 秒）；rerun300 **1,617,797 個**。新增磁碟 71 MB ＋ 52 MB。

## 順帶查到的第三個缺陷：放大比恆為零

`amplification_ratio` 在 conn 版與封包版**都是 0.00% 非零**。原因不是沒有回流，
是配對方式在這個協定上不成立：

**RTPS 的回應來自對方的臨時埠，不是鏡像埠。** 實測一場的 462 個五元組，
存在嚴格反轉配對 `(dst, dport, src, sport)` 的是 **0** 個。Zeek 也因此把回流
記成另一條連線，`conn_state` 停在 `S0`。

改成按**主機**計：`resp_bytes` = 這個視窗裡送到這台主機的總位元組。
反射攻擊要問的本來就是主機層的問題——這台送出多少、收回多少。
回歸測試用**不對稱的埠**釘住這件事，修正前那個測試會失敗。

## 防止再犯

| 閘門 | 擋什麼 |
|---|---|
| `features.py` 拒絕混用 conn.log 來源 | 一半重建一半沒有，等於把「被重建過」偷渡成特徵 |
| `merge_rerun_features.py` 比對 `feature_build.json` | **欄位名不論分窗方式都一樣**，欄位比對擋不到；缺欄位算不一致，不算相符 |
| 重建腳本檢查警告是否消失 | 旗標沒吃到時不會靜靜收下壞結果 |
| 封包 artifact 缺失即拒絕建表 | 靜靜回傳空清單會讓該場消失，看起來像「這場沒有流量」 |

新增測試 **33 個**（`test_zeek_checksum_rebuild.py` 14、`test_packet_windows.py`
14、`test_merge_provenance.py` 6，扣掉重疊計數）。完整測試 **842 passed、
0 failed**。

## 第四個缺陷：比例特徵的分母（是我自己引入的）

第一版封包實作跑出來，Permissive 上升但 **Enforce 掉了 0.129**。逐類拆開，
下降幾乎全部來自單一類別：`command_injection` **0.833 → 0.150**，其餘八類
小幅變動，二元 PR-AUC 幾乎沒動（0.9906 → 0.9896）。

**一個類別掉 0.68 而其餘不動，是特徵資訊被抹掉的樣子，不是資料變乾淨的樣子。**

先驗證了一個假設再放棄它：校驗和碎裂比是否帶著 scenario 指紋？

```
enforce 各攻擊 scenario   0.379 – 0.395   （幾乎相同）
enforce normal_patrol     0.533
permissive 各攻擊         0.215 – 0.252
permissive normal_patrol  0.373
```

碎裂比只分得出正常與攻擊，**不帶類別資訊**，假設不成立。

真正的原因：`spdp_ratio`、`meta_ratio`、`userdata_ratio`、`mcast_ratio`、
`dst_port_entropy`、`dominant_port_ratio`、`dominant_host_ratio`、
`tuple_repeat_ratio` 問的都是「**流量**分布長什麼樣」。

損壞版意外做對了這件事——流被打碎成幾千筆短紀錄，每筆約對應幾個封包，所以
那些比例實際上一直是**按封包量加權**的。第一版封包實作改成按**五元組**加權，
等於把「九成封包打在 SPDP 埠」去重成「我用過 SPDP 埠」。

修法：比例特徵按封包加權，`conn_count`／`conn_rate` 維持按單位（視窗內活躍
的五元組數）。**兩個分母本來就是不同的東西**；conn 來源兩者相等，行為逐位不變。

## 重訓結果（validation only）

四組訓練：{舊表, 封包表} × {Permissive fusion, Enforce network}。

**先確認控制組**：舊表在新程式下**逐位重現**
（0.8823005031122984、0.4673621699926408），所以這些改動對 conn 路徑
一個位元都沒有動到。

| | 舊表 | 封包表 | 差 |
|---|---:|---:|---:|
| **Permissive** balanced accuracy | 0.8823 | **0.9243** | **+0.0420** |
| Permissive macro F1 | 0.8617 | **0.9174** | +0.0556 |
| Permissive binary PR-AUC | 0.9937 | 0.9992 | +0.0055 |
| **Enforce** balanced accuracy | 0.4674 | **0.4892** | **+0.0218** |
| Enforce macro F1 | 0.4578 | **0.4867** | +0.0289 |
| Enforce binary PR-AUC | 0.9906 | 0.9941 | +0.0036 |

### Permissive 逐類：全部持平或上升

| 類別 | 舊 | 新 |
|---|---:|---:|
| `normal` | 0.864 | **0.966** |
| `identity_abuse` | 0.552 | **0.706** |
| `command_injection` | 0.588 | **0.706** |
| 其餘六類 | 0.966–1.000 | 0.970–1.000 |

`normal` recall +0.102 是誤報大幅下降；升最多的兩類正是至今沒有專屬證據通道的
那兩類——**量體特徵補的正好是它們缺的東西**。

### Enforce 逐類：五升三降

| 類別 | 舊 | 新 |
|---|---:|---:|
| `replay_dos` | 0.272 | **0.456** |
| `replay` | 0.350 | **0.520** |
| `service_dos` | 0.375 | **0.542** |
| `sensor_spoof` | 0.387 | **0.477** |
| `normal` | 0.922 | **0.966** |
| `message_dos` | 0.171 | 0.205 |
| `identity_abuse` | 0.438 | 0.419 |
| `parameter_tamper` | 0.458 | 0.342 |
| **`command_injection`** | **0.833** | **0.475** |

### 關於 `command_injection` 那 0.833

它在舊表是**強烈的離群值**（次高只有 0.458），在新表落回其他類別的區間
（0.34–0.54）。

**無法乾淨歸因。** 兩張表的 `burstiness`／`interarrival_cv`／`dst_port_entropy`
中位數都沒有讓它突出，所以那 0.833 來自更高階的結構，不是單一特徵的位移。

可以確定的是它**依賴什麼**：舊表的網路特徵是從一份**依校驗和有效性挑選出來的
封包子集**算出來的（約 39% 的封包被 Zeek 接受）。而校驗和卸載是**擷取主機網卡
的性質**，不是攻擊的性質——同一套系統換到 Pi 5 或任何其他主機上，這個子集會
完全不同。

所以：不主張 0.833 是假的，但它**不可重現於真實流量**，也不該被依賴。

## 現在的狀態

- 完整測試 809 → **846 passed、0 failed**
- `--network-source` 改為**必填**，沒有預設值。兩種基底欄位相同、意義不同，
  選錯不會有任何徵兆——所以每一次建表都要明講用哪一種

  training gate**：抽取失敗時 Zeek 證據仍然有效，讓一個後處理步驟否決掉
  一場真實 live 資料是不成比例的
