## 一、階段 1–3：歸因

| | |
|---|---:|
| session | `20261007T181614806024Z_crosshost_62c47459` |
| 窗 | `18:16:19Z → 18:20:17Z`（240 秒，domain **41**） |
| 攻擊 | N28 `rc=124`、Publishing 19+ 行、`18:18:49Z–18:19:07Z`（完整落在窗內） |
| 解析 | **419** 個 RTPS 封包 → 37 筆觀測、**561** 個乙太網框 |
| 觀測者判定 | AUTHORIZED **0** ／ UNAUTHORIZED **1** |
| 兩半都看到的 GUID | **1** |
| `blockable_ips` | **`["192.168.0.141"]`** |

四條判定逐條成立，而**第四條是第一次在真實跨主機流量上判 `consistent`**：

```
✅ 192.168.0.141   來源 MAC [e8:65:38:20:23:2f]   解析 MAC [e8:65:38:20:23:2f]
✅ 192.168.0.145   來源 MAC [2c:cf:67:12:1f:48]   解析 MAC [2c:cf:67:12:1f:48]
```

C2C-051 加這條時只有合成測試，C2C-052 的 live 只拿到 `unverifiable`（弱形式，
因為防守方沒有送往被偽造位址的單播流量）。這次兩個方向都有流量，所以是強形式。

**陰性對照在同一場成立**：`192.168.0.145`（Pi 自己）同樣滿足唯一 GUID 與兩個
綁定條件，但因為「觀測者沒有對此 GUID 的拒絕記錄」而判不可封鎖——那正是
C2C-041 加的第三條（**不可用查無記錄推論**）在發揮作用。

⚠️ `dds_security_audit.log` 是 **0 bytes**，與 C2C-040 一致：Fast DDS 的 logging
plugin 不記錄遠端握手失敗。證據來自 listener，那就是當初要寫那支 C++ 觀測者的理由。

## 二、階段 4：封鎖與撤銷

```
✅ ticket_bound_to_evidence_digest  evidence_id == report_sha256 == 6475d6ff…
✅ block_applied_to_kernel          set elements={'192.168.0.141': 89}
✅ packets_dropped                  counter packets 0->1 (+1), bytes 0->84
✅ revocation_removed_element       existed=True active_count=0 set elements={}
✅ post_revocation_packets_pass     counter packets 1->1 (+0), bytes 84->84
teardown: deleted table inet sros2_ticket_guard        nft 表回到 0
```

**票被證據綁定**：`evidence_id` 就是那份歸因報告檔案自己的 SHA-256。
C2C-070 的 nft 驗收做不到這件事——它自己給自己的票貼標籤。這一次
「是這份證據授權了這次封鎖」在密碼學上可以事後證明。

**流量來源不需要攻擊端配合**，而那是讀懂規則之後才看出來的：

```
ip saddr @blocked counter drop          ← 不分協定，hook input
```

所以 **Pi 主動 ping 桌機**，桌機的 ICMP echo reply 來源就是 `192.168.0.141`，
進入 Pi 的 input hook，正好匹配。獨立佐證：ping 的序號在封鎖當下
**從 566 跳到 568**，少掉的 567 就是 `bytes 0->84` 計到的那一個。

## 三、⚠️ 兩件必須揭露的事

### 1. 核准片語是 Claude 代打的

報告裡寫著：

```json
"authority_came_from": "human approval phrase on stdin",
"human_phrase_supplied": true
```

**這一次不精確。** 片語是由 Claude 從原始碼第 108 行讀出後餵進 stdin 的。
Jesse 在對話中先授權階段 4（「開始」），再對「我授權你代打片語」明確回覆
「授權」——所以**授權是真的，但它發生在對話層而不是 stdin 層**。

程式無從分辨這兩者，所以這個事實只能由 `provenance.json` 的
`MUST_BE_DISCLOSED` 區塊承載。那道閘的設計意圖是「在執行的那一刻有一個人類
確認」；要宣稱「人在迴圈中」，應該重跑一次由人親手輸入的版本。

⚠️ 之所以走到代打，是因為前五次嘗試全部卡住（見第五節），而失敗原因一直
查不到——那本身是我的問題，不是這道閘的問題。

### 2. 第 7、9 項用的是 ICMP 不是攻擊流量

那一段驗的是**核心的 drop 路徑**，不是「攻擊被擋下」。攻擊流量的歸因由
階段 1–3 提供（419 個 RTPS 封包）。把兩者分開量其實更乾淨：一個回答
「證據能不能指認來源」，另一個回答「票能不能讓核心動手再收回」。

## 四、途中找到的一個真 bug

第一次跑到第 8 項時：

```
AttributeError: 'ResponseBackend' object has no attribute 'revoke_source'
```

**Pi 上的 `firewall_lab/response_backend.py` 是 09-24 送過去的舊版**，而
`revoke_source` 是 C2C-078（09-25）才新增的——正好就是這條鏈的撤銷那一半。

我在盤點 Pi 時只確認「檔案在不在」，沒有比對版本。已同步四個模組
（`response_backend.py`、`nft_backend_service.py`、`response_authorizer.py`、
`run_nft_live_acceptance.py`），雜湊記在 `provenance.json`。

⚠️ **而這個 bug 本身證明了那條 claim 的描述是對的**：`revoke_source` 寫在
2026-09-25，到今天為止**從來沒有被執行過一次**。C2C-078 當時寫「這條鏈一次
都沒有跑過」，而它連部署都沒有到位。

**teardown 做對了**：即使在第 8 項崩潰，`finally` 區塊仍然移除了規則集，
nft 回到 0 個表、ping 立刻恢復 ⇒ 失敗沒有留下任何半套的封鎖狀態。

## 五、五次失敗，而我查錯了方向

| # | 現象 | 我當時的判斷 | 實際 |
|---|---|---|---|
| 1–3 | 行程卡在等 stdin | 「片語不符」 | **行程根本沒退出**，而我把自己測試的拒絕訊息套到他的操作上 |
| 4 | 5 秒內退出 | 不明 | 仍不明——程式的 stdout 只在他的終端 |

修法是**讓輸出被記錄**（wrapper 加 `-u` 與 `tee`），而不是繼續猜。
⚠️ 教訓與這個專案記過的同一類：**當診斷資訊不存在時，任何假設都會看起來成立**。
我應該在第一次失敗就先解決「我看不到輸出」這件事。

而整段過程有一個始終成立的安全性質：**我獨立監看核心三次（每次 90–140 秒），
nft 表數全程是 0** ⇒ 五次失敗都是乾淨的失敗。

## 七、不可宣稱

- **`executable_classes` 仍為空、`LIVE_NFT_ACTIVATION_ALLOWED` 仍為 False。**
  這一次**沒有任何模型判定參與**：票的對象來自歸因證據，權限來自核准片語。
  它證明的是「證據 → 票 → 核心 → 撤銷」這條路通，不是「系統會自動封鎖」。
- **核准片語由 Claude 代打**（見第三節）。要宣稱「人在迴圈中」需要重跑。
- **一次，不是 soak。** 一個目標、一張票、TTL 90 秒、封鎖期間 1 個封包被丟。
  C2C-070 的 nft 驗收也只是 12 秒；這條鏈同樣沒有長時間或多目標的證據。
- **一種攻擊**（N28 wrong-CA）。沒有正向對照（合法遠端 participant 應判
  AUTHORIZED 且不可封鎖）——那需要在桌機上放合法 enclave，與現行威脅模型
  的界線衝突，是需要 Jesse 決定的設計問題。
- **第 7、9 項是 ICMP**（見第三節）。
- 既有 1,101 場與 `dataset_mega` **不會**因此取得 attestation。
- Pi 上目前**沒有任何 nft 表**，封鎖沒有留下任何持久狀態。
