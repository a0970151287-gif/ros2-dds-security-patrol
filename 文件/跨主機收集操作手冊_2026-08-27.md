## 步驟 0 — 防守端：確認 mirrored 生效

```bash
wsl -d Ubuntu-24.04 bash -lc 'ip -4 -o addr show'
```

**過關條件**：看到一個 `192.168.0.x` 的位址。

看到 `172.30.x.x` 就是還在 NAT——確認 `.wslconfig` 是 `networkingMode=mirrored`
並且 **Windows 已經重新開機**（`wsl --shutdown` 不夠，主機的 HNS 要完整重置）。

接著確認擷取介面的名字，mirrored 之後可能不叫 `eth0`：

```bash
wsl -d Ubuntu-24.04 bash -lc 'dumpcap -D'
```

記下帶著區網位址的那個介面名，步驟 4 要用。

⚠️ **不會是 `eth0`。** 2026-08-27 重開機後實測是 **`eth2`**，而且這個編號
不保證固定——每次都要用 `dumpcap -D` 現看，不要照抄。

## 步驟 1 — 兩台互 ping

兩台各自查位址（前三段要一樣）：

```bash
ip addr
```

然後互 ping。**ping 不通不要往下走。** 常見原因：一邊 Wi-Fi 一邊有線被路由隔開、
兩台連到不同 SSID、或路由器開了 AP isolation。

## 步驟 2 — UDP 可達性（**不可跳過**）

`ping` 是 ICMP。防火牆放行 ICMP 卻擋 UDP 是很常見的設定，而 DDS 走 UDP。

**防守端先跑**：

```bash
wsl -d Ubuntu-24.04 bash -lc 'cd /mnt/c/Users/Jesse/Documents/專題ROS2 && ~/.venvs/sros2-firewall/bin/python 工具腳本/check_udp_reachability.py --listen --domain 30 --seconds 60 --output /home/jesse/reachability.json'
```

**攻擊端在這 60 秒內跑**：

```bash
python3 check_udp_reachability.py --send --target 192.168.0.129 --domain 30
```

（`--target` 換成步驟 0 量到的實際位址。）

三種結果：

| 結果 | 處置 |
|---|---|
| **兩條都通** | 直接進步驟 3 |
| **只有單播通** | **照樣可以跑**——步驟 3 一定要帶 `ATTACKER_IP`，讓 discovery 走 unicast peer 而不是多播 |
| 兩條都不通 | **停**。這時才需要 Windows 防火牆規則。先解決，不要硬跑 |

Wi-Fi 對 Wi-Fi 常見「單播通、多播不通」——AP 用最低 basic rate 發多播，
加上 IGMP snooping 就可能整個吃掉。這是**可以接受**的，不必修。

## 步驟 3 — 取得授權

live 跨主機操作依規則 5 需要 **Jesse 對該次操作的明確授權**，
不因步驟 2 已完成而延續。

## 步驟 4 — 防守端開觀測視窗

```bash
wsl -d Ubuntu-24.04 bash -lc 'cd /mnt/c/Users/Jesse/Documents/專題ROS2 && ATTACKER_IP=192.168.0.30 bash 工具腳本/run_crosshost_identity.sh eth0 90'
```

`eth0` 換成步驟 0 記下的介面名。

`ATTACKER_IP` 有兩個作用，都很重要：

1. 當成觀測者的 **unicast initial peer**，discovery 不依賴多播；
2. 交叉比對時檢查攻擊者的封包**到底有沒有到**——沒到就把整輪標成無效，
   而不是安靜地少一列。

腳本會印出「攻擊視窗開始」的 UTC 時間。**看到那一行再叫攻擊端動手。**

## 步驟 5 — 攻擊端在視窗內執行

```bash
source /opt/ros/jazzy/setup.bash && export ROS_DOMAIN_ID=30 && export ROS_AUTOMATIC_DISCOVERY_RANGE=SUBNET && export ROS_STATIC_PEERS=192.168.0.129 && bash ~/N28_wrong_ca_participant.sh 40
```

`ROS_AUTOMATIC_DISCOVERY_RANGE` 不能是 `OFF`，否則 rcl 會忽略 `ROS_STATIC_PEERS`。

**攻擊端要回報**：rc（124 或 0 才算跑了）、`Publishing` 行數、UTC 起訖時間。
rc 是其他非零值代表 participant 根本沒起來，**不可視為攻擊已執行**。

## 步驟 6 — 讀結果

腳本最後會印出交叉比對。要看的是這幾行：

```
封包看到的 GUID   : ?
來源位址          : ?
觀測者判定 AUTHORIZED / UNAUTHORIZED : ? / ?
**兩半都看到的 GUID** : ?
```

### 什麼算成功

```
  ✅ 可封鎖位址：192.168.0.30
```

要同時滿足三條：該 IP 只掛一個 GUID、該 GUID 沒有合法身分記錄、
**且觀測者對它有一筆明確的 UNAUTHORIZED 判定**。

第三條是刻意要求「正面證據」而不是「查無記錄」——觀測者靜默失效是真實會發生的事
（見下表），那種情況下每個正常 participant 都會看起來可封鎖。

### 什麼算無效（不是失敗，是這一輪不算數）

| 輸出 | 意思 |
|---|---|
| `⛔ 本輪證據無效：攻擊機位址 … 在擷取檔裡完全不存在` | 封包沒到這台。網路路徑問題，**不是**防禦擋住了 |
| `⚠️ 交集為零——兩半沒有對上` | 擷取介面錯、時間沒重疊、domain 不同、或 FastCDR 不同源 |
| 觀測者事件檔是空的但攻擊確實跑了 | 見下方「已知的靜默失效」 |

**以上任何一種都不可以寫成結論。**

---

## 已知的靜默失效（都已經做成 fail-closed，這裡只是供對照）

| 現象 | 根因 | 現在的防線 |
|---|---|---|
| 觀測者跑滿視窗、log 乾淨、事件檔空的 | `libfastcdr` 與 `libfastrtps` 不同源，discovery 靜默失效 | runner 的 preflight 用 `ldd` 斷言，不符即中止 |
| 攻擊者位址不在擷取檔裡 | 網路路徑不通 | `ATTACKER_IP` → 報告標成「本輪證據無效」 |
| 攻擊「跑完了」但 rc 非 124/0 | participant 沒起來 | N28 自己會大聲報錯 |
| 多播被 AP 吃掉 | Wi-Fi | `ATTACKER_IP` 兼作 unicast initial peer |
