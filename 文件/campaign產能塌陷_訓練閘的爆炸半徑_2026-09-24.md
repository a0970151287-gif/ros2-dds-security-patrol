## 二、真因不是 SHM，是 `gate=not_eligible:attack_process`

`execute_campaign` 對訓練閘失敗是 `raise`，所以**一場不合格殺掉整批 40 場
＋ 一次 stack 啟動**。

量 406 場自適應場次的 `attack_process.duration_sec` 減去給定預算：

| | n | 超出預算 |
|---|---:|---|
| 乾淨退出 | 348 | min +0.00、median **+0.01**、max +0.08 |
| 被 SIGKILL | 58 | min +0.06、median **+2.81**、max +3.73 |

⚠️ **更正：這兩列裡只有第二列是證據。**

我原本從第一列推論「預留被啟動吃光」。那個推論是錯的，因為 `duration_sec`
量的是**工廠的視窗**而不是 N37 的退出時間——`orchestrator` 是
`_phase_sleep(duration)` 睡滿之後才 `stop()`，所以一個提早在 t=70 退出的 N37
一樣會記成約 77 秒。第一列的 `+0.01` 只反映那個固定的 sleep。

**第二列成立。** `+2.81` 是工廠 `stop()` 從 SIGTERM 升級到 SIGKILL 所花的時間，
而那只在 **N37 在 deadline 時還活著**的情況下才會發生。

真正的證據來自修正自己新增的遙測：實測 **啟動耗時 2.79 秒 / 預留 4 秒**。
`t0 = time.monotonic()` 寫在 `main()` 裡，在參數解析與 `firewall_lab` 的 import
之後（repo 在 `/mnt/c` drvfs 上，讀取慢），所以

```
stop_by = process_start + startup + duration - 4
        = process_start + duration - 1.21     ← 真實餘裕只有約 1.2 秒
```

而收子行程最壞要 `2 × CHILD_REAP_SEC` = 2 秒。**1.2 < 2 ⇒ 必然超時。**

疊上第二個原因：burst 被切成「剩餘時間的**全部**」，`observer.pump(burst)`
一結束就已經在 `stop_by` 上，那 2 秒的收子行程於是整段落在 deadline 之後。

**58／406 = 14.3%。**

被砍最多的兩類是 `heartbeat_replay`（9）與 `unauthorized_participant`（7）
——正是 C2C-024 記過「Enforce 下 RELIABLE writer 配不到訂閱者、
`destroy_node()` 會卡住」的那些，所以它們每次都用滿那 2 秒。

### 爆炸半徑的算術

40 場一批、單場失敗率 14.3%：

```
一批跑到底的機率 = 0.857^40 ≈ 0.2%
```

**幾乎每一批都會死。** 這完全解釋了 69 → 2 → 4 的塌陷。

## 三、兩個修正

### A. N37 從**行程啟動**起算預算

```python
_PROCESS_START = time.monotonic()   # 在任何昂貴的東西之前
...
t0 = _PROCESS_START
startup_cost = time.monotonic() - _PROCESS_START
```

並新增 `BURST_EXIT_RESERVE_SEC = 2 * CHILD_REAP_SEC`，burst 的長度要扣掉它，
讓收子行程落在 `stop_by` **之前**。啟動耗時現在會印進決策軌跡——先前它是
不可見的，所以兩輪都沒人發現。

### B. 一場不合格不再殺掉整批

⚠️ **訓練閘本身沒有放寬。** 不合格的場次仍然是 `training_eligible: false`，
仍然進不了訓練集——那份證據在它被寫到磁碟的當下就已經是正確且安全的。
`raise` 並沒有增加任何安全性，只是額外毀掉同一批剩下的 39 場。

改成記錄為 `status="ineligible"` 並繼續，而**仍然 fail-closed，只是改看比率**：

```python
MAX_INELIGIBLE_BEFORE_ABORT = 5     # 數量下限：不讓三場的 smoke 一次就中止
MAX_INELIGIBLE_RATE = 0.25          # 比率：這才是偵測「stack 壞了」的那一半
```

兩個條件要同時成立。扣掉 N37 缺陷之後的殘餘不合格率是 **7／406 = 1.7%**，
所以 25% 遠高於正常運作會產生的任何值。

`ineligible` 在一次執行內與 `repair` 裡都是**終態**。監督器每一輪都會呼叫
`repair`，自動重排會讓一個系統性壞掉的 scenario 無限重跑——那正是這支監督器
其他機制在防的形態。修好成因之後用 `repair --reset-ineligible` 明確放回。

## 四、我自己在這一輪製造的兩個缺陷（都被測試抓到）

1. **patch 吞掉了既有的 `entry["error"] = None`**，於是修復過的 `failed` entry
   會留著一個已經不適用的 ValueError。既有測試 `test_repair_flips_...` 抓到。
2. **requeue 被我放進「只處理內鬼 entry」的迴圈裡**，範圍完全錯——
   `--reset-ineligible` 會只放回同時需要改模式的那幾個，而且回報一個看起來
   對的數字。已改成獨立一輪掃過所有 entry，並補了一個專門驗這件事的測試。

第二個值得記：**它不會壞掉，只會少做事並且安靜地回報成功**。

## 五、不可宣稱

- 兩個修正**還沒有 live 證據**。修正後的 campaign 剛重啟，要看新一批的
  `inside_sec` 與不合格率才算驗過。判準已經寫下來：不合格率應該回到 1.7%
  附近，步調中位數應該回到約 95 秒。
- 14.3% 這個數字含 09-19 那批退化場次；乾淨環境下的真實值可能更低。
- `MAX_INELIGIBLE_RATE = 0.25` 是從 1.7% 的殘餘率往上取的，**沒有在
  「stack 真的壞掉」的情境下驗過它會咬**——那需要刻意弄壞一次 stack。
- N37 的啟動耗時 **2.79 秒**是 `/mnt/c`（drvfs）上的單次觀測，n=1。把 repo 搬到
  WSL 原生檔案系統應該會大幅縮短，但那是另一件事，本輪沒有做。
- ⚠️ 修正後的前 4 場殘差中位數 **+258.7 秒**，比 2026-09-19 那次退化（+116.8）
  **還嚴重**，而且 4 場裡有 2 場 `packet_windows` 逾時。所以這台機器目前確實
  在退化狀態，量體無法解釋。
- ⚠️ **我自己很可能是原因之一**：同一段時間我在同一台機器上跑了三次完整測試、
  並對 500 場資料集做了多次全量掃描，全部在 `/mnt/c` 上。要判斷真因必須在
  沒有其他負載的情況下再量一次。
- **49／502 場的 `packet_windows` 逾時失敗，其中 40 場仍是 `training_eligible:
  true`**——那些場次沒有封包分窗，網路特徵是缺的，而訓練閘沒有看這一項。
  這是本輪發現、**尚未處理**的資料品質缺口。
