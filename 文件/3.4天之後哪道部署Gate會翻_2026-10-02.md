## 二、`minimum_1100_independent_sessions` 會翻，而它是第一次

```python
"minimum_1100_independent_sessions": int(
    frame["group_id"].astype(str).nunique()
) >= MIN_DEPLOYMENT_SESSIONS,      # = 1100
```

它數的是**這一次訓練的特徵表裡有幾個相異場次**。因為模型是**分模式**的，
每個模式各算一次，而現況是每邊 550 ⇒ 從來沒有通過。

跑完之後（用 C2C-095 的保守上界 3.7% 不合格）：

| 模式 | 已合格 | pending | 保守預估合計 |
|---|---:|---:|---:|
| enforce | 369 | 1,602 | **約 1,912** |
| permissive | 993 | 535 | **約 1,508** |

**兩個模式都遠超 1,100** ⇒ 這道 gate 第一次會通過。

⚠️ 但它只是**十一道裡的一道**，而且是最不需要判斷的那一道。
`MIN_DEPLOYMENT_SESSIONS = 1100` 本來是為 pooled 模型寫的
（CLAUDE.md 記過這一點），分模式之後它一直是個算術上的副作用。

## 三、`all_policy_classes_present` 與資料量無關

```python
"all_policy_classes_present": set(calibrated.classes_) == policy_classes,
```

**集合相等**，而：

```
action_policy.json 的 rules : 23 條（含 normal）
scenarios.json 可產生       : 20 類
policy 有而 catalog 沒有    : baseline_poisoning, cmd_vel_race, node_name_evasion
catalog 有而 policy 沒有    : （無）
```

而 campaign 實際產出的類別數就是 catalog 的上限：**enforce 20、permissive 18**
（兩個持證內鬼只在 Enforce 下有意義）。

⇒ **20 ≠ 23、18 ≠ 23，再跑多久都一樣。** 這一項要的是三支 runner：

| 缺的類別 | 狀態（來自攻擊面覆蓋那一列） |
|---|---|
| `baseline_poisoning` | 兩輪都**正好在地板上**，不可分 |
| `cmd_vel_race` | 與 `cmd_vel_injection` 同機制 |
| `node_name_evasion` | 兩輪 0／0／0——**規避成功，是結果不是缺口** |

⚠️ 第三項值得單獨講：`node_name_evasion` 之所以產不出資料，是因為它**成功繞過了
白名單比對**。要讓它「可產生資料」等於要讓防禦偵測到它——那是**改防禦**，
不是補 runner。所以這道 gate 的 100% 定義本身可能需要 Jesse 重新決定，
而**那是放寬標準，不是我該自己改的**。

## 四、`fusion_feature_contract` 是一個在重訓時才決定的選擇

```python
"fusion_feature_contract": feature_set == "fusion",
```

出貨的兩個模型是 `final_permissive_fusion` 與 **`final_enforce_network`**
⇒ Enforce 這一道現在就是 ❌，而原因不是資料，是**當初選了 network**。

⚠️ 但那個選擇是有依據的：C2C-054 量到 Enforce 的 telemetry-only 只有 0.3083、
network-only 0.2420，差距很小。

**而我原本以為「重訓照 r4 註冊走就會把這一道翻過來」，那是錯的。** 去查了之後：

```
grouped_training.FEATURE_SETS = {"network", "telemetry", "fusion"}   ← 被驗證的,不合就 raise
r4 註冊的 feature_variant     = "full"                               ← **另一套詞彙**
retrain_from_registration.py:154   if feature_variant != "full": raise
```

`full` 在那裡的意思是「六個聚合統計量全用、不丟死欄位」，是 `session_aggregate`
的概念，**不是 `FEATURE_SETS` 的成員**。兩套詞彙不會相撞，原因比「它們相等」
更根本——**它們不在同一條路上。**

## 四之二、⚠️ 真正的缺口：已註冊的重訓路徑完全不評估部署 gate

```
retrain_from_registration.py 裡 deployment_gates 的出現次數  : 0
                             deployment_eligible             : 0
                             train_grouped                   : 0
它呼叫的是 compare_session_models 的 aggregate_sessions / make_model
```

而那十一道 gate 住在 `grouped_training.py:1054`。兩者用**不同的問題表述**：

| | 表述 | 特徵詞彙 | 產出 gate？ |
|---|---|---|---|
| `grouped_training.py` | **逐視窗** | `FEATURE_SETS`（network／telemetry／fusion） | **✅ 十一道** |
| `retrain_from_registration.py` | **`session_aggregate`**（2026-09-16 選定） | 六個聚合統計量 | **❌ 一道都沒有** |

三個後果：

1. **照註冊重訓會得到一個處女 holdout 上的識別率，但沒有任何 gate 判定。**
2. 要拿到 gate 判定就得跑 `grouped_training`，而那是對 Enforce **較差**的那個
   表述（出貨 test 0.4155，而 `session_aggregate` 的 CV 是 0.6851）。
3. **那些 0.80 的門檻是為逐視窗表述校準的**，直接套到場次層級不可比
   ——C2C-059 已經記過「場次層級與視窗層級是不同的任務」。

⇒ **「3.4 天之後哪道 gate 會翻」這個問題，答案取決於跑哪一條路**，
而目前兩條路沒有一條同時具備「選定的表述」與「gate 判定」。

⚠️ 把 gate 那一段移植到新表述會**改變 `deployment_eligible` 的意義**
（門檻的校準基礎變了）⇒ **那是改變通過標準，要 Jesse 決定，我沒有做。**
本輪只是把這個缺口變成可見的，而它先前只會在重訓那天才現形。

## 五、所以 3.4 天買到的是什麼

**買到的**：

1. `minimum_1100_independent_sessions` 第一次通過（兩個模式）。
2. **每類約 95 場**（對現在 CV 的 17 場是 5.6 倍），這是識別率與未知攻擊
   唯一還沒走過的軸——C2C-064／065／066／088 已經把超參數、問題表述、
   24 個學習法與 Enforce 的 24 格評分器×池化全部走完，剩下的只有樣本數。
3. **一批沒有被花過的 open-set holdout**——現有的已用第三次，數字不可引用。
   那是待辦表上剩下兩項需要新 campaign 的其中一項。

**買不到的**：

1. `all_policy_classes_present`（3 支 runner，其中一支的「缺口」其實是防禦有效）。
2. `validated_live_multimodal_contract`（已量到的否定）。
3. 跨主機那條端到端鏈（需要兩台機器）。

⇒ **3.4 天之後 `deployment_eligible` 仍然是 false，而那是對的。**
它買到的是「識別率與未知攻擊有沒有可能達標」這個問題第一次有足夠解析度去回答。
